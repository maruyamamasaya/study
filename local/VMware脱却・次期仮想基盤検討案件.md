## 1. 案件の背景

現在、TEPcube上のクラウド環境において、VMwareを利用した仮想基盤が稼働している。

近年のVMwareライセンス体系や契約体系の変更により、VMware環境の継続利用にかかるコスト増加が見込まれている。

そのため、本案件では、

> **現在のVMware環境を継続するのか、別の仮想基盤やクラウドサービスへ移行するのかを検討する**

ことが主な目的となる。

```text
VMwareのライセンス・利用コスト増加
                ↓
現行環境を継続すべきか再検討
                ↓
VMware以外の選択肢を比較
                ↓
次期仮想基盤の選定・移行
```

---

## 2. 移行対象

移行対象は、オンプレミス環境ではなく、

> **TEPcubeのクラウド基盤上で稼働しているVMware環境**

である。

```text
TEPcube（クラウド基盤）
        │
        └─ VMware仮想基盤
              │
              ├─ VM①
              ├─ VM②
              ├─ VM③
              └─ VM④
```

そのため、本案件は物理サーバーを新しく設置する一般的なオンプレ更改とは異なる。

現時点では、移行先としてオンプレミス基盤を新設するというよりも、

* 別のクラウド型仮想基盤
* VMware以外の仮想化サービス
* コンテナ基盤
* クラウドネイティブな構成

などを検討する可能性が高い。

---

| 現行基盤    | TEPcube上のVMware環境 |

| オンプレ新設  | 現時点では可能性が低い       |

## 4. 今回の案件で重要な考え方

VMwareは、単なる1つのアプリケーションではなく、複数のシステムを稼働させるための**基盤**である。

そのため、

> 「VMwareより安い製品へ変更する」

という費用だけの判断ではなく、システム全体への影響を踏まえて移行先を選定する必要がある。

```text
費用
  │
  ├─ 可用性
  ├─ 性能
  ├─ セキュリティ
  ├─ 運用性
  ├─ サポート
  ├─ 移行難易度
  └─ 将来性
```

これらを総合的に比較し、次期基盤を決定する。

# 5. 比較・検討すべき主な観点

## 5.1 コスト

まず、現行VMware環境と次期基盤の費用を比較する。

確認する費用は、単純なライセンス料金だけではない。

* 仮想基盤の利用料金
* CPU・メモリ・ストレージ料金
* ネットワーク利用料金
* バックアップ料金
* 監視サービス料金
* サポート契約費用
* データ転送料
* OpenShift利用費用
* 移行作業費用
* 移行後の運用費用
* エンジニアの教育・習熟コスト

例えば、ライセンス費用が安くなっても、運用が複雑になり人件費が増加すると、全体コストは削減できない可能性がある。

そのため、比較では**TCO（総保有コスト）**を考えることが重要。

```text
TCO
＝
基盤利用料
＋ ライセンス料
＋ 構築・移行費用
＋ 運用費用
＋ 保守・サポート費用
＋ 教育費用
```

---

## 5.2 システム規模

次期基盤を選定するためには、現在のシステム規模を把握する必要がある。

主な確認項目は以下。

* VM台数
* 顧客数
* 顧客ごとのVM台数
* vCPU数
* メモリ容量
* ストレージ容量
* 月間・年間のデータ増加量
* 通信量
* 同時接続数
* バックアップ容量
* 開発・検証・本番環境の数

現時点ではVM台数や顧客数が不明のため、まずは現行環境の棚卸しが重要となる。

```text
現行環境調査
    ↓
VM・リソース情報を一覧化
    ↓
システムを分類
    ↓
必要な基盤規模を算出
    ↓
移行先候補を比較
```

---

## 5.3 稼働時間

システムごとに、必要な稼働時間が異なる可能性がある。

例えば、

| システム        | 稼働要件の例       |
| ----------- | ------------ |
| 社内業務システム    | 平日9:00～18:00 |
| 顧客向けWebシステム | 24時間365日     |
| バッチ処理基盤     | 夜間中心         |
| 開発環境        | 業務時間のみ       |
| 基幹システム      | 原則24時間365日   |

すべてのシステムに最高レベルの可用性を持たせると、費用が高くなる。

そのため、

> **システムの重要度に応じて必要な可用性を設定する**

ことが重要。

---

## 5.4 SLA

**SLA（Service Level Agreement）**は、サービス提供者と利用者の間で定めるサービス品質の合意である。

主な確認項目として、

* 月間稼働率
* 障害時の受付時間
* 障害対応開始までの時間
* 復旧目標
* サポート時間
* 計画停止の扱い
* SLA未達時の補償

などがある。

例として、月間稼働率が以下の場合、許容される停止時間は異なる。

| 稼働率    | 1か月あたりの停止時間の目安 |
| ------ | -------------: |
| 99%    |        約7時間18分 |
| 99.9%  |           約43分 |
| 99.95% |           約22分 |
| 99.99% |            約4分 |

稼働率を高くするほど、一般的には基盤コストや設計・運用の複雑性も高くなる。

そのため、各システムについて、

```text
本当に99.99%必要か
        ↓
99.9%で業務上問題ないか
        ↓
障害時にどこまで停止を許容できるか
```

を整理する必要がある。

---

## 5.5 RTO・RPO

SLAと合わせて、障害復旧要件も確認する。

### RTO

**RTO（Recovery Time Objective）**は、障害発生後、どの程度の時間でサービスを復旧させる必要があるかを示す。

```text
障害発生
   ↓
1時間以内に復旧

RTO：1時間
```

### RPO

**RPO（Recovery Point Objective）**は、障害時にどの時点までのデータを復旧できればよいかを示す。

```text
障害発生：15:00
最終バックアップ：14:00

最大1時間分のデータ損失を許容
RPO：1時間
```

システムごとに、

* RTO
* RPO
* バックアップ頻度
* データ複製方式
* 災害対策

を定義する必要がある。

---

## 5.6 セキュリティ

クラウド上の基盤を選定する場合、セキュリティも重要な比較項目となる。

主な確認ポイントは以下。

### ネットワーク

* インターネット公開範囲
* プライベートネットワークの構成
* VLAN・セグメント分離
* ファイアウォール
* WAF
* VPN・専用線
* 外部システムとの接続

### 認証・権限

* 管理者認証
* 多要素認証
* ロール・権限管理
* 特権ID管理
* 操作ログ
* 顧客ごとの環境分離

### データ保護

* 通信の暗号化
* 保存データの暗号化
* 暗号鍵の管理
* バックアップデータの保護
* 個人情報・機密情報の保管場所

### 脆弱性・運用

* OSパッチ管理
* 仮想基盤の脆弱性対応
* コンテナイメージの脆弱性管理
* ログ監視
* セキュリティ監視
* インシデント対応
* 監査証跡の保存

移行先が安価であっても、必要なセキュリティ機能が不足している場合は採用できない。

---

## 5.7 可用性・障害対策

VMwareでは、従来以下のような機能を利用している可能性がある。

* vSphere HA
* vMotion
* クラスタ
* 仮想マシンの自動再起動
* ホスト障害時の退避
* 共有ストレージ
* バックアップ製品との連携

次期基盤でも、同等の機能が必要かを確認する。

```text
現行VMwareの機能
        ↓
本当に必要な機能を整理
        ↓
次期基盤で代替可能か確認
```

例えば、現行環境でvMotionを使用していても、次期基盤で同じ機能を必ず採用しなければならないとは限らない。

サービス停止が許容できるシステムなら、より単純で安価な方式を選択できる可能性もある。

---

## 5.8 運用性

移行後に誰が、どのように運用するかも重要。

確認する項目として、

* VM作成・削除方法
* コンテナのデプロイ方法
* パッチ適用
* 監視
* バックアップ
* 障害対応
* ログ確認
* キャパシティ管理
* アカウント管理
* 構成管理
* 変更管理
* 問い合わせ対応

などがある。

新しい基盤の機能が優れていても、運用担当者が扱えなければ安定運用は難しい。

---

## 5.9 サポート体制

基盤障害が発生した場合に、誰が対応するのかを明確にする。

* 24時間365日サポートか
* 日本語対応か
* 問い合わせ窓口はどこか
* 基盤事業者の対応範囲
* 自社の対応範囲
* OpenShiftのサポート範囲
* 障害解析の支援があるか
* ハードウェア障害を誰が担当するか

クラウドサービスであっても、OSやアプリケーションまですべて事業者が対応するわけではない。

責任分界点を明確にする必要がある。

# 6. OpenShift導入との関係

次期環境では、コンテナ基盤として**OpenShift**を導入する想定となっている。

ただし、既存のVMをすべてそのままコンテナへ移行できるとは限らない。

```text
現行VMware上のシステム
          │
          ├─ VMとして継続するシステム
          │
          ├─ OpenShiftへ移行するシステム
          │
          ├─ クラウドサービスへ置き換えるシステム
          │
          └─ 廃止するシステム
```

そのため、システムごとに移行方式を分類する必要がある。

### VMとして移行しやすいもの

* Windows Server
* 市販パッケージ製品
* 古い業務システム
* OS依存が強いアプリケーション
* コンテナ化が難しいシステム

### OpenShiftへの移行を検討しやすいもの

* Webアプリケーション
* API
* Java・Node.js・Pythonなどのアプリケーション
* ステートレスなサービス
* マイクロサービス化を予定しているシステム

### 注意点

コンテナ化には、

* アプリケーション改修
* コンテナイメージ作成
* 永続データの扱い
* ネットワーク設計
* CI/CD
* 監視
* ログ管理
* セキュリティ対策

が必要となる。

そのため、

> **VMware脱却とコンテナ化は、同じものではない**

ことに注意する。

VMwareを別の仮想基盤へ移行するだけなら、主にインフラ移行となる。

OpenShiftへ移行する場合は、アプリケーション改修も含む可能性がある。

# 7. 想定される次期構成

現時点では移行先の仮想基盤は選定中である。

そのため、次期構成は以下のようなハイブリッド構成になる可能性がある。

```text
              次期クラウド基盤
                     │
          ┌──────────┴──────────┐
          │                     │
     新仮想基盤              OpenShift
          │                     │
     VMとして稼働          コンテナとして稼働
          │                     │
 ┌────────┼────────┐       ┌────┼────┐
 Windows  Linux  製品系     Web  API  Batch
```

つまり、

* VMで残すシステム
* コンテナへ移行するシステム
* サービスとして置き換えるシステム

を分けて考える必要がある。

# 10. 本案件のポイント

本案件では、単にVMwareの代替製品を探すのではなく、

> **システムごとの重要度や要件を整理し、必要なサービス品質を維持しながら、全体コストを最適化する**

ことが重要。

```text
VMwareのコスト増加
        ↓
安い基盤へ単純移行
        ×
        ↓
システム要件を整理
        ↓
費用・可用性・性能・セキュリティを比較
        ↓
システムごとに最適な移行先を決定
        ↓
安全に段階移行
```

# 11. 一言でまとめると

> **本案件は、TEPcube上で稼働しているVMware環境について、ライセンス・利用コストの増加を背景に、次期仮想基盤を選定し、VMおよび一部システムをOpenShiftなどの新基盤へ移行するプロジェクトである。**

ただし、VMwareは企業システムを支える基盤であるため、価格だけで移行先を決定することはできない。

以下を総合的に評価する必要がある。

* 現行および将来のコスト
* VM・顧客・システムの規模
* 稼働時間
* SLA
* RTO・RPO
* 可用性
* 性能
* セキュリティ
* 運用性
* サポート体制
* 移行期間
* 移行リスク
* OpenShiftへの移行可否

最終的には、

> **VMとして残すもの、OpenShiftへ移行するもの、別サービスへ置き換えるものを分類し、コストと品質のバランスが取れた次期基盤を設計する**

ことが本案件の中心となる。
