# OSI参照モデル ― 画像をAからBへ送るとき通信はどうなる？

## 1. 今回の例

たとえば、AさんがWebサービスで**1MBのプロフィール画像**をアップロードし、B側のサーバーへ送信するとします。

```text
A：PC・スマホ
   ↓
「test.jpg」という1MBの画像を送信
   ↓
ネットワーク
   ↓
B：Webサーバー
```

ここで重要なのは、

> **1MBの画像が、そのままネットワークを流れているわけではない**

ということです。

実際には、画像データに通信に必要な情報を付けたり、適切なサイズに分割したりしながら送信します。

---

# 2. まず全体像

AからBへ送るときは、OSI参照モデルを**上から下**へ進みます。

```text
A（送信側）

第7層 アプリケーション層
        ↓
第6層 プレゼンテーション層
        ↓
第5層 セッション層
        ↓
第4層 トランスポート層
        ↓
第3層 ネットワーク層
        ↓
第2層 データリンク層
        ↓
第1層 物理層
        ↓
========================
       ネットワーク
========================
        ↓
第1層 物理層
        ↓
第2層 データリンク層
        ↓
第3層 ネットワーク層
        ↓
第4層 トランスポート層
        ↓
第5層 セッション層
        ↓
第6層 プレゼンテーション層
        ↓
第7層 アプリケーション層

B（受信側）
```

つまり、

* **送信側A：上 → 下**
* **受信側B：下 → 上**

となります。

---

# 3. A側：画像を送信する

## 第7層：アプリケーション層

まずAさんがブラウザからプロフィール画像を選択します。

```text
プロフィール画像を変更
        ↓
test.jpg
        ↓
「アップロード」を押す
```

Webアプリケーションは、

```text
この画像をWebサーバーに送ってください
```

という通信を行います。

例えばHTTPSを使って、

```text
POST /profile/image
```

のようなHTTPリクエストを作ります。

この時点では、

```text
HTTPの情報
+
test.jpg のデータ
```

というイメージです。

### 第7層の役割

**「このデータを何のために使うのか」**

を扱う層です。

今回なら、

```text
この画像はプロフィール画像としてアップロードされた
```

という意味をWebアプリケーションが理解しています。

---

# 4. 第6層：プレゼンテーション層

次に、データを通信できる形式にします。

ここでは、

* データ形式
* 文字コード
* 暗号化
* 復号

などを考えます。

例えばHTTPS通信なら、TLSによって通信内容が暗号化されます。

元データを単純化して、

```text
test image
```

だったとします。

暗号化すると、イメージとしては、

```text
test image

↓ 暗号化

afenidegefeagdjiaeg...
```

のように、人間がそのまま読めないデータになります。

※実際の暗号化データはこのような文字列になるとは限りません。あくまでイメージです。

### 「暗号化」と「エンコード」は別物

ここは混同しやすいので注意します。

```text
暗号化
→ 内容を第三者に読めなくする

エンコード
→ データを別の表現形式に変換する
```

例えばBase64はエンコードですが、暗号化ではありません。

HTTPSの場合に重要なのは**TLSによる暗号化**です。

---

# 5. 第5層：セッション層

第5層では、

> **AとBの通信をどのように開始・維持・終了するか**

という通信のセッションを考えます。

イメージとしては、

```text
A ←────────→ B
   通信中
```

という状態を管理する役割です。

ただし、現在のTCP/IP通信では、第5〜7層の役割がアプリケーション側にまとめて実装されることも多いため、

```text
「必ず第5層だけで独立して何かのデータが付く」
```

と考える必要はありません。

---

# 6. 第4層：トランスポート層

ここからネットワーク通信らしくなってきます。

代表的なのが**TCP**です。

1MBの画像をネットワークで送る場合、

```text
1MBの画像を丸ごと1回で送る
```

わけではありません。

ネットワークで扱いやすいサイズに分けて送ります。

イメージとしては、

```text
1MBのデータ

↓

データ①
データ②
データ③
データ④
データ⑤
...
```

となります。

TCPの場合、それぞれにTCPヘッダーが付きます。

```text
┌────────────┬─────────────┐
│ TCPヘッダー │ データ①      │
└────────────┴─────────────┘

┌────────────┬─────────────┐
│ TCPヘッダー │ データ②      │
└────────────┴─────────────┘

┌────────────┬─────────────┐
│ TCPヘッダー │ データ③      │
└────────────┴─────────────┘
```

TCPヘッダーには、

* 送信元ポート番号
* 宛先ポート番号
* シーケンス番号
* ACK番号

などが入ります。

例えばHTTPSなら、

```text
宛先ポート：443
```

です。

### シーケンス番号

TCPでは、

```text
どのデータがどの順番なのか
```

を管理できます。

例えば、

```text
① ABCD
② EFGH
③ IJKL
```

というデータを送ったとします。

ネットワーク上で、

```text
③
↓
①
↓
②
```

の順番で届いたとしても、TCPの情報を使って正しいデータとして処理できます。

```text
① → ② → ③

ABCDEFGHIJKL
```

また、途中のデータが届かなければ**再送**することもできます。

---

# 7. 第3層：ネットワーク層

次に、

> **どのコンピュータから、どのコンピュータへ送るのか**

という情報を付けます。

ここで登場するのが**IPアドレス**です。

例えば、

```text
A
192.168.0.2

↓

B
203.0.113.5
```

なら、IPヘッダーにはイメージとして、

```text
送信元IP：192.168.0.2
宛先IP：203.0.113.5
```

などの情報が入ります。

データは、

```text
IPヘッダー
+
TCPヘッダー
+
データ
```

という形になっていきます。

```text
┌──────────┬──────────┬──────────────┐
│ IP Header│TCP Header│     Data     │
└──────────┴──────────┴──────────────┘
```

ルーターは主にこの**宛先IPアドレス**を見ながら、

```text
次はこっちへ送ろう
```

と判断して、Bまでデータを運びます。

---

# 8. 第2層：データリンク層

さらに、

> **今いるネットワーク内で、次にどの機器へ渡すのか**

という情報が必要になります。

ここで使われる代表的なものが**MACアドレス**です。

Ethernetの場合、

```text
Ethernetヘッダー
+
IPヘッダー
+
TCPヘッダー
+
データ
+
FCS
```

のような形になります。

```text
┌────────────┬─────────┬─────────┬─────────┬─────┐
│Ethernet Hdr│ IP Hdr  │ TCP Hdr │  Data   │ FCS │
└────────────┴─────────┴─────────┴─────────┴─────┘
```

この単位を**フレーム**と呼びます。

---

# 9. 第1層：物理層

最後は、このフレームを実際に物理的な信号として送ります。

例えばLANケーブルなら電気信号、光ファイバーなら光信号、Wi-Fiなら電波です。

```text
データ

↓

010101101010101010...

↓

電気信号・光信号・電波

↓

ネットワークへ送信
```

ここまで来ると、A側から実際にデータが出ていきます。

---

# 10. インターネットを通ってBへ

大量のデータがネットワークを流れます。

```text
A
↓
ルーター
↓
インターネット
↓
ルーター
↓
B
```

1MBの画像であれば、実際には多数のパケット等として通信されます。

重要なのは、

```text
1MB
+
64bitのヘッダー
```

という単純な構造ではないことです。

実際には各階層で、

```text
Ethernetヘッダー
IPヘッダー
TCPヘッダー
TLS関係の情報
HTTPの情報
...
```

などが関係します。

また、データは複数に分かれて送られるため、**それぞれの通信単位に必要なヘッダー等が付加されます。**

---

# 11. B側に到着

ここからは逆です。

A側では、

```text
第7層
↓
第6層
↓
第5層
↓
第4層
↓
第3層
↓
第2層
↓
第1層
```

でした。

B側では、

```text
第1層
↓
第2層
↓
第3層
↓
第4層
↓
第5層
↓
第6層
↓
第7層
```

と、**下から上へ戻していきます。**

---

# 12. B側：第1層

まず電気信号・光信号などを受け取ります。

```text
電気信号

↓

010101010101...
```

データとして扱える状態にします。

---

# 13. B側：第2層

Ethernetフレームを確認します。

```text
Ethernet Header
+
IP Header
+
TCP Header
+
Data
+
FCS
```

必要な処理を行い、上位のIPへ渡します。

イメージとしては、

```text
Ethernet関係の情報を処理

↓

IP Header
+
TCP Header
+
Data
```

となります。

---

# 14. B側：第3層

IPヘッダーを確認します。

```text
宛先IP
203.0.113.5
```

を見て、

```text
これは自分宛ての通信だ
```

と判断します。

そして上位のTCPへ渡します。

```text
TCP Header
+
Data
```

---

# 15. B側：第4層

TCPの情報を確認します。

ここで重要なのが、

* 順番
* 欠損
* 再送
* ポート番号

などです。

例えば分割されて届いたデータを、

```text
データ③
データ①
データ②
データ④
```

から、

```text
データ①
データ②
データ③
データ④
```

として正しく扱えるようにします。

さらに、

```text
宛先ポート：443
```

なら、

```text
HTTPSとして待ち受けているサービスへ渡す
```

という処理につながります。

---

# 16. B側：第5〜6層

通信状態を管理しながら、TLSを使用している場合は暗号化されたデータを復号します。

例えばイメージとして、

```text
afenidegefeagdjiaeg...

↓ 復号

test image
```

となります。

これでB側が元の内容を扱える状態になります。

---

# 17. B側：第7層

最終的にWebサーバー・Webアプリケーションまでデータが届きます。

```text
HTTPリクエスト
        ↓
プロフィール画像を変更したい
        ↓
test.jpg
```

Webアプリケーションは、

```text
これはプロフィール画像のアップロードだ
```

と判断します。

ここから先は**ネットワーク通信というより、アプリケーション側の処理**です。

例えば、

```text
受信した画像
   ↓
画像として問題ないか確認
   ↓
ファイル名などを決める
   ↓
S3などのストレージへ保存
   ↓
DBに画像のURLなどを登録
```

といった処理を行います。

---

# 18. 「画像を表示する」のはさらに次の通信

画像をアップロードした後、Bさんがプロフィール画面を開いたとします。

すると今度は、

```text
Bさんのブラウザ

「プロフィール画像をください」
        ↓
Webサーバー
        ↓
画像データを返す
        ↓
Bさんのブラウザ
        ↓
画像を画面に表示
```

という**別の通信**が発生します。

例えばHTMLに、

```html
<img src="/images/profile/test.jpg">
```

があれば、ブラウザは画像を取得するためにHTTP/HTTPSリクエストを送ります。

そして画像データを受け取り、

```text
JPEGデータ
   ↓
ブラウザが解釈
   ↓
画面にプロフィール画像として表示
```

となります。

---

# 19. 全体を一本につなげる

最終的なイメージはこれです。

```text
【A：送信側】

プロフィール画像
test.jpg（1MB）
        ↓
第7層
HTTPとして「画像をアップロード」
        ↓
第6層
TLSなどによって暗号化
        ↓
第5層
通信状態を管理
        ↓
第4層
TCP
ポート番号・順序・再送などを管理
        ↓
第3層
IP
送信元IP・宛先IPを付ける
        ↓
第2層
Ethernet
MACアドレスなどを使ってフレーム化
        ↓
第1層
電気・光・電波として送信


========================
       ネットワーク
========================


【B：受信側】

第1層
信号を受信
        ↓
第2層
Ethernetフレームを処理
        ↓
第3層
宛先IPなどを確認
        ↓
第4層
TCPで順序・欠損・ポートなどを処理
        ↓
第5層
通信状態を管理
        ↓
第6層
TLSなどを復号
        ↓
第7層
HTTPとしてWebアプリが受信
        ↓
「プロフィール画像だ」
        ↓
画像を保存
```

# 20. 一番大事な考え方

OSI参照モデルを覚えるときは、

**送信側では「情報を付けながら下へ行く」**

**受信側では「情報を確認・処理しながら上へ行く」**

と考えると分かりやすいです。

```text
送信側

アプリのデータ
     ↓
┌─────────────────────┐
│      Data           │
└─────────────────────┘

     ↓ TCP

┌────────┬────────────┐
│TCP情報 │    Data    │
└────────┴────────────┘

     ↓ IP

┌──────┬────────┬────────────┐
│IP情報│TCP情報 │    Data    │
└──────┴────────┴────────────┘

     ↓ Ethernet

┌──────────┬──────┬────────┬────────────┐
│Ethernet情報│IP情報│TCP情報 │    Data    │
└──────────┴──────┴────────┴────────────┘

     ↓
   物理信号
```

B側ではこれを逆方向に処理していきます。

```text
受信
 ↓
Ethernetを処理
 ↓
IPを処理
 ↓
TCPを処理
 ↓
TLSを復号
 ↓
HTTPとして解釈
 ↓
元の画像データをアプリが利用
```

この**「送るときに包んで、受け取るときに開ける」**という考え方を、**カプセル化／非カプセル化**と呼びます。

OSI参照モデルでは、この流れを理解しておくと、後から「IPアドレス」「MACアドレス」「ポート番号」「HTTP」「HTTPS」などがどの位置にあるのか整理しやすくなります。
