Codexで考えると、**1つの開発タスクを任せたCodexの作業単位が「エージェント」**です。

たとえば、Next.js＋AWS EC2で予約システムを作る場合、

> 「予約登録APIを実装して、重複予約を防止し、テストまで追加してください」

とCodexに依頼すると、そのタスクを担当するCodexが1つのエージェントとして動きます。

Codexはリポジトリを読み、コードを変更し、テストや静的解析を実行し、結果を確認しながら修正できます。Codexでは複数のエージェントを別々のスレッドや作業環境で並行して動かす構成も想定されています。

# 予約システムを作る場合

想定する技術構成を、次のようにします。

```
フロントエンド
├─ Next.js
├─ TypeScript
└─ Tailwind CSS

バックエンド
├─ Next.js Route Handler
└─ Node.js

認証
└─ Amazon Cognito

データベース
└─ DynamoDB または RDS

インフラ
├─ AWS EC2
├─ nginx
├─ PM2
├─ ALB
└─ Route 53

決済
└─ PAY.JP

テスト
├─ Vitest
└─ Playwright
```

このシステム全体を一度にCodexへ依頼するのではなく、**独立して確認できる作業単位に分けます**。

# メインエージェントのイメージ

メインエージェントは、プロジェクト全体を整理する担当です。

```
人間
  │
  │「予約システムを構築する」
  ▼
メインエージェント
  │
  ├─ 要件を整理
  ├─既存コードを調査
  ├─作業を分割
  ├─各エージェントへ依頼
  └─最終的に統合・確認
```

メインエージェントへの依頼例です。

```
このリポジトリに、バイクレンタルの予約システムを実装してください。

技術構成：
- Next.js
- TypeScript
- AWS EC2
- DynamoDB
- Amazon Cognito
- PAY.JP
- nginx
- PM2

必要な機能：
- 車両一覧
- 空き状況確認
- 予約登録
- 重複予約防止
- オンライン決済
- 予約確認
- 予約キャンセル
- 管理画面

まず既存コードを調査し、必要な作業を機能単位に分解してください。
この段階では実装せず、設計案と作業順序を提示してください。
```

最初から「全部実装して」と頼むより、まず調査と設計をさせる方が安全です。

# サブエージェントの分け方

予約システムなら、次のように分けられます。

```
メインエージェント
│
├─ ① 調査・設計エージェント
├─ ② データベースエージェント
├─ ③ 予約APIエージェント
├─ ④ フロントエンドエージェント
├─ ⑤ 認証エージェント
├─ ⑥ 決済エージェント
├─ ⑦ AWS・インフラエージェント
├─ ⑧ テストエージェント
└─ ⑨ レビューエージェント
```

ここでいうサブエージェントは、必ずしも「1つのAIの内部から別AIが自動で出てくる」という意味だけではありません。

Codexでは実務上、

- 別スレッドで別タスクを実行する
- 別ブランチやworktreeで作業する
- それぞれ独立した変更を作る
- 最後に人間または統合担当がまとめる

という形が、サブエージェント的な使い方になります。Codexアプリは、複数エージェントを別スレッドで並行管理し、変更差分を確認するワークフローを提供しています。

---

# ① 調査・設計エージェント

役割は、既存コードを読んで構成を把握することです。

```
このリポジトリを調査してください。

以下を確認してください。
- Next.jsのバージョン
- App RouterかPages Routerか
- データベース接続方法
- 認証方法
- 予約関連の既存機能
- AWS関連の設定
- 環境変数
- テスト構成
- デプロイ方法

コードは変更しないでください。
調査結果、問題点、予約機能を追加する場合の実装案をまとめてください。
```

このエージェントは、基本的にコードを変更させません。

最初にこれを行うことで、

- 既存機能を壊す
- 同じ処理を二重に作る
- App RouterなのにPages Routerで実装する
- 既存DB設計と合わない

といった問題を減らせます。

# ② データベースエージェント

予約データの設計を担当します。

DynamoDBなら、たとえば次のデータを設計します。

```
Reservation
├─ reservationId
├─ userId
├─ vehicleId
├─ shopId
├─ startAt
├─ endAt
├─ status
├─ paymentStatus
├─ amount
├─ createdAt
└─ updatedAt
```

依頼例です。

```
DynamoDBを使用した予約データモデルを設計してください。

要件：
- 利用者は車両を日時指定で予約する
- 同じ車両の予約時間が重複してはいけない
- 店舗ごとに車両を管理する
- 予約状態は pending、confirmed、cancelled、completed
- PAY.JPの決済IDを保存する
- 利用者別、車両別、日付別に予約を検索する

まず設計案を提示してください。
承認されるまで実装しないでください。
```

重要なのは、単にテーブルを作るだけでなく、**どの条件で検索するか**まで渡すことです。

# ③ 予約APIエージェント

予約作成、取得、キャンセルを担当します。

```
予約作成APIを実装してください。

対象：
- POST /api/reservations

要件：
- Cognito認証済みユーザーのみ利用可能
- vehicleId、startAt、endAtを受け取る
- 開始日時は終了日時より前であること
- 過去日時は予約できない
- 同一車両の予約時間が重複しないこと
- 登録成功時は予約情報を返す
- エラー形式を統一する
- TypeScriptの型を定義する
- 単体テストを追加する

既存のディレクトリ構成とコーディング規約に従ってください。
変更後にlint、型チェック、テストを実行してください。
```

この依頼では、Codexに「APIを作って」だけでなく、

- 入力値
- バリデーション
- 認証
- 重複判定
- テスト
- 完了条件

まで渡しています。

# ④ フロントエンドエージェント

予約画面を担当します。

```
予約入力画面を実装してください。

必要なUI：
- 店舗選択
- 車両選択
- 利用開始日時
- 利用終了日時
- 料金表示
- 予約内容確認
- 予約ボタン
- エラー表示
- 送信中表示

要件：
- Next.js App Routerを使用する
- TypeScriptを使用する
- 既存のTailwind CSSデザインに合わせる
- スマートフォン表示を優先する
- 予約APIと接続する
- 二重送信を防止する
- APIエラーを利用者向けの日本語で表示する
```

画面側のエージェントには、AWSやDBを触らせず、担当範囲を限定します。

# ⑤ 認証エージェント

Amazon Cognitoとの連携を担当します。

```
Amazon Cognitoを使用した予約APIの認証処理を実装してください。

要件：
- 未ログイン利用者は予約APIを利用できない
- JWTを検証する
- 検証済みユーザーのsubをuserIdとして使用する
- トークンが期限切れの場合は401を返す
- 権限不足の場合は403を返す
- 秘密情報をクライアント側へ公開しない
- 既存の認証処理がある場合は再利用する

認証部分以外は変更しないでください。
```

「認証部分以外は変更しない」と明示することで、変更範囲を抑えます。

# ⑥ 決済エージェント

PAY.JPとの接続を担当します。

```
PAY.JPを使用した予約決済処理を実装してください。

処理順：
1. 仮予約を作成する
2. PAY.JPで決済する
3. 決済成功後に予約をconfirmedへ変更する
4. 決済失敗時は仮予約を解放する
5. 決済成功後に予約確定処理が失敗した場合は返金する

要件：
- 二重決済を防止する
- Idempotencyを考慮する
- 秘密鍵はサーバー側のみで使用する
- 決済IDと返金状態を保存する
- ログにカード情報を出さない
- エラー発生時の復旧方法を実装する
- テストを追加する
```

決済処理では、単純な成功パターンよりも、

> 決済は成功したが、予約保存に失敗した

という途中失敗の設計が重要です。

# ⑦ AWS・インフラエージェント

EC2、nginx、PM2、ALBなどを担当します。

```
Next.js予約システムをAWS EC2で安全に運用するため、
現在のインフラ設定を確認してください。

確認対象：
- EC2
- nginx
- PM2
- ALB
- Route 53
- HTTPS証明書
- セキュリティグループ
- 環境変数
- CloudWatchログ
- ヘルスチェック
- デプロイ手順

まず問題点と改善案を提示してください。
本番環境への変更やデプロイは行わないでください。
```

インフラについては、いきなり変更させるより、

1. 調査
2. 設定ファイルの修正
3. 差分確認
4. ステージング確認
5. 本番反映

に分ける方が安全です。

# ⑧ テストエージェント

実装担当とは別に、テスト専門のCodexを使います。

```
今回追加された予約機能をレビューし、テストを追加してください。

重点項目：
- 終了日時が開始日時より前
- 過去日時で予約
- 同一時間の重複予約
- 一部だけ重なる予約
- 境界時刻が同一の予約
- 未ログイン利用者
- 二重クリック
- 決済失敗
- 予約保存失敗
- 返金失敗

実装コードは、テストに必要な最小限以外は変更しないでください。
```

実装したエージェントとテスト担当を分けると、実装者が見落としたケースを発見しやすくなります。

# ⑨ レビューエージェント

最後に、コードを書いていない別のCodexにレビューさせます。

```
予約機能の変更差分をレビューしてください。

次の観点で確認してください。
- 重大なバグ
- 重複予約の可能性
- 二重決済の可能性
- 認証・認可の不足
- 個人情報の漏えい
- 環境変数の扱い
- エラー処理
- パフォーマンス
- TypeScriptの型安全性
- テスト不足

コードは変更せず、重要度を
Critical、High、Medium、Low
に分けて指摘してください。
```

# 実際の並列作業

すべてを同時に進めてよいわけではありません。

依存関係を考えると、次の順序が現実的です。

```
第1段階
├─ 調査エージェント
└─ 要件整理エージェント

        ↓

第2段階
├─ DB設計エージェント
├─ API設計エージェント
└─ 画面設計エージェント

        ↓

第3段階
├─ 予約APIエージェント
├─ フロントエンドエージェント
├─ 認証エージェント
└─ 決済エージェント

        ↓

第4段階
├─ テストエージェント
├─ セキュリティレビュー
└─ コードレビュー

        ↓

第5段階
├─ AWS設定
├─ ステージング反映
└─ 動作確認

        ↓

本番リリース
```

たとえば、DB設計が決まっていないのに予約APIと画面を同時に作らせると、それぞれが異なるデータ形式を想定する危険があります。

# Codexを複数使うイメージ

```
Codex 1：既存コード調査
  branch: investigation

Codex 2：DB・予約モデル
  branch: feature/reservation-model

Codex 3：予約API
  branch: feature/reservation-api

Codex 4：予約画面
  branch: feature/reservation-ui

Codex 5：PAY.JP決済
  branch: feature/payment

Codex 6：テスト
  branch: test/reservation

Codex 7：レビュー
  変更せず指摘のみ
```

Codexの各エージェントは、同じリポジトリを対象にしながらも、別のタスク・スレッド・作業環境で進められます。変更後は差分を確認して、人間が承認してから統合します。

# 人間の役割

エージェントを使っても、人間が不要になるわけではありません。

人間は主に次を担当します。

```
人間
├─要件を決める
├─優先順位を決める
├─設計を承認する
├─エージェントの担当範囲を決める
├─変更差分を確認する
├─本番反映を承認する
└─最終的な責任を持つ
```

Codexは「優秀な開発担当者」に近いですが、プロジェクト固有の事情をすべて自動で判断できるわけではありません。

特に以下は、人間が明示する必要があります。

- 予約の重複条件
- キャンセル規定
- 料金計算方法
- 返金条件
- 店舗の営業時間
- 車両を確保するタイミング
- 決済と予約の処理順
- 本番環境へ反映してよいか

# 一番現実的な捉え方

あなたがCodexを使って予約システムを作るなら、次のように考えると分かりやすいです。

```
あなた
＝プロダクト責任者・最終承認者

Codexのメインスレッド
＝リードエンジニア・作業整理担当

個別のCodexスレッド
＝フロント、API、AWS、決済、テストなどの担当者

AGENTS.md
＝プロジェクトの開発ルール・引き継ぎ資料

GitHubのIssue
＝各担当者への作業指示書

Pull Request
＝各エージェントが提出する成果物
```

つまりCodexにおけるエージェント開発は、

> **1つの巨大な依頼をAIへ丸投げすることではなく、作業を適切な単位に分解し、それぞれのCodexに担当させ、差分をレビューして統合する開発方法**

と考えるとよいです。
