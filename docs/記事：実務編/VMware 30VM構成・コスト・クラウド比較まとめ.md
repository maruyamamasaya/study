## 1. VMwareの基本的な考え方

VMwareでは、1台の物理サーバー上に複数のVMを稼働させる。

```text
物理サーバー
├─ CPU
├─ メモリ
├─ ストレージ
│
└─ ESXi
    ├─ VM01
    ├─ VM02
    ├─ VM03
    └─ ...
```

物理サーバーのスペックは、

> 「VMが30台だから○コア」

ではなく、

> **各VMのCPU・メモリ・ディスク容量を合計して決める**

のが基本。

---

# 2. 30VMの必要リソース例

1VMを以下と仮定する。

```text
CPU：2 vCPU
RAM：8GB
Disk：100GB
```

30VMでは、

| リソース |      合計 |
| ---- | ------: |
| vCPU | 60 vCPU |
| RAM  |   240GB |
| Disk |     3TB |

となる。

---

# 3. vCPUと物理CPUは1:1ではない

VMwareでは、複数VMで物理CPUを共有できる。

例えば、

```text
VM合計
60 vCPU

↓

物理CPU
32コア
```

のような構成も可能。

```text
60 vCPU ÷ 32物理コア
≒ 1.9 : 1
```

これを**CPUオーバーコミット**という。

そのため、

> 60 vCPUだから60物理コア必要

というわけではない。

ただし、オーバーコミットしすぎるとCPU Readyなどが増加し、性能低下につながる。

---

# 4. CPUよりメモリに注意

30VM × 8GBの場合、

```text
240GB
```

のメモリが必要。

さらに、

* ESXi自身
* VMのオーバーヘッド
* 将来のVM追加
* 障害時の余力

なども必要になる。

目安として、

```text
256GB → かなりギリギリ

384GB → 現実的

512GB → 余裕あり
```

となる。

VMware環境では**CPUだけでなくメモリ容量が重要**。

---

# 5. 物理サーバー1台に30VMは危険

例えば、

```text
物理サーバー
└─ ESXi
    └─ 30VM
```

とすると、

```text
物理サーバー故障
        ↓
30VMすべて停止
```

となる。

そのため、本番環境では複数ESXiホストによるクラスタ構成を取ることが多い。

---

# 6. 30VMなら3台構成が候補

コストと可用性のバランスを考えると、

```text
ESXiホスト × 3台
```

が候補。

### 1台あたり

```text
CPU：1CPU × 16物理コア
RAM：256GB
NIC：10GbE × 2以上
電源：冗長化
```

### クラスタ全体

```text
CPU：48物理コア
RAM：768GB
VM：30台
```

通常時：

```text
ESXi01 → 10VM

ESXi02 → 10VM

ESXi03 → 10VM
```

1台故障時：

```text
ESXi01 → 15VM

ESXi02 → 15VM

ESXi03 → 故障
```

残り2台で30VMを動かす。

このような、

> **1台故障しても残りで処理できる設計**

をN+1構成として考える。

---

# 7. VMwareライセンスとCPU構成

現在のVMwareは物理CPUの**コア数ベース**でライセンス費用が大きく変わる。

そのため、

```text
2CPU × 少ないコア
```

より、

```text
1CPU × 16コア
```

のような構成を検討する価値がある。

特に最低ライセンスコア数の条件があるため、

```text
1CPU × 16core
```

はコストを考える際の一つの基準になる。

---

# 8. 2台構成と3台構成

## 2台

```text
ESXi01 → 15VM
ESXi02 → 15VM
```

障害発生：

```text
ESXi01 → 30VM
ESXi02 → 故障
```

### メリット

* サーバー購入台数が少ない
* ラック・電力を抑えられる

### デメリット

* 1台あたり高スペックが必要
* 障害時に1台ですべて処理
* メンテナンス時の余裕が少ない

---

## 3台

```text
10VM
 +
10VM
 +
10VM
```

障害時：

```text
15VM
 +
15VM
 +
故障
```

### メリット

* 障害に強い
* メンテナンスしやすい
* 1台あたりのスペックを抑えられる
* 負荷分散しやすい

30VM程度なら、

> **3台構成がコスト・性能・可用性のバランスを取りやすい。**

---

# 9. ストレージ

30VM × 100GBなら、

```text
最低3TB
```

必要。

ただし実際には、

* スナップショット
* バックアップ
* ログ
* 将来増加
* 空き容量

なども考える。

そのため、

```text
実効6～8TB程度
```

を一つの目安とする。

---

# 10. 共有ストレージ構成

例えば、

```text
       ESXi01
          │
       ESXi02
          │
       ESXi03
          │
        10GbE
          │
    共有ストレージ
     NFS / iSCSI
```

のようにする。

共有ストレージを利用すると、VMを別ESXiホストから起動・移動しやすくなる。

---

# 11. vSANという選択肢

別途共有ストレージを用意せず、

```text
ESXi01 SSD/NVMe
ESXi02 SSD/NVMe
ESXi03 SSD/NVMe
        ↓
       vSAN
        ↓
仮想的な共有Datastore
```

とする方法もある。

ただし、

* VMwareライセンス
* vSANライセンス条件
* SSD/NVMe
* ネットワーク

などの費用も含めて比較する必要がある。

---

# 12. オンプレ3台構成の費用感

30VM程度の環境なら、

### 初期費用イメージ

| 項目          |                概算 |
| ----------- | ----------------: |
| サーバー3台      |         250～350万円 |
| 共有ストレージ     |          80～150万円 |
| 10GbEネットワーク |           30～80万円 |
| VMware      |    100～250万円/年程度～ |
| 保守・その他      |           30～70万円 |
| **初年度**     | **約500～900万円程度～** |

※ VMwareは契約内容・エディション・最低購入コア数・販売パートナーなどによって大きく変動するため、実際には見積が必要。

---

# 13. 物理サーバー単体の維持費

16コア・RAM256GB程度のサーバーなら、

| 費用       |     年間目安 |
| -------- | -------: |
| 電気       |   5～15万円 |
| 空調・設備    |   3～10万円 |
| ハードウェア保守 |  10～30万円 |
| ラック/DC   | 0～30万円以上 |
| VMware   |       別途 |
| 運用人件費    |       別途 |

ざっくり、

```text
1台
年間20～80万円程度
```

が一つの目安。

---

# 14. 電気代の考え方

例えば平均消費電力500Wなら、

```text
0.5kW
× 24時間
× 365日

= 4,380kWh
```

30円/kWhなら、

```text
約13万円 / 年
```

となる。

実際の平均消費電力が250～350Wなら、もう少し安くなる。

つまり、

> **オンプレで本当に高いのは電気代だけではない。**

---

# 15. オンプレの主なコスト

重要なのは、

```text
サーバー購入
     +
ハードウェア保守
     +
VMwareライセンス
     +
ストレージ
     +
バックアップ
     +
ネットワーク
     +
電気・空調
     +
運用担当者
```

という全体コスト。

特に現在は、

> **VMwareライセンスの継続費用**

が大きな検討ポイントになりやすい。

---

# 16. クラウドに30VMをそのまま移行した場合

例えばAWSへ、

```text
30VM

1VM
├─ 2vCPU
├─ RAM 8GB
└─ Disk 100GB
```

をそのまま移行する。

イメージ：

```text
VM01 → EC2
VM02 → EC2
VM03 → EC2
...
VM30 → EC2
```

これは**リフト＆シフト**に近い。

---

# 17. AWSの概算

24時間365日稼働とすると、

| 項目          |            月額目安 |
| ----------- | --------------: |
| EC2 × 30    |         45～70万円 |
| EBS         |           3～5万円 |
| LB等         |           1～5万円 |
| Backup      |           2～5万円 |
| データ転送       |         3～10万円～ |
| CloudWatch等 |           1～3万円 |
| **合計**      | **約55～100万円/月** |

年間では、

```text
約660～1,200万円
```

程度が大まかなイメージ。

※ OS・通信量・インスタンスタイプ・契約方法などで大きく変動する。

---

# 18. 30VMをそのままAWSへ持っていくと高くなりやすい

オンプレでは、

```text
物理CPU
   ↓
30VMで共有
```

できる。

AWSで30EC2にすると、

```text
EC2 × 30
   ↓
30台分を時間課金
```

となる。

そのため、

> **24時間365日動かすVMをそのままクラウドへ移行すると、オンプレより高くなる可能性がある。**

---

# 19. クラウドではサーバーを減らす

AWSを利用するなら、

```text
30VM → 30EC2
```

だけで考えない。

例えば、

```text
Webサーバー
→ EC2 / ECS

DBサーバー
→ RDS / Aurora

ファイルサーバー
→ S3 / EFS

バッチサーバー
→ Lambda / ECS

ロードバランサー
→ ALB

バックアップ
→ S3
```

のようにAWSサービスへ置き換える。

イメージ：

```text
オンプレ

30VM
 ↓

AWS

ALB
 │
EC2 / ECS
 │
RDS
 │
S3
```

こうすることで、

```text
30VM
 ↓
EC2 10～15台
＋
RDS
＋
S3
＋
ECS / Lambda
```

などに減らせる可能性がある。

---

# 20. Savings Plansなども利用する

24時間稼働するEC2なら、

* Savings Plans
* Reserved系の割引
* 夜間停止
* Auto Scaling
* インスタンスのRightsizing

などでコストを削減する。

つまり、

```text
クラウド移行
≠
VMをEC2へそのままコピー
```

と考えることが重要。

---

# 21. オンプレとクラウドの特徴

|           | オンプレ  | クラウド    |
| --------- | ----- | ------- |
| 初期費用      | 高い    | 低い      |
| 月額費用      | 比較的安定 | 利用量次第   |
| 5年以上の固定利用 | ○     | △       |
| 急な拡張      | △     | ◎       |
| 縮小        | △     | ◎       |
| ハード保守     | 必要    | 不要      |
| 電気・空調     | 必要    | 不要      |
| 物理障害対応    | 必要    | AWS等が担当 |
| 24時間固定VM  | ◎     | 高くなりやすい |
| 負荷変動      | △     | ◎       |

---

# 22. オンプレが向いているケース

```text
・24時間365日稼働
・負荷が安定している
・VM数があまり変わらない
・5年以上利用する
・既存サーバールームがある
・運用担当者がいる
```

この場合、

> **オンプレの方がTCOを抑えられる可能性がある。**

---

# 23. クラウドが向いているケース

```text
・VM数が頻繁に増減
・負荷変動が大きい
・短期間利用
・夜間停止できる
・急速な拡張が必要
・ハードウェアを管理したくない
・マネージドサービスを活用できる
```

この場合、

> **AWS / Azureなどのクラウドが有利になりやすい。**

---

# 24. VMware更改時に比較する構成

VMwareのコストが問題になった場合、

```text
① VMware継続

3ホスト
30VM
↓
5年間TCO
```

だけでなく、

```text
② 別ハイパーバイザー

Proxmox / Hyper-V等
↓
VMwareライセンス削減
```

も比較する。

さらに、

```text
③ AWS リフト＆シフト

30VM
↓
30EC2
```

と、

```text
④ AWS最適化

EC2
＋
ECS
＋
RDS
＋
S3
＋
Lambda
```

も比較する。

---

# 25. 一番重要な考え方

VMware更改では、

```text
VMware高い
   ↓
AWSへ移行
```

と単純に判断しない。

正しくは、

```text
                現在の30VM
                     │
          ┌──────────┼──────────┐
          ↓          ↓          ↓
       VMware      Proxmox     AWS
        継続        等へ移行     移行
          │          │          │
          └──────────┼──────────┘
                     ↓
                 5年間TCO
                     ↓
                  比較・判断
```

で考える。

## 覚えておくポイント

> **「VM30台」ではなく、CPU・RAM・Disk・IOPSから物理スペックを決める。**

> **本番では1台故障しても稼働できるN+1構成を考える。**

> **30VM程度ならESXi 3台構成は一つの現実的な選択肢。**

> **オンプレで高いのは電気代だけではなく、ライセンス・保守・運用。**

> **24時間固定稼働ならオンプレが安くなることも多い。**

> **クラウドは30VMを30EC2にするだけではコストメリットが出にくい。**

> **クラウドではRDS・S3・ECS・Lambdaなどを使い、VMそのものを減らすことが重要。**

> **最終的には「初期費用」ではなく、3～5年間のTCOで比較する。**
