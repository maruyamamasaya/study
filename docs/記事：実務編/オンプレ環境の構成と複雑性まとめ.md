## 1. オンプレは「物理サーバーだけ」ではない

企業のオンプレ環境では、単純に、

```text
物理Server01
物理Server02
物理Server03
```

と並んでいるだけとは限らない。

実際には、

```text
物理サーバー
＋
VMwareなどの仮想化
＋
共有ストレージ
＋
DBクラスタ
＋
Proxy / FW / LB
＋
バックアップ
＋
監視
＋
DR
```

などが組み合わされている。

そのため、**長期間運用されている大規模環境ほど構成が複雑になりやすい。**

---

# 2. ケース① 1役割 = 1物理サーバー

昔からある構成。

```text
物理Server01 → Web
物理Server02 → AP
物理Server03 → DB
物理Server04 → Batch
```

### メリット

* 構成が分かりやすい
* 他システムの影響を受けにくい
* 性能を占有できる

### デメリット

* サーバー台数が増える
* CPU/RAMが余りやすい
* 電気・ラック・保守費用が増える

例えば、

```text
CPU使用率：5%
RAM使用率：20%
```

でも物理サーバー1台を占有する。

→ **リソース効率が悪い。**

---

# 3. ケース② VMwareで集約

現在よくある構成。

```text
         VMware Cluster
               │
    ┌──────────┼──────────┐
    ↓          ↓          ↓
 ESXi01      ESXi02      ESXi03
    │          │          │
   VM群       VM群       VM群
```

例えば、

```text
物理サーバー：3台
       ↓
仮想サーバー：30～50VM
```

のように集約する。

### メリット

* 物理サーバー削減
* CPU/RAMを共有できる
* VM追加が簡単
* vMotionが利用できる
* HA構成を組める

### デメリット

* VMwareの知識が必要
* ライセンス費用
* 仮想化基盤障害の影響が大きい
* vCenterなど管理基盤も必要

---

# 4. ケース③ VMware + 共有ストレージ

企業環境でよく見る構成。

```text
 ESXi01 ─┐
 ESXi02 ─┼─→ SAN / NAS
 ESXi03 ─┘
```

VMのデータをESXi本体ではなく、共有ストレージに保存する。

例えば、

```text
VM01
 ↓
VMDK
 ↓
共有Storage
```

となる。

これによって、

```text
ESXi01
  ↓
VM01

vMotion

ESXi02
  ↓
VM01
```

のような移動がしやすくなる。

---

# 5. ケース④ 物理サーバーとVMが混在

実際の企業環境ではかなりあり得る。

```text
【VMware】
ESXi01
ESXi02
ESXi03
 ↓
業務VM × 30


【物理】
DB Server01
DB Server02


【Storage】
SAN


【NW】
Firewall
Proxy
Load Balancer
```

つまり、

> **全部VMとは限らない。**

---

# 6. なぜDBだけ物理なのか？

例えば、

```text
Web → VM
AP  → VM
DB  → 物理
```

という構成。

理由としては、

* DB性能を安定させたい
* 大容量RAMが必要
* 高IOPSが必要
* CPUを占有したい
* 製品ベンダーの推奨構成
* 古いシステムをそのまま使用
* ライセンス条件

などがある。

---

# 7. ケース⑤ DBクラスタ

重要なDBを1台だけにすると、

```text
DB01
 ↓
故障
 ↓
システム停止
```

となる。

そのため、

```text
       DB Cluster

     Active
       │
     DB01
       │
       │ 障害
       ↓
     DB02
       │
    Standby
```

のような構成にする。

障害時、

```text
DB01 Active
 ↓
障害

DB02
 ↓
Activeへ昇格
```

となる。

---

# 8. ケース⑥ VMware HA + DBクラスタ

さらに重要なシステムでは、

```text
       VMware Cluster
              │
      ┌───────┴───────┐
      ↓               ↓
    ESXi01          ESXi02
      │               │
   DB VM01          DB VM02
   Active           Standby
      │               │
      └───────┬───────┘
              ↓
            Storage
```

のように、

```text
物理レベル
↓
VMware HA

OS/VMレベル
↓

DBレベル
↓
DB Cluster
```

と多重に冗長化することもある。

---

# 9. ケース⑦ Proxy / Firewall / LB

サーバー以外にも重要な機器が存在する。

```text
Internet
   │
Firewall
   │
Proxy / LB
   │
Web Server
   │
AP Server
   │
DB Server
```

それぞれ役割が違う。

### Firewall

```text
通信を許可 / 拒否
```

### Proxy

```text
通信を代理
社内 ↔ Internet
```

### Load Balancer

```text
アクセス
 ↓
Web01
Web02
Web03

へ振り分け
```

---

# 10. ケース⑧ Proxy自体も冗長化

Proxyが1台しかないと、

```text
社員
 ↓
Proxy
 ↓
Internet
```

Proxy障害で通信できなくなる。

そのため、

```text
           社内
            │
      ┌─────┴─────┐
      ↓           ↓
   Proxy01      Proxy02
   Active       Standby
      │           │
      └─────┬─────┘
            ↓
         Internet
```

のような冗長構成もある。

---

# 11. ケース⑨ HCI

従来構成では、

```text
ESXi Server
     │
SAN Switch
     │
Storage
```

とサーバーとストレージが分離されている。

HCIでは、

```text
Node01
CPU + RAM + SSD

Node02
CPU + RAM + SSD

Node03
CPU + RAM + SSD
```

をまとめて利用する。

```text
Node01 ─┐
Node02 ─┼→ 仮想化基盤
Node03 ─┘
```

VMwareではvSANなどがこの考え方に近い。

---

# 12. ケース⑩ バックアップ基盤

本番サーバーとは別に、

```text
VM / DB
   │
   ↓
Backup Server
   │
   ↓
Backup Storage
```

を用意する。

さらに、

```text
本番
 ↓
Backup
 ↓
別Storage
 ↓
別拠点 / Cloud
```

までコピーする場合もある。

重要なのは、

> **バックアップを同じサーバーだけに置かないこと。**

---

# 13. ケース⑪ DR（災害対策）

さらに重要なシステムではデータセンター自体を分ける。

```text
東京DC
├─ VMware
├─ DB
├─ Storage
└─ Backup

       ↓ Replication

大阪DC
├─ VMware
├─ DB
├─ Storage
└─ Backup
```

東京DCが、

```text
地震
停電
ネットワーク障害
火災
```

などで使用できなくても、大阪側へ切り替える。

これが**DR（Disaster Recovery）**。

# 14. ケース⑫ 古いシステムが残っている

企業オンプレを複雑にする大きな原因。

例えば、

```text

Windows Server

↓

2015年
VMware導入

↓

2020年
AWS導入

↓

2026年
Azure / SaaS導入
```

すると、

```text

       ＋
SaaS
```

という状態になる。

これが**ハイブリッド環境**。

# 21. なぜこんなに複雑になるのか？

主な理由は、

### ① 歴史

```text
古いシステムを簡単に捨てられない
```

### ② 可用性

```text
止められない
↓
冗長化
```

### ③ 性能

```text
DBなどは専用リソースが必要
```

### ④ セキュリティ

```text
FW / Proxy / DMZなどが必要
```

### ⑤ 製品制約

```text
特定OS
特定Java
特定DB
```

### ⑥ 災害対策

```text
Backup / DR
```

### ⑦ クラウド移行途中

```text
オンプレ
＋
AWS
＋
Azure
```

# 22. インフラ案件で最初に確認すること

複雑な環境では、まず構成を整理する。

```text

② ESXiは何台？

③ VMは何台？

④ OSは何？

⑤ Storageは何？

⑥ DBは何？

⑦ Proxy / FW / LBは？

⑧ HA構成は？

⑨ Backupは？

⑩ DRは？

⑪ AWS / Azureとの接続は？

⑫ 各製品のバージョンは？

⑬ サポート期限は？

⑭ システム間の依存関係は？
```

# 24. まとめ

企業オンプレは、

```text
物理サーバー
＋
VMware
＋
共有Storage
＋
物理DB
＋
DB Cluster
＋
Proxy
＋
Firewall
＋
Load Balancer
＋
Backup
＋
監視
＋
DR
＋
AWS / Azure
```

などが混在する。

特に長期間運用されている環境では、

> **「古い物理環境＋VMware＋クラウド」が共存する**

ことも珍しくない。

そのためインフラ案件では、

> **「何台あるか」より「何が何に依存しているか」を把握することが重要。**

構成変更や更改では、

> **1台変更したとき、どこまで影響するか？**

を考えることが、インフラ運用・設計の重要なポイントになる。
