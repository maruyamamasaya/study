# VMwareの変化と今後のインフラ基盤

## 1. VMwareとは

VMwareは、**1台の物理サーバー上で複数の仮想サーバー（VM）を動かすための仮想化基盤**として広く利用されてきた。

代表的な製品・技術として、**VMware ESXi / vSphere / vCenter Server** がある。

```text
物理サーバー
    ↓
VMware ESXi
    │
    ├─ VM① Windows Server
    ├─ VM② Linux
    ├─ VM③ Webサーバー
    └─ VM④ DBサーバー
```

従来は用途ごとに物理サーバーを用意するケースも多かったが、仮想化によって1台の物理サーバーを複数のVMで共有できる。

これにより、

* 物理サーバー台数の削減
* CPU・メモリなどの有効活用
* サーバー追加の容易化
* 運用・管理の効率化
* 可用性の向上

などを実現できる。

---

# 2. VMware環境の基本構成

基本的な関係は以下。

```text
               vCenter Server
              （集中管理）
                    │
                    ↓
                 Cluster
                    │
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      ESXi①       ESXi②       ESXi③
        │           │           │
      VM VM       VM VM       VM VM
        │           │           │
 物理サーバー①  物理サーバー②  物理サーバー③
```

### 主な用語

| 用語         | 役割                     |
| ---------- | ---------------------- |
| ESXi       | 物理サーバー上でVMを動かすハイパーバイザー |
| VM         | 仮想マシン・仮想サーバー           |
| vCenter    | 複数のESXiを集中管理           |
| Cluster    | 複数のESXiをグループ化          |
| vMotion    | 稼働中のVMを別ESXiへ移動        |
| vSphere HA | ESXi障害時に別ESXiでVMを再起動   |

# 3. 従来のVMwareの料金体系

Broadcomによる買収以前は、

> **必要なVMware製品を購入し、保守契約を結びながら長期間利用する**

という使い方が一般的だった。

特に従来は**永続ライセンス（Perpetual License）**が中心だった。

```text
ライセンス購入
      ↓
VMware環境構築
      ↓
サポート・保守契約
      ↓
数年間利用
      ↓
EOL / ハードウェア更改
      ↓
次期基盤へ移行
```

そのため企業側も、

> VMwareを導入
> → 5年程度利用
> → ハードウェア更改時に次期環境を検討

といった中長期的な計画を立てやすかった。

---

# 4. 従来のCPUソケット単位ライセンス

以前のVMwareでは長く、**物理CPUソケット**を基準としたライセンス体系が使われていた。

例えば、

```text
物理サーバー

├─ CPU①
└─ CPU②

＝ 2 CPUソケット
```

というサーバーなら、CPUソケット数を基準として必要なライセンスを考える。

その上で、

```text
ESXi
├─ VM①
├─ VM②
├─ VM③
├─ VM④
├─ VM⑤
└─ ...
```

と複数のVMを構築できる。

つまり、

> **VMが10台あるからVMwareライセンスも10個必要**

という考え方ではない。

---

# 5. BroadcomによるVMware買収

2023年11月、BroadcomによるVMwareの買収が完了した。

買収額は**約690億ドル規模**。

買収後、VMwareの

* 製品体系
* 販売方法
* ライセンス体系
* パートナー体系

などが大きく変更された。

重要なのは、

> 「VMwareの技術そのものが突然高価になった」

というより、

> **BroadcomがVMwareの製品・販売・ビジネスモデルを大きく再編した**

と理解すること。

---

# 6. VMwareのコスト構造が変化した主な理由

大きく整理すると、次の変化が重要。

```text
① 永続ライセンス
        ↓
   サブスクリプション


② CPUソケット中心
        ↓
   CPUコア数中心


③ 必要製品を個別購入
        ↓
   製品体系の集約・バンドル化


④ 幅広い顧客への販売
        ↓
   大規模・戦略顧客をより重視
```

この変化によって、企業によってはVMwareの更新コストが従来より大幅に変化するケースが出てきた。

---

# 7. 永続ライセンス → サブスクリプション

従来は、

```text
最初にライセンス購入
        ↓
保守・サポート費を支払う
        ↓
長期間利用
```

という形が中心だった。

現在は**サブスクリプション型**が中心となっている。

```text
契約
 ↓
利用
 ↓
契約更新
 ↓
利用
 ↓
契約更新
 ↓
・・・
```

つまり、

> **利用し続けるためには継続的な契約が必要**

というモデルになった。

企業側から見ると、従来の「ライセンス資産＋保守更新」とはコスト構造が大きく異なる。

---

# 8. CPUソケット → CPUコア数

もう一つ重要なのが、ライセンス算定基準の変化。

例えば、

```text
物理サーバー

CPU①：32コア
CPU②：32コア

合計
32 + 32
= 64コア
```

というサーバーがあったとする。

従来は、

```text
2 CPUソケット
```

という考え方が中心だった。

現在の主要なサブスクリプション製品では、

```text
64 CPUコア
```

のように、**物理CPUのコア数を基準としてライセンス数量を考える体系**が中心となっている。

最近のCPUは、

* 16コア
* 32コア
* 64コア
* それ以上

と多コア化している。

そのため、特に高コア数CPUを多数搭載した環境では、ライセンスコストへの影響が大きくなる可能性がある。

---

# 9. 製品体系の集約・バンドル化

従来は比較的、

> 「この機能が必要だから、この製品・エディションを購入する」

という選択がしやすかった。

Broadcom買収後は製品体系が大きく整理され、

**VMware Cloud Foundation（VCF）**

などを中心とした製品体系へ再編された。

イメージすると、

```text
【従来】

必要機能

A ○
B ○
C ×
D ×

↓
必要な製品・エディションを選択
```

から、

```text
【現在】

A
B
C
D
│
└─ 統合された製品・サブスクリプション
```

という方向へ変化したと考えると分かりやすい。

そのため利用環境によっては、

> 「必要な機能は限定的なのに、以前より契約規模が大きくなる」

というケースが発生する可能性がある。

---

# 10. なぜBroadcomはVMware事業を変えたのか

単純に、

> 「VMwareの維持費が高くなったから値上げした」

だけで考えると本質を捉えにくい。

BroadcomはVMwareを、

> **大企業や重要システムを中心とする、高収益なインフラソフトウェア事業**

として再構築していると考えると理解しやすい。

---

# 11. 理由① VMware買収から利益を生み出す

Broadcomは約690億ドルという非常に大きな規模でVMwareを買収した。

企業としては当然、

```text
VMware買収
    ↓
事業再編・効率化
    ↓
収益性向上
    ↓
キャッシュフロー拡大
```

を目指すことになる。

VMwareは企業の重要システムへ深く組み込まれているケースが多い。

例えば、

```text
VMware基盤

├─ Windows Server × 100
├─ Linux × 200
├─ DBサーバー × 50
└─ その他 × 100
```

という環境だった場合、

> 「VMwareが高くなったから来月AWSへ全部移行する」

とはできない。

移行には、

* 現行調査
* 移行先選定
* アプリケーション調査
* ネットワーク設計
* ストレージ設計
* データ移行
* バックアップ設計
* テスト
* 切り替え
* 障害対策

などが必要になる。

大規模環境ほど、基盤変更には時間とコストがかかる。

---

# 12. 理由② 顧客数より1社あたりの収益を重視

従来のVMwareは、

```text
小規模企業
中規模企業
大企業
超大規模企業
```

まで幅広い顧客を抱えていた。

Broadcomは事業再編によって、

```text
多数の顧客
×
比較的小規模な契約
```

だけではなく、

```text
重要な大企業
×
大規模な契約
```

をより重視する方向へ進んでいる。

製品・契約・販売・サポート体系を整理することで、事業全体の収益性を高める狙いがある。

---

# 13. 理由③ サブスクリプションで収益を安定させる

買い切り型では、新規ライセンス販売のタイミングによって売上が変動する。

```text
2025年：ライセンス販売
2026年：少ない
2027年：ライセンス販売
```

サブスクリプション型では、

```text
2025年：契約
   ↓
2026年：更新
   ↓
2027年：更新
   ↓
2028年：更新
```

となる。

そのため事業者側には、

> **継続的な収益を得やすく、将来の売上を予測しやすい**

というメリットがある。

---

# 14. VMware利用企業では何が起きているか

契約・料金体系が変わったことで、一部の企業では次のような検討が発生している。

```text
VMware契約更新
      ↓
更新費用を確認
      ↓
「従来より高い」
      ↓
「VMwareを継続するべきか？」
      ↓
他基盤も含めて比較
```

代表的な選択肢として、

```text
既存VMware
   │
   ├─ VMware継続
   │
   ├─ Hyper-V
   │
   ├─ Nutanix AHV
   │
   ├─ Proxmox VE
   │
   ├─ AWS
   │
   ├─ Azure
   │
   └─ その他
```

などが考えられる。

# 15. 「VMware脱却」がインフラ案件になる理由

VMwareから別基盤へ移行するといっても、

> **VMを単純にコピーすれば終わり**

ではない。

まず既存環境を調査する必要がある。

### 現行調査

```text
VMは何台ある？
        ↓
OSは何？
        ↓
CPU・メモリは？
        ↓
ストレージ容量は？
        ↓
ネットワーク構成は？
        ↓
VLANは？
        ↓
DBは？
        ↓
バックアップは？
        ↓
監視は？
        ↓
ジョブ管理は？
        ↓
他システムとの通信は？
```

その上で移行先を検討する。

```text
              現行VMware
                   │
        ┌──────────┼──────────┐
        ↓          ↓          ↓
    VMware継続   他仮想基盤   Cloud
                   │          │
              ┌────┼────┐   ┌─┴─────┐
              ↓    ↓    ↓   ↓       ↓
          Hyper-V AHV Proxmox AWS   Azure
```

     ↓

     ↓

     ↓

大規模な基幹システムでは、数か月～数年規模のプロジェクトになることもある。

# 17. VMware継続という選択肢もある

「VMware脱却」が注目されているからといって、

> **すべての企業がVMwareから移行する**

わけではない。

VMwareには、

* 長年の運用実績
* vMotion
* vSphere HA
* 大規模環境での実績
* 豊富な運用ノウハウ
* 周辺製品との連携
* VMwareに習熟したエンジニア

などの強みがある。

そのため、

```text
VMwareコスト
      VS
移行コスト + 移行リスク + 運用変更
```

を比較した結果、

> **VMwareを継続した方が合理的**

となる企業も当然存在する。

VMwareのライセンス体系変更は、インフラエンジニアにとって単なる「値上げニュース」ではない。

重要なのは、

> **既存環境を理解し、次の基盤へ安全に移行・更改できる能力**

である。

* TCP/IP
* VLAN
* DNS
* ストレージ
* SAN / NAS
* バックアップ
* 監視
* ジョブ管理
* AWS / Azure
* 仮想化
* サーバー構築
* 移行設計
* バージョン管理
* EOL管理
* 構成管理
* 変更管理

などがつながってくる。

# 19. 維持管理・バージョン管理との関係

インフラ環境には、それぞれバージョンやサポート期限が存在する。

例えば、

```text
物理サーバー
     ↓
VMware ESXi
     ↓
Windows Server
     ↓
Java
     ↓
Tomcat
     ↓
業務アプリケーション
```

という構成だった場合、ESXiだけを考えてバージョンアップすることはできない。

```text
ESXiをアップグレード
       ↓
ゲストOSは対応している？
       ↓
VMware Toolsは対応している？
       ↓
バックアップ製品は対応している？
       ↓
監視製品は対応している？
       ↓
ストレージは対応している？
       ↓
アプリケーションへの影響は？
```

といった確認が必要になる。

そのため、

> **バージョン管理・互換性確認・EOL管理**

はインフラ運用で非常に重要になる。

---

# 20. EOLとは

**EOL（End of Life）**は、製品・バージョンなどのライフサイクル終了を意味する。

例えば、

```text
ESXi バージョン
      ↓
サポート終了が近づく
      ↓
継続利用リスク増加
      ↓
アップグレード・更改を検討
```

となる。

EOL対応ではVMwareだけを見るのではなく、

```text
ハードウェア
   ↓
ESXi
   ↓
OS
   ↓
ミドルウェア
   ↓
アプリケーション
```

まで含めて互換性を確認する必要がある。

---

# 21. インフラ変更作業のワークフロー

実際のインフラ維持管理では、いきなり本番サーバーを変更することは基本的にない。

一般的には、

```text
変更要求
   ↓
影響調査
   ↓
変更内容決定
   ↓
変更・構築手順書作成
   ↓
レビュー
   ↓
承認
   ↓
検証環境でテスト
   ↓
本番作業
   ↓
動作確認
   ↓
証跡保存
   ↓
構成管理情報更新
```

という流れになる。

さらに重要なのが、問題発生時に元へ戻せるようにする**切り戻し（ロールバック）計画**。

```text
変更作業
   ↓
問題発生
   ↓
切り戻し判断
   ↓
旧構成へ復旧
   ↓
正常性確認
```

つまりインフラエンジニアには、

> **「サーバーを構築できる」だけではなく、安全に変更し、問題があれば戻し、その状態を正確に管理できること**

が求められる。
