## 調査範囲と画面の対応

本資料は `pages/admin/dashboard` 配下だけを管理 UI として調査した結果である。依頼上の名称と実装上の名称に差があるため、次のように対応付けた。

| 依頼上の対象 | 実装上の画面           | URL                                                                                                             |
| ------ | ---------------- | --------------------------------------------------------------------------------------------------------------- |
| 予約管理   | レンタル予約管理、予約詳細    | `/admin/dashboard/reservations`、`/admin/dashboard/reservations/[reservationId]`                                 |
| 会員管理   | 会員一覧、会員詳細        | `/admin/dashboard/members`、`/admin/dashboard/members/[id]`                                                      |
| 料金設定   | 車種ごとの料金設定、日毎料金設定 | `/admin/dashboard/bike-models/rental-pricing`、`/admin/dashboard/bike-models/[modelId]/rental-pricing`           |
| 車両管理   | 車両一覧、車両詳細、車両登録   | `/admin/dashboard/vehicles`、`/admin/dashboard/vehicles/[managementNumber]`、`/admin/dashboard/vehicles/register` |
| 店舗管理   | 休日管理             | `/admin/dashboard/holiday-manager`、`/admin/dashboard/holiday-manager/[storeId]`                                 |
| 通知管理   | 新着情報管理           | `/admin/dashboard/announcements`                                                                                |

> **名称上の注意**
>
> 現行コードに店舗マスターを CRUD する「店舗管理」画面や、会員ごとのサイト内通知を管理者が配信・編集する「通知管理」画面は存在しない。
>
> 実装上は、
>
> - 「店舗管理」＝店舗別休日管理
> - 「通知管理」＝サイト上部のお知らせバナー（新着情報管理）
>
> として実装されている。
>
> また、会員向け `/api/notifications` は Cognito ログイン済み会員本人向け API であり、本管理画面からは利用されていない。

---

# 共通認証

## 管理画面

`/admin` で始まる画面アクセスは、Next.js Middleware により **HTTP Basic 認証** が適用される。

認証情報は以下の環境変数を利用する。

- `ADMIN_BASIC_USER`
- `ADMIN_BASIC_PASS`

環境変数が設定されていない場合は、コード内に定義された既定値へフォールバックする。

---

## API の認証状況

Middleware の matcher は **`/api` を除外**している。

そのため、本資料で扱う管理 API は Basic 認証の対象外である。

さらに、

各 API 自身にも

- 管理者認証
- ロール判定
- 権限チェック

は実装されていない。

---

## 例外

例外として、

```
POST /api/reservations
```

（一般ユーザーによる予約作成）

のみ、

Cognito の ID Token Cookie を検証している。

しかし、

管理画面が利用する

- `GET /api/reservations`
- `GET /api/reservations/[reservationId]`
- `PATCH /api/reservations/[reservationId]`

などは認証を行っていない。

---

## 現状の構成

現在は以下のような構成となっている。

```
管理画面
        │
        │ Basic認証
        ▼
画面（/admin/...）
        │
        │ API呼び出し
        ▼
/api/*
        │
        └── 認証なし
```

つまり、

- 管理画面の入口は Basic 認証で保護されている
- API 自体は URL が分かれば直接呼び出せる

という構造になっている。

更新 API についても同様であり、認可上の重要な課題となっている。

# 1. 予約管理

## 役割

### 一覧画面

全予約を取得し、

以下の条件で絞り込みができる。

- キーワード
- ステータス
- 店舗
- 車種
- 貸出日
- 返却日

また、

各列で並び替えを行い、予約詳細画面へ遷移する。

---

### 詳細画面

以下の情報を確認できる。

- 予約情報
- 会員情報
- 決済情報
- 貸出車両
- 貸出日時
- 返却日時

---

### 管理者操作

管理画面から以下の操作を行える。

- 返却日の延長
- 貸出日時の変更
- 割当車両変更
- キャンセル（返金あり）
- キャンセル（返金なし）
- 管理者による返却承認

---

## 利用 API

| Method | API | 用途 |
| --- | --- | --- |
| `GET` | `/api/reservations` | 予約一覧取得 |
| `GET` | `/api/reservations/[reservationId]` | 予約詳細取得 |
| `PATCH` | `/api/reservations/[reservationId]` | 日時・車両・ステータス更新 |
| `GET` | `/api/vehicles` | 車両一覧取得 |
| `GET` | `/api/vehicles/[managementNumber]` | 現在の車両・空き状況取得 |
| `GET` | `/api/high-season?month=YYYY-MM` | 延長料金計算用ハイシーズン取得 |
| `POST` | `/api/admin/return-approval` | 管理者返却承認 |

---

## 更新処理

### 1. 延長

処理内容

1. 延長日数を入力
2. 新しい返却日時を計算
3. 同一車両の空きをクライアント側で確認
4. `returnAt` を `PATCH`

注意点

- 決済は実施しない
- 追加料金は別途ユーザー決済が必要である旨を表示する

---

### 2. 日時変更

処理内容

- 予約期間（日数）は維持
- `pickupAt`
- `returnAt`

を更新する。

API 側では

- 予約時間更新
- 車両の日別稼働状態更新

を実施する。

返却日時が変更された場合は

KEYBOX PIN の再発行も試行する。

---

### 3. 車両変更

条件

同一車種で、

予約期間中すべて利用可能な車両のみ選択できる。

更新内容

- `vehicleCode`
- `vehiclePlate`
- 通知フラグ

API 側では

旧車両

```
予約解除
```

↓

新車両

```
RENTED
```

へ更新する。

---

### 4. キャンセル

送信内容

```json
{
  "status": "キャンセル"
}
```

および

- 返金メモ
- skipRefund

通常

API は

- PAY.JP 返金
- 決済番号確認
- 金額確認
- 売上から180日以内確認

を行う。

```
skipRefund = true
```

の場合は

返金を行わずキャンセルのみ実施する。

---

### 5. 返却承認

管理者操作により

予約を

```
返却済み
```

へ変更する。

同時に

車両側の予約期間を

```
RENTAL_COMPLETED
```

へ更新する。

---

## 認証

管理画面は Basic 認証対象である。

しかし、

以下の API

- GET
- PATCH
- 管理者返却 POST

については

**管理者認証・ロールチェックは実装されていない。**

# 3. 料金設定

## 役割

親画面

- クラス一覧取得
- 車種一覧取得
- 車種ごとの料金設定状況表示
- 車種別設定画面への遷移

車種別画面

- 1〜30日料金を表示
- 1・2・3・4・7日の料金から中間日を自動補間
- 未登録車種はクラス料金から初期生成
- 日毎料金を削除可能

---

## 利用 API

| Method | API | 用途 |
| ------ | --- | ---- |
| GET | `/api/bike-classes` | クラス・クラス料金取得 |
| GET | `/api/bike-models` | 車種一覧取得 |
| GET | `/api/vehicle-rental-prices?vehicle_type_id=...` | 車種別料金取得 |
| PUT | `/api/vehicle-rental-prices` | 日毎料金 Upsert |
| DELETE | `/api/vehicle-rental-prices` | 日毎料金削除 |

---

## 更新処理

### 保存

算出した日毎料金を

```
1日
↓
2日
↓
3日
...
```

のように **1件ずつ PUT** する。

※ 一括トランザクションではないため、途中失敗すると一部だけ保存される可能性がある。

### Upsert

```
vehicle_type_id
+
days
```

が一致すれば更新。

```
price = 0
```

の場合は削除扱い。

### 削除

- 確認ダイアログ表示
- DELETE実行
- 成功後に画面Stateから削除

---

## 認証

- Basic認証のみ
- 料金API・クラスAPI・車種APIはサーバ側認証なし

# 横断的な注意点

## ① APIの管理者認可不足（最重要）

現状

- Middlewareが`/api`を除外
- 更新APIに認証なし

そのため

```
API URLを知っていれば
誰でも更新可能
```

となっている。

### 対応推奨

- 共通管理者認証Middleware追加
- サーバ側ロールチェック追加

---

## ② Basic認証のデフォルト値

環境変数未設定時

既知の固定文字列へフォールバックしている。

本番では

```
環境変数未設定
↓
起動失敗
```

となる Fail Closed が望ましい。

---

## ③ 実際の責務との差異

現在存在しない機能

- 店舗マスター編集
- 通知配信
- Push通知
- メール通知

これらを要件とするなら

**新規機能開発**になる。

---

## ④ 部分更新リスク

以下は複数API呼び出しで構成される。

- 料金保存
- CSV車両登録

途中失敗すると

```
一部だけ保存
```

となる。

現在

- トランザクションなし
- ロールバックなし

で実装されている。

### 改善案

- 一括保存API
- DynamoDB Transaction
- エラー時ロールバック
- リトライ処理
- 保存結果一覧の返却
