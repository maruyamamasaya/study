### 予約システムの排他制御・重複予約判定の仕組み
## 概要

この予約システムでは、**予約可能かどうかを2回確認する**ことで、できるだけ重複予約を防ぐ設計になっています。

しかし、DynamoDBのトランザクションや条件付き更新は利用していないため、**同時アクセス（Race Condition）には完全には対応できていません。**

---

# 全体フロー

```text
Step3（確認画面）
      │
      ▼
日時をISO形式へ変換
      │
      ▼
予約可能か確認（validateOnly）
      │
      ▼
Pay.JPで決済
      │
      ▼
POST /api/reservations
      │
      ▼
再度予約可能か確認
      │
      ▼
Reservationsへ保存
      │
      ▼
VehiclesをRENTEDへ更新
      │
      ▼
予約完了
```

ポイントは、**決済前と予約保存直前の2回、空き状況を確認している**ことです。

---

# 重複予約を判定する処理

## ① isReservationRangeAvailable

**ファイル**

```
pages/api/reservations/index.ts
```

### 役割

対象車両の

```
rentalAvailability
```

を確認し、

```
貸出日
↓

返却日
```

までの全日が

```
AVAILABLE
```

なら予約可能と判定します。

---

## 判定イメージ

例えば

```
7/20 AVAILABLE
7/21 AVAILABLE
7/22 AVAILABLE
```

なら

```
7/20〜22
```

は予約できます。

一方

```
7/21 RENTED
```

なら

```
予約不可
```

になります。

---

# 期間チェック

別の関数

```
isWithinReservationWindow
```

では

以下を確認しています。

- 貸出日時 < 返却日時
- 3か月以内
- 最大31日

つまり

こちらは

**重複判定ではなく入力チェック**です。

---

# 日時比較の仕組み

最初は

```
pickupAt

returnAt
```

を

```
Date
```

へ変換し

```
返却 > 貸出
```

を確認します。

しかし

重複判定では

```
時間

09:00〜12:00
```

などは見ません。

見るのは

```
2026-07-20
```

のような

**日付だけ**です。

---

## つまり

```
9:00〜12:00
```

予約済でも

```
13:00〜18:00
```

は予約できません。

その日は丸ごと

```
RENTED
```

になります。

---

# buildDateKeysInRange

予約保存後

```
貸出日

↓

返却日
```

までを

```

2026-07-21

2026-07-22
```

のように展開します。

# Vehiclesテーブルの更新

更新内容は

```text
rentalAvailability

2026-07-20
↓

RENTED

2026-07-21
↓

RENTED
```

となります。

つまり

時間単位ではなく

**日単位管理**です。

# Race Conditionとは

## 同時アクセス

例えば

Aさん

```
予約開始
```

Bさん

```
同時予約開始
```

だった場合

両方とも

```
AVAILABLE
```

を読みます。

その後

```
A 保存

B 保存
```

となる可能性があります。

---

## イメージ

```text
A
│
├── AVAILABLEを見る
│
│
│
├───────────────保存

B
│
├── AVAILABLEを見る
│
│
│
├───────────────保存
```

この間

ロックがありません。

---

# DynamoDB側

現在利用している処理は

```
GetCommand

↓

PutCommand
```

だけです。

つまり

```
読んで

↓

全部書き換える
```

方式です。

---

# ConditionExpression

Vehicles更新時は

```
attribute_exists(managementNumber)
```

のみ。

つまり

保証されるのは

```
車両が存在する
```

だけです。

例えば

```
まだAVAILABLEか？
```

は確認しません。

---

# Transaction

現在

```
TransactWriteItems
```

は使われていません。

つまり

```
予約保存

↓

Vehicles更新
```

は

別々の処理です。

---

# Lost Update

こちらも起こり得ます。

例えば

```
A

7/20予約

↓

RENTED更新
```

その途中で

```
B

7/25予約

↓

古いデータでPut
```

すると

Aの更新内容が

消える可能性があります。

これを

```
Lost Update
```

と呼びます。

---

# 現状の問題点

## ① 二重予約

同じ日程を

同時予約できる可能性があります。

---

## ② Lost Update

別日程でも

後からのPutが

前の更新を消す可能性があります。

---

## ③ 予約だけ残る

処理順は

```
Reservations保存

↓

Vehicles更新
```

です。

Vehicles更新で失敗すると

予約だけ残る可能性があります。

---

## ④ 日単位管理

時間単位ではありません。

```
7/20

9:00〜10:00
```

だけ予約しても

```
7/20
```

全体が予約不可になります。

---

## ⑤ 決済とのタイミング

現在は

```
予約確認

↓

決済

↓

予約保存
```

なので

決済中に

他人が予約を確定できる可能性があります。

---

# 改善案

もし今後改善するなら、以下のような構成が考えられます。

## ① DynamoDB Transaction

```
Reservation保存

+

Vehicles更新
```

を1つのトランザクションで実行する。

---

## ② ConditionExpression

更新時に

```
まだAVAILABLEなら更新
```

という条件付き更新を行う。

---

## ③ 時間単位管理

現在

```
日単位
```

ですが

```
09:00〜12:00
```

など時間帯で判定できれば、同じ日の別時間帯も予約可能になります。

---

## ④ 仮予約方式

```
仮予約

↓

決済

↓

本予約
```

とすることで、

決済中の取り合いを減らせます。

---

# まとめ

現在の予約システムは、**決済前・予約保存前の二重チェック**によって通常利用では十分な安全性を確保しています。

一方で、DynamoDBのトランザクションや条件付き更新を使用していないため、

- 二重予約
- Lost Update
- 予約だけ残る不整合

といった**同時アクセス時の競合リスク**が残っています。

そのため、この実装は小〜中規模サービスでは運用可能ですが、予約数や同時アクセスが増える場合は、トランザクションや排他制御の導入を検討する価値があります。
