### 1. 現場の「要望」と「本当の課題」は違う

現場から「こういう機能が欲しい」と言われても、そのまま作らない。

```
現場の要望
  ↓
なぜそれが必要？
  ↓
何に困っている？
  ↓
他部署にも同じ問題はない？
  ↓
本当にITで解決すべき？
  ↓
全社として最も効果の高い解決策は？
```

つまり、

> **要望を実装するのではなく、要望の裏にある課題を解く。**

さらに「その部署だけの最適化」ではなく、**横展開できる共通課題に抽象化する視点**が重要です。

---

### 2. 「作ったら終わり」ではなく、浸透まで設計する

社内システムでは、技術的に完成しても使われなければ意味がありません。

重要なのは、

**徐々に理解してもらう → 最後は新しい運用へ統一する**

という流れ。

「なぜ変えるのか」「何が便利になるのか」は丁寧に説明する。一方で移行段階では、

> 「旧運用でも新運用でも好きな方を使ってください」

にしてしまうと定着しにくい。

**説明は丁寧に、移行は明確に。**

これはかなり実務的に重要なポイントです。

---

### 3. 組織には「UXの好み」がある

UI/UXというと一般的な「使いやすさ」を考えがちですが、この記事で面白いのは、**会社ごとに使いやすさの基準が違う**という視点です。

たとえば、

|組織の特徴|相性の良い仕組み|
|---|---|
|チャット文化|チャットから操作|
|スマホ利用が多い|モバイル完結|
|ITリテラシーに差がある|操作を極力減らす|
|入力作業への抵抗が強い|自動入力・選択式|
|既存ツールへの依存が強い|既存ツールとの連携|

つまり、

> **「一般的に使いやすいUI」より「この会社の人が使いやすいUI」を作る。**

ここまで理解できるのは、社内IT担当ならではの強みです。

---

### 4. ユーザーを「利用者」ではなく「仲間」にする

かなり重要なのがこれです。

完成してから、

```
作りました
↓
説明会します
↓
使ってください
```

ではなく、

```
課題を聞く
↓
一緒に考える
↓
プロトタイプを触ってもらう
↓
フィードバックを反映
↓
一緒に完成させる
↓
その人が部署内で広める
```

という流れを作る。

現場のキーマンが、

**「IT部門が作ったシステム」ではなく「自分たちも一緒に作ったシステム」**

と思える状態を作ることで、自然と推進役になってくれます。

これは単なるヒアリングではなく、**社内にプロダクトのファンを作る活動**と考えると分かりやすいです。

---

### 5. AI時代ほど「何を作るか」の価値が上がる

生成AIによって、

**作る能力そのものは急速にコモディティ化している**

というのが最後の重要ポイントです。

以前は、

```
アイデア → 設計 → 開発 → 数週間〜数ヶ月
```

だったものが、

```
アイデア → AI → プロトタイプ
                 ↑
              数時間〜数日
```

まで短縮できるケースも増えています。

すると差がつく場所が変わります。

**「どう実装するか」だけでなく、**

- 誰が困っているのか
- なぜ困っているのか
- 本当に解決すべき問題は何か
- どうすれば自然に使ってもらえるか
- どこまで業務フローを変えるべきか
- 会社全体では何を優先すべきか

を判断する能力が重要になります。

---

## この話を一言でまとめるなら

> **社内IT推進とは「システム開発」ではなく「組織の行動変容をプロダクトで起こす仕事」である。**

ここがこの記事で一番重要だと思います。

技術力だけを見ると、

**要望 → 実装**

になりがちですが、実際の社内IT推進では、

**観察 → ヒアリング → 課題発見 → 抽象化 → 優先順位 → 設計 → プロトタイプ → 巻き込み → 開発 → 導入 → 浸透 → 効果測定 → 改善**

までが一連の仕事です。

そしてAIによって「開発」のコストが下がるほど、前後にある**課題発見・判断・巻き込み・浸透設計**の価値が相対的に大きくなっていく、というのがこの記事から拾える一番大きな学びです。
