「複数顧客・複数案件を並行して、要件整理→設計→開発→テストまで動かす」仕事では、かなり参考になる実例があります。

結論からいうと、重要なのは**マルチタスクが上手くなることではなく、「案件は複数持つが、実作業はなるべく1つずつ流す」仕組みを作ること**です。Qiitaでも、年間数十件のWeb案件を担当するエンジニアが案件別の情報整理を徹底していたり、WIP（仕掛かり作業）を制限して切替コストを抑える実践が紹介されています。

## まず「複数案件」と「マルチタスク」は分けて考える

例えば西川計測でこうなったとします。

```
A社：WeLS 画面改修
B社：NEXS 新機能
C社：既存システム不具合
D社：来月リリース予定
```

4案件を担当しているからといって、

```
9:00  A社実装
9:20  B社メール
9:40  A社実装
10:00 C社調査
10:30 A社実装
11:00 B社仕様確認
```

と細切れにするのは避けたい。

Qiitaのカンバン実践例でも、仕掛かり作業が増えるほど切り替えが増え、完了までの時間が延びるため、原則として一人が集中する作業を絞る方法が紹介されています。待ち状態になったら別タスクへ移る、という考え方です。

つまり理想は、

```
案件：4つ持っている

でも

「今やっている作業」：1つ
```

です。

# ① まず「案件一覧」と「タスク」を分ける

これはかなり大事です。

複数プロジェクトのタスク管理についての記事でも、プロジェクトごとに専用ページを作り、概要・目的・期日などをまとめ、その下に具体的なタスクを置く方法が紹介されています。

今回なら、まずこういう**案件台帳**を持つ。

|案件|状態|次の期限|自分の担当|次のアクション|
|---|---|---|---|---|
|A社 WeLS|開発中|9/18|画面改修|API実装|
|B社 NEXS|要件定義|9/20|要件整理|顧客回答待ち|
|C社 WeLS|テスト|9/16|不具合修正|原因調査|
|D社 AFAS|未着手|10/1|基本設計|仕様確認|

その下にタスクを置く。

```
A社
 ├─ API仕様確認
 ├─ DB確認
 ├─ API実装
 ├─ 単体テスト
 └─ PR

B社
 ├─ 顧客ヒアリング
 ├─ 議事録
 ├─ 画面イメージ
 ├─ 要件整理
 └─ 顧客確認
```

**「案件」と「今日やること」を同じ粒度で管理しない**のがポイントです。

---

# ② 状態は「ToDo / Doing / Done」だけでは足りない

今回のような顧客案件なら、僕ならこうします。

```
Backlog
   ↓
ToDo
   ↓
Doing
   ↓
Review
   ↓
Waiting
   ↓
Done
```

特に重要なのが、

**Waiting（待ち）**

です。

例えば、

```
B社 NEXS

状態：Waiting
理由：顧客から仕様回答待ち
回答予定：9/17
次のアクション：
回答が来たら画面仕様書を更新
```

ここまで残す。

これならB社を頭から追い出してA社に集中できます。

カンバンでは「見える化」「WIP制限」「流れの管理」が中心で、どこに仕事が滞留しているかを把握する考え方が重視されています。

---

# ③ Doingを増やさない

ここが今回一番重要だと思います。

例えば、

```
Doing

A社 API実装
B社 画面設計
C社 バグ調査
D社 DB調査
```

となったら危険。

全部「着手済み」だけど何も終わらない状態です。

WIP制限の記事でも、狙いとして

- リードタイム改善
- スループット改善
- ボトルネック発見
- コンテキストスイッチ削減

が挙げられています。

なので個人レベルでは、

```
Doing

A社 API実装 ← 今これ
```

くらいが理想。

ただし実務では完全なWIP=1にすると「顧客回答待ちで全部止まる」といった問題もあるため、厳密な1個流しを理想化しすぎない方がいいという指摘もあります。

今回なら、

**Doing最大1〜2個**

くらいが現実的でしょう。

# ④ 仕事を「時間帯」でまとめる

これもかなり有効です。

例えば、

```
09:00
案件一覧確認

09:15〜11:00
━━━━━━━━━━━━━━
A社 開発
━━━━━━━━━━━━━━

11:00〜11:30
メール
Teams
問い合わせ
レビュー

13:00〜14:00
B社 顧客MTG

14:00〜14:30
議事録・仕様整理

14:30〜16:30
━━━━━━━━━━━━━━
C社 不具合調査
━━━━━━━━━━━━━━

16:30〜17:00
レビュー・問い合わせ

17:00〜17:30
進捗更新
明日のタスク整理
```

という感じ。

「開発しながらSlackを見る」ではなく、

```
開発時間
──────────
Slack見ない
メール見ない

↓

連絡時間
──────────
Slack
メール
レビュー
問い合わせ

↓

また開発
```

とする。

タイムボックスとWIP=1を組み合わせ、集中時間中はチャットへの返信も別タスクとして扱う実践例もあります。

これはWeb開発ではかなり理にかなっています。

# ⑤ タスクを小さくする

「A社対応」

では大きすぎます。

```
× A社対応

○ A社検索画面
    ↓
  既存仕様確認 30分
    ↓
  API調査 1時間
    ↓
  API修正 2時間
    ↓
  テスト 1時間
    ↓
  PR作成 30分
```

こうすると、

「今日どこまで終わるか」

が分かります。

複数案件ではこれが非常に重要です。

```
今日

A社
API修正まで完了

B社
顧客MTG＋議事録まで

C社
明日着手
```

と判断できるからです。

# ⑥ 優先順位の基準を持つ

Qiitaで最近公開されたエンジニア向けの記事では、シンプルな基準として**「影響範囲」**で優先度を考える方法が紹介されています。たとえば本番障害→他チームの問題→内部資料、という順番です。

今回なら、僕ならこんな基準にします。

```
① 本番障害
    ↓
② 顧客業務が止まっている
    ↓
③ 今日・明日が期限
    ↓
④ 他メンバーを止めている
    ↓
⑤ 顧客回答が必要
    ↓
⑥ 通常開発
    ↓
⑦ ドキュメント・改善
```

例えば、

```
A社 API実装
期限：金曜

B社 本番障害
顧客業務停止

C社 設計レビュー
今日まで
```

なら、

```
B → C → A
```

です。

重要なのは、**「先に依頼された順」ではない**ことです。

---

# ⑦ ただし、優先順位を自分だけで決めない

これはSEとして結構重要です。

例えば、

```
A社
「明日までにお願いします」

B社
「これ最優先です」

C社
「今週リリースです」
```

全部Highになったら、

```
自分：
全部頑張ります！
```

ではなく、

```
自分
 ↓
PL / PM

「A・B・Cが競合しています。

A：2h
B：4h
C：3h

現在の優先順位は
B → C → A
と考えています。

Aは明日にずれる可能性があります。」
```

と上げる。

複数プロジェクトでは、横断的な調整やリソース最適化そのものが必要になるというPMO/マルチプロジェクト管理の考え方とも一致します。

つまり、

**優先順位の衝突は「個人の頑張り」で吸収するものではなく、管理上の問題として見える化する。**

これが大事です。

# ⑧ スケジュールを100%埋めない

今回の案件なら、ここもかなり重要。

顧客案件では必ず、

```
問い合わせ
仕様変更
レビュー依頼
不具合
顧客から電話
PMから確認
テストNG
```

が飛んできます。

だから、

```
8時間勤務

8時間分予定
```

にすると一瞬で破綻します。

僕なら最初は、

```
予定作業    5〜6時間

会議        1時間

問い合わせ
レビュー
割り込み
バッファ    1〜2時間
```

くらいで考えます。

毎日必ず2時間空けるという意味ではなく、**自分の稼働を100%予約しない**ということです。

---

# ⑨ 案件を切り替えるとき「再開メモ」を残す

これは複数Web案件ではかなりおすすめです。

例えばA社作業を途中で止めるなら、

```
A社 WeLS

■ 現在
検索API改修中

■ 完了
・既存API調査
・SQL確認
・パラメータ追加

■ 次
SearchService修正

■ 問題
equipmentIdsがnullの場合の仕様不明

■ 確認先
田中さん

■ 関連
Backlog #1234
PR #567
```

これを残してB社へ移る。

翌日、

```
「昨日何やってたっけ？」
```

がなくなります。

複数案件ではこういう**脳の外に状態を保存する仕組み**がかなり重要です。

年間数十件の案件を担当するWebエンジニアの記事でも、案件ごとのメール振り分けなど、案件単位で情報を整理することが実践されています。

# 僕なら今回、この「3階層」で管理する

これが一番おすすめです。

```
┌─────────────────────┐
│ ① 案件管理           │
│                     │
│ A社 WeLS             │
│ B社 NEXS             │
│ C社 AFAS             │
│ D社 WeLS             │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ ② タスク管理         │
│                     │
│ 要件                 │
│ 設計                 │
│ 実装                 │
│ テスト               │
│ レビュー             │
│ Waiting              │
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│ ③ 今日やること       │
│                     │
│ 09-11 A社 API        │
│ 11-12 レビュー       │
│ 13-14 B社 MTG        │
│ 14-16 A社 React      │
│ 16-17 割り込み枠     │
└─────────────────────┘
```

**①案件は全部見る。  
②タスクは全部記録する。  
③でも実際に作業するものは絞る。**

これです。

今回調べた中でも、複数案件の専用ページ化、カンバンによる見える化、WIP制限、優先順位付け、案件ごとの情報整理という考え方が繰り返し出ています。

西川計測案件に入るなら、**「マルチタスクが得意な人」より、「複数案件を可視化し、優先順位を付け、今やることを1つに絞り、問題があれば早くPL/PMへ上げられる人」**の方が強いと思います。

特に参画直後は、まず **案件名 / 顧客 / 製品 / PM・PL / 自分の役割 / 次の期限 / 現在工程 / 次のアクション / Waiting / リスク** を一覧化するところから始めると、かなり仕事しやすくなるはずです。
