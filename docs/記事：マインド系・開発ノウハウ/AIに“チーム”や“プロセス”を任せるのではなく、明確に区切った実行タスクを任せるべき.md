特に重要な部分を整理すると、次のようになります。

# 一番大事な結論

> **AIは作業者としては強いが、プロジェクトマネージャーやスクラムチームとして自律運転させると破綻しやすい。**

AIに、

```
あなたはPOです
あなたはスクラムマスターです
あなたは開発者です

役割を切り替えながら、
自律的にスクラム開発してください
```

と頼んでも、人間のチームのようには動きません。

この記事の検証では、最終的に次の状態になりました。

```
計画を立てる
  ↓
プロセスを無視して実装する
  ↓
局所的な修正を重ねる
  ↓
複数作業が競合する
  ↓
修正の修正が発生する
  ↓
AIがさらに修正する
  ↓
コストと混乱だけが増える
```

つまり、**AIに役割を与えるだけでは、組織的な協調は生まれない**ということです。

---

# 1. AIは「プロセス」より「目の前の解決」を優先する

スクラムでは、本来このように進めます。

```
バックログ整理
  ↓
スプリントプランニング
  ↓
実装
  ↓
レビュー
  ↓
振り返り
```

しかしAIは、Issueや課題を見ると、

> 「この問題を今すぐ解決しよう」

と動きやすい。

そのため、

```
今は計画だけしてください
まだコードは変更しないでください
```

と指示しても、コード修正に進んでしまうことがあります。

これは単なる指示不足ではなく、AIが基本的に、**入力された課題に対して答えを返すよう作られている**ことと関係しています。

つまり、

> **AIは目的達成には強いが、途中の儀式や手順を守ること自体には価値を感じない。**

スクラムのイベントを守ることと、問題を早く解くことが競合した場合、AIは後者に寄りやすいということです。

---

# 2. 1つのAIに複数の役割を演じさせても、独立した議論にはならない

この記事で特に重要なのが、**AIのロールプレイは、本物の複数人による議論ではない**という点です。

たとえば、

```
PO：要件を説明する
スクラムマスター：進め方を整理する
開発者：実装方法を提案する
```

と役割を分けても、実際にはすべて同じAIのコンテキスト内で処理されています。

そのため、

```
POが誤った前提を置く
  ↓
スクラムマスター役がその前提を引き継ぐ
  ↓
開発者役もその前提で設計する
  ↓
全員が同じ方向に間違える
```

ということが起きます。

人間のチームなら、別の人が、

> 「その前提は違うのでは？」

と指摘する可能性があります。

しかし単一AIの中で役割を切り替えても、前の出力を前提として続けるため、**誤りを相互監視するのではなく、誤りを増幅させる**場合があります。

> **人格を分けても、思考基盤まで独立するわけではない。**

ここが大事です。

---

# 3. AIは局所的な正解を積み重ねて、全体設計を壊すことがある

AIは、目の前のバグを直すことには非常に強いです。

ただし、その修正が、

- システム全体の設計方針に合っているか
- 同じロジックが別の場所に存在しないか
- 責務の分離を壊していないか
- 将来的に保守しやすいか
- 一時的なパッチになっていないか

まで常に考慮されるとは限りません。

たとえば本来は、共通処理を修正すべき問題なのに、

```
画面Aにif文を追加
画面Bにもif文を追加
APIにも例外処理を追加
別のサービスにも条件分岐を追加
```

と個別対応を重ねることがあります。

一つひとつの修正は動いていても、全体では、

```
重複コード
例外処理の乱立
責務の混在
条件分岐の増加
設計思想の不統一
```

が起きます。

> **「動く修正」と「良い設計」は同じではない。**

AIは前者を素早く作れますが、後者には人間による設計判断が必要です。

---

# 4. AIを並列で動かすと、会話だけでなくファイルも競合する

複数のAIタスクを同時に動かせば、開発が速くなるように見えます。

しかし、同じコードベースを共有していると、

```
AI-A：認証処理を修正
AI-B：同じ認証処理をリファクタリング
AI-C：関連APIを変更
```

のような状態が発生します。

それぞれが作業開始時点のファイルを前提に変更すると、

```
AI-Aの変更をAI-Bが上書き
AI-Bの修正をAI-Cが消す
AI-Cの変更でテストが壊れる
```

といった競合が起こります。

そこからAIに競合解決まで任せると、

```
競合を解消
  ↓
別のテストが失敗
  ↓
追加修正
  ↓
別のファイルと競合
  ↓
再度マージ
```

というループに入る可能性があります。

その結果、作業速度を上げるための並列化が、逆に、

- トークン消費
- API利用料金
- 実行時間
- レビュー負荷
- マージ作業

を増やします。

> **AIエージェントの並列化は、人数を増やすことではなく、競合可能性を増やすことでもある。**

---

# 5. AIの作業時間を、人間のベロシティと同じようには測れない

AIに対して、タスクを「大・中・小」で見積もらせること自体は可能です。

しかし、実際にどれだけ処理できたかを測ると問題が出ます。

理由は、AIの作業時間に次のようなものが混ざるからです。

- コマンドの実行許可待ち
- ユーザーの返信待ち
- APIやツールの応答待ち
- エラーによる再試行
- コンテキストの読み直し
- マージ競合の解決
- 人間によるレビュー待ち

そのため、

```
AIが10分で修正した
```

ように見えても、実際には、

```
純粋な生成時間
ツール実行時間
承認待ち
再実行時間
人間の確認時間
```

が混在しています。

つまり、人間のチームで使う、

- 作業時間
- ストーリーポイント
- ベロシティ
- スプリント消化率

をそのままAIに適用しても、意味のある指標にならない場合があります。

AI活用では、時間よりも、

- 人間の作業が何時間減ったか
- 修正後の不具合率
- レビューにかかった時間
- 一度で通ったタスクの割合
- 手戻り回数
- 完了までの総コスト

を見る方が実務的です。

---

# 6. AIは反省文を書けても、反省によって成長するとは限らない

レトロスペクティブでAIに、

```
今回の問題点を分析してください
次回の改善策を考えてください
```

と頼むと、非常にもっともらしい内容を出します。

たとえば、

```
今後は実装前に影響範囲を確認します
既存設計との整合性を重視します
並列作業時には競合を確認します
```

といった改善策です。

しかし、ここで重要なのは、

> **反省文を出力することと、次回の行動が本当に変わることは別。**

という点です。

人間は失敗を経験すると、判断基準や習慣が変化する可能性があります。

一方、AIは前回の反省をテキストとして参照できても、それが自動的にモデルの性質や重みに反映されるわけではありません。

ルールファイルに追加しても、

- ルールが長くなって見落とす
- 目の前の指示を優先する
- 別の文脈では適用されない
- ルール同士が競合する

といった問題があります。

> **AIの改善は「反省させる」より「失敗できない仕組みに変える」方が有効。**

たとえば、

- コード変更前に必ず計画を出させる
- 変更可能なファイルを限定する
- テストが通らなければ完了扱いにしない
- 並列作業ではディレクトリを分ける
- 設計変更には人間の承認を必要とする

といった、仕組みによる制御が必要です。

---

# 人間が管理すると動くが、自動化の意味が薄れる

失敗を防ぐために、人間がPOとスクラムマスターを担当すると、ある程度は安定します。

```
人間
・タスクを分解
・優先順位を決定
・実装範囲を指定
・設計を承認
・競合を管理
・成果物を検証

AI
・指定された作業を実行
```

ただし、人間がAIの行動を細かく監視すると、今度は、

> **AIを管理するための作業が増えすぎる**

という問題が出ます。

これは、経験の浅い開発者にすべて細かく指示するマイクロマネジメントに近い状態です。

AIによって作業が速くなっても、

```
指示を作る
途中経過を確認する
暴走を止める
競合を解消する
成果物を修正する
```

ための負荷が大きければ、開発全体としては効率化できません。

# 現実的な役割分担

この記事から得られる現実的な形は、次のようになります。

## 人間が担当すること

- 目的を決める
- 優先順位を決める
- 要件を確定する
- 全体設計を決める
- タスクを分割する
- 変更範囲を決める
- 成果物を検証する
- リリースを判断する

## AIに任せること

- コードベースの調査
- 原因候補の列挙
- 実装案の提示
- 限定されたコード修正
- テストコードの作成
- ドキュメント更新
- 定型的なリファクタリング
- レビュー観点の洗い出し

整理すると、

```
人間：方向・境界・判断
AI　：調査・生成・実行
```

という役割分担です。

# AIには「役割」より「明確な単一タスク」を与える

この記事の中でも、特に実務で使いやすい教訓です。

悪い依頼は、

```
あなたは優秀な開発チームです。
このプロジェクトを分析し、
計画、実装、テスト、レビューまで
自律的に進めてください。
```

です。

これでは、AIが判断すべき範囲が広すぎます。

より良い依頼は、

```
この不具合の原因を調査してください。
まだコードは変更しないでください。

次の内容だけを出してください。

1. 原因候補
2. 根拠となるファイル
3. 影響範囲
4. 修正案
5. 推奨案

調査対象は認証処理に限定してください。
```

です。

その後、人間が修正方針を選びます。

```
推奨案で進めてください。

変更可能なファイルは次の3つだけです。
共通認証ロジックの設計は変更しないでください。
実装後に既存テストと追加テストを実行してください。
```

このように、AIの仕事を**小さく、明確に、検証可能に切る**ことが重要です。

# 前の記事とのつながり

先ほどの「AI協業の発注の型」と、ほぼ同じ結論につながります。

```
AI協業の記事
完成品を丸投げしない
↓
結論と構成を確認
↓
小さく意思決定
↓
重要部分を検証


AIスクラムの記事
プロセス全体を丸投げしない
↓
人間が計画と設計を統制
↓
単一タスクをAIに渡す
↓
成果物を検証
```

共通しているのは、

> **AIに自律性を与えすぎるのではなく、仕事の境界を設計することが重要**

という点です。

# 特に覚えておきたい5つ

1. **AIはプロセスより目の前の解決を優先する**  
    「計画だけ」と指示しても、実装に進むことがある。
2. **単一AIの複数人格は、本当のチームではない**  
    役割を分けても、誤った前提やコンテキストを共有している。
3. **AIは局所最適で全体設計を壊すことがある**  
    動くコードを作れても、保守しやすい設計になるとは限らない。
4. **並列化にはファイル競合と管理コストがある**  
    AIを増やせば、単純に開発速度が上がるわけではない。
5. **反省よりも制御の仕組みが必要**  
    ルールを書くだけではなく、権限・範囲・承認・テストで行動を制御する。

# 一言でまとめるなら

> **AIにスクラムをさせるのではなく、人間がスクラムを運営し、その中の明確な作業をAIに実行させる。**

AIは、チームそのものの代替というより、**人間が統制する開発プロセスの中に組み込む高速な実行担当**として考える方が、現在は現実的です。

そしてこの記事の最大の学びは、単に「AIスクラムは失敗した」ということではありません。

> **何をAIに任せて、何を人間が握るべきかという境界線が見えたこと。**

これが一番価値のある部分だと思います。
