## 一番大事な考え方

> **AIに仕事を丸ごと渡すのではなく、人間が「方向」と「判断」を握りながら、AIに作業を進めてもらう。**

AIに、

```
これについて調べて、
比較して、
結論を出して、
資料にまとめて。
```

と一気に頼むと、完成品は速く出ます。

ただし方向がズレていた場合、

```
依頼
 ↓
AIが大量に作業
 ↓
完成品
 ↓
「なんか違う」
 ↓
大量修正
```

となります。

この記事が提案しているのは、これを**小さな意思決定の連続に変えること**です。

```
依頼
 ↓
AI「結論はこれだと思います」
 ↓
人間：方向を確認
 ↓
AI「この構成で進めます」
 ↓
人間：承認
 ↓
AI：調査・作成
 ↓
人間：重要部分だけ検証
 ↓
完成
```

つまり、**完成品ではなく途中の方向性をレビューする**のがポイントです。

---

# ① 最初に本文を書かせない

特に重要なのが、

> **「結論＋構成」→ 承認 → 本文**

という順番です。

いきなり5,000文字のレポートを書かせるのではなく、

```
まず本文を書かないでください。

① 現時点での結論
② その理由
③ レポートの構成案

だけを提示してください。
```

とする。

人間が見るのは、

**「その方向で調べてほしいのか？」**

だけです。

### なぜ重要なのか

AIの作業量が増えるほど、方向転換のコストも大きくなるからです。

```
悪い例

方向性がズレる
↓
5000文字生成
↓
レビュー
↓
全部やり直し
```

ではなく、

```
良い例

方向性を提示
↓
人間が確認
↓
OK
↓
5000文字生成
```

にする。

ソフトウェア開発でいう**設計レビューを実装前に行う**のとかなり近い考え方です。

---

# ② 人間に「全部考えさせない」

ここも重要です。

AIから、

> 「どうしたいですか？」

と聞かれても、人間側の負担が大きい。

そこで、

> **「選択肢＋AIの推奨」を出させる。**

たとえば、

```
通知方式について決めてください。

A. Slack通知 ← 推奨
B. メール通知
C. Slack＋メール

推奨：A

理由：
即時性が高く、現在の社内運用とも
最も相性が良いためです。
```

ここまでAIに整理させる。

人間は、

**AでOK / Bにしたい**

くらいの判断で済みます。

つまり、

> **人間を「ゼロから考える人」ではなく「意思決定する人」にする。**

これが認知負荷を大きく下げます。

---

# ③ 「1回に1つの意思決定」にする

さらに選択肢を出すときも、一気に10個聞かない。

```
① 通知方式は？
② 保存期間は？
③ 権限管理は？
④ UIは？
⑤ エラー時は？
⑥ ログは？
```

これでは結局重い。

そうではなく、

```
AI
「まず通知方式を決めたいです」

人間
「A」

AI
「次に保存期間です」

人間
「B」
```

と進める。

> **AIとの仕事を「巨大な依頼」ではなく「小さな意思決定の連続」にする。**

これはAIエージェントを使うときにもかなり重要な考え方です。

---

# ④ 結論を「正解」ではなく「仮説」として扱う

この記事でもう一つ重要なのが、

> **AIの結論を最初から信用するのではなく、仮説として扱う。**

という考え方です。

たとえばAIが、

> 「Aサービスを採用すべきです」

と結論を出したとします。

全部の調査資料を最初から読む必要はありません。

まず、

```
仮説
「Aサービスが最適」

      ↓

何が決め手？

      ↓

コスト
セキュリティ
既存システムとの連携

      ↓

この3点だけ詳しく確認

      ↓

本当にAが最適？

 YES → 採用
 NO  → 結論を修正
```

と確認する。

これはかなり強い考え方です。

---

# ⑤ 「全部確認する」のではなく、結論に効くところだけ確認する

AI時代には、AIが大量の情報を処理できます。

問題は、

**人間がその全部をレビューできないこと。**

だから、

> **「どこを人間が確認すれば、この結論の妥当性を判断できるか？」**

をAIに考えさせます。

たとえば100ページの調査結果があったとしても、

```
100ページ全部読む
```

ではなく、

```
結論
 ↓
結論を左右する3つのポイント
 ↓
その3点の根拠
 ↓
一次情報・出典
```

まで絞り込む。

人間はそこを重点的に確認します。

つまり、

**AIに「情報を集めさせる」だけでなく、「人間がどこを確認すべきか」まで整理させる。**

---

# この考え方を仕事の流れにすると

この記事の内容は、かなり綺麗に次のサイクルに整理できます。

```
① GOAL
   人間が目的を決める
        ↓
② PLAN
   AIが結論・構成・進め方を提示
        ↓
③ APPROVE
   人間が方向性を承認
        ↓
④ EXECUTE
   AIが調査・分析・作成
        ↓
⑤ VERIFY
   人間が重要ポイントだけ検証
        ↓
⑥ REVISE
   必要ならAIが修正
        ↓
⑦ COMPLETE
   完成
```

人間が特に担当するのは、

**依頼 → 承認 → 検証**

の3ヶ所。

それ以外の重い処理をAIに寄せるという考え方です。

---

# さらに重要なのは「AIを部下のように扱う」ということ

この記事からもう一段抽象化すると、AIへの依頼は**仕事の発注そのもの**だと考えられます。

優秀な人に仕事をお願いするときでも、

```
これ調べといて。
いい感じにまとめて。
```

だけでは良い仕事になりにくい。

本来は、

```
目的はこれ

最終的に決めたいのはこれ

この観点を重視したい

まず調査方針を出して

方向性を確認してから進めよう

判断が必要なら選択肢を持ってきて

最後に根拠を確認させて
```

と依頼するはずです。

AIでも同じです。

> **AIの性能だけではなく「仕事をどう切り出して渡すか」が成果物の品質を左右する。**

```
社内IT

↓
本当の課題を考える
↓
方向性を確認
↓
作る
↓
現場で検証する

↓

↓
方向性を確認
↓

↓

```

どちらも、

> **「作業する能力」より「何を作るべきかを判断する能力」が重要**

というところにつながっています。

---

## 特に覚えておきたい5つ

1. **いきなり完成品を作らせない**  
    まず「結論＋構成」を確認する。
2. **AIに推奨案を出させる**  
    人間はゼロから考えず、選択・修正する。
3. **意思決定を小さくする**  
    「全部決めて」ではなく「ここだけ決めて」。
4. **AIの結論は仮説として扱う**  
    結論そのものではなく、決め手となった根拠を見る。
5. **人間は重要部分だけ深く見る**  
    AIに大量処理を任せ、人間は方向性・判断・検証に集中する。

最終的には、**「AIに何を書かせるか」より「AIとの意思決定プロセスをどう設計するか」**が重要、という記事だと捉えると分かりやすいです。

そしてこれは単なる「プロンプトテクニック」ではなく、**AI時代の仕事の任せ方・レビューの仕方そのもの**の話だと思います。
