# 管理画面の構成・処理フロー・認証設計

## 概要

このシステムの管理画面では、主に次の業務を扱っています。

```text
予約管理
会員管理
料金設定
車両管理
店舗別休日管理
新着情報管理
```

画面URLは次のように分かれています。

|対象|主な画面|
|---|---|
|予約管理|予約一覧・予約詳細|
|会員管理|会員一覧・会員詳細|
|料金設定|車種別料金一覧・日毎料金設定|
|車両管理|車両一覧・車両詳細・車両登録|
|店舗管理|店舗別休日管理|
|通知管理|サイト共通のお知らせバナー管理|

ただし、名称と実際の機能には一部差があります。

```text
店舗管理
└── 店舗マスター管理ではなく、店舗別休日管理

通知管理
└── 会員向け通知配信ではなく、サイト共通バナー管理
```

---

# 管理画面の全体構成

```text
/admin
  │
  ├── dashboard
  │     │
  │     ├── reservations
  │     ├── members
  │     ├── bike-models
  │     │     └── rental-pricing
  │     ├── vehicles
  │     ├── holiday-manager
  │     └── announcements
  │
  └── Next.js Middleware
        └── HTTP Basic認証
```

画面自体は、Next.js MiddlewareによるHTTP Basic認証で保護されています。

一方で、画面から呼び出すAPIは `/api/...` に存在し、多くのAPIには管理者認証がありません。

---

# 最重要ポイント

現在の構造は次のとおりです。

```text
管理画面URL
└── Basic認証あり

管理画面が呼ぶAPI
└── 原則として管理者認証なし
```

そのため、管理画面を開かなくても、API URLを直接呼び出せる可能性があります。

```text
利用者
  │
  ├── /admin/dashboard
  │     └── Basic認証が必要
  │
  └── /api/admin/members
        └── Basic認証を通らない
```

画面を保護することと、APIを保護することは別です。

```text
画面認証
≠
API認証
```

---

# 共通の認証構造

## 管理画面のBasic認証

`/admin` から始まる画面は、MiddlewareによるBasic認証の対象です。

使用する環境変数は次のとおりです。

```text
ADMIN_BASIC_USER
ADMIN_BASIC_PASS
```

認証ヘッダーがない場合：

```text
401 Auth Required
```

認証情報が一致しない場合：

```text
401 Unauthorized
```

---

## APIはMiddlewareの対象外

Middlewareのmatcherでは、`api` が除外されています。

つまり、次のようなURLは管理画面用Basic認証を通りません。

```text
/api/reservations
/api/admin/members
/api/vehicles
/api/vehicle-rental-prices
```

API Route内部で別途認証しなければ、直接アクセス可能です。

---

## Basic認証の既定値

管理画面用のBasic認証情報には、環境変数未設定時の既定値がコード上に存在します。

これは本番環境で環境変数の設定に失敗した場合、既知の認証情報で管理画面へアクセスされるリスクがあります。

本番では次の対応が必要です。

```text
既定値を廃止する
環境変数未設定時は起動失敗にする
十分に長いランダム値を設定する
定期的にローテーションする
```

# レンタル延長

管理画面からの延長処理は次の流れです。

```text
延長日数を入力
      │
      ▼
現在の返却日時から
新しい返却日時を計算
      │
      ▼
対象車両が延長期間中に
空いているか確認
      │
      ▼
PATCH /api/reservations/[reservationId]
      │
      ▼
returnAtを更新
```

管理画面内では決済しません。

延長操作時には、次の確認が表示されます。

```text
延長料金の決済は別途ユーザー側で必要
```

---

## 延長処理の課題

管理者が返却日時だけを延長した場合、次の状態が発生する可能性があります。

```text
予約期間
└── 延長済み

決済
└── 未決済
```

つまり、予約状態と決済状態が分離します。

管理画面上で、少なくとも次の状態管理が必要です。

```text
延長申請済み
延長決済待ち
延長決済済み
延長キャンセル
```

---

# 貸出日時変更

貸出日時を変更すると、元のレンタル時間を維持したまま返却日時も再計算します。

```text
元の貸出時間
10:00 ～ 翌日10:00
24時間

新しい貸出日時
12:00

新しい返却日時
翌日12:00
```

画面から送信する主な値は次のとおりです。

```text
pickupAt
returnAt
```

---

## API側の連動処理

日時変更時には、予約レコードだけでなく車両の日別状態も更新します。

```text
予約日時変更
      │
      ├── 旧期間の車両状態を解除
      ├── 新期間の車両状態をRENTED
      └── 予約日時を更新
```

既存のKEYBOX PINがある場合は、PINの再発行も試みます。

```text
返却日時変更
      │
      ▼
既存PINあり
      │
      ▼
PIN再発行
```

---

## 日時変更のリスク

複数処理が原子的に実行されていない場合、次の不整合が発生する可能性があります。

```text
予約日時更新：成功
車両日別状態更新：失敗
PIN再発行：失敗
```

トランザクションまたは補償処理が必要です。

---

# 割当車両変更

車両変更は、同じ車種内の車両だけを対象にします。

更新する主な項目は次のとおりです。

```text
vehicleCode
vehiclePlate
vehicleModel
vehicleChangeNotified
```

API側では次を確認します。

```text
変更先車両が存在するか
予約期間の全日で利用可能か
```

その後、次の更新を行います。

```text
旧車両
└── 予約期間を解放

新車両
└── 予約期間をRENTED
```

---

## 車両変更の処理フロー

```text
変更先車両を選択
       │
       ▼
同じ車種か確認
       │
       ▼
対象期間が空いているか確認
       │
       ▼
旧車両を解放
       │
       ▼
新車両をRENTED
       │
       ▼
予約情報を更新
```

この処理も複数アイテムを更新するため、途中失敗への対策が必要です。

---

# キャンセル

キャンセルには2種類あります。

```text
返金ありキャンセル
返金なしキャンセル
```

---

## 返金あり

処理内容は次のとおりです。

```text
予約ステータスをキャンセルへ変更
PAY.JP決済番号を確認
決済金額を確認
売上日から180日以内か確認
PAY.JP返金を実行
返金内容をrefundNoteへ保存
```

処理イメージ：

```text
キャンセル操作
      │
      ▼
返金対象確認
      │
      ▼
PAY.JP返金
      │
      ▼
予約ステータス更新
      │
      ▼
refundNote保存
```

---

## 返金なし

返金しない場合は、次の値を送信します。

```text
skipRefund: true
```

この場合はPAY.JP返金処理を行わず、返金なしでキャンセルしたことを `refundNote` に保存します。

---

## キャンセル処理の問題

返金処理と予約更新が別処理の場合、次の不整合が考えられます。

```text
返金成功
予約更新失敗
```

または、

```text
予約キャンセル成功
返金失敗
```

返金状態を予約ステータスとは別に管理する方が安全です。

例：

```text
refund_status:
  NOT_REQUESTED
  PROCESSING
  SUCCEEDED
  FAILED
```

---

# 管理者返却承認

管理者返却承認では、次のAPIへ予約IDを送信します。

```text
POST /api/admin/return-approval
```

主な処理は次のとおりです。

```text
予約を返却済みに更新
車両の貸出可能日を更新
```

---

# 予約管理の認証

現在の認証状況は次のとおりです。

|対象|認証|
|---|---|
|管理画面|Basic認証あり|
|予約一覧GET|管理者認証なし|
|予約詳細GET|管理者認証なし|
|予約更新PATCH|管理者認証なし|
|管理者返却承認POST|管理者認証なし|

顧客が予約を作成する次のAPIは、Cognito認証があります。

```text
POST /api/reservations
```

一方、管理画面が使用するGETやPATCHには同じ認証がありません。

---

# 予約管理の重大リスク

未認証で予約APIへ直接アクセスできる場合、次の操作が可能になる恐れがあります。

```text
全予約一覧取得
個別予約取得
貸出日時変更
返却日時変更
車両変更
予約キャンセル
返金
返却承認
```

個人情報・決済・在庫・物理貸出状態に影響するため、最優先の修正対象です。

```text
住所
```

---

```text
管理画面

/api/admin/members*
└── 管理者認証なし
```

APIパスには `admin` が含まれていますが、パス名だけでは認証になりません。

```text
/api/admin/*
という名前
≠

```

---

# 会員管理のリスク

```text
        │
```

# 車種ごとの料金設定

親画面では、次を並行取得します。

```text
  │
  ├── 車種A
  │     └── 料金設定済み
  │
  └── 車種B
        └── 未設定
```

---

# 日毎料金設定

対象車種について、1日から30日までの日次料金を設定します。

主な機能：

```text
1～30日料金表示
1日料金入力
2日料金入力
3日料金入力
4日料金入力
7日料金入力
中間日の自動計算
クラス料金から初期値生成
日単位の削除
```

---

# 料金設定で利用するAPI

|Method|API|用途|
|---|---|---|
|GET|`/api/bike-classes`|クラス取得|
|GET|`/api/bike-models`|車種取得|
|GET|`/api/vehicle-rental-prices`|車種別料金取得|
|PUT|`/api/vehicle-rental-prices`|料金保存|
|DELETE|`/api/vehicle-rental-prices`|料金削除|

---

# 料金保存

料金保存では、各日について1件ずつPUTします。

例：

```json
{
  "vehicle_type_id": 123,
  "days": 1,
  "price": 10000
}
```

30日分を保存する場合、最大30回のAPI呼び出しが発生します。

```text
1日料金 PUT
2日料金 PUT
3日料金 PUT
...
30日料金 PUT
```

---

# 非トランザクション更新

現在は、一括更新APIではありません。

途中で通信エラーが発生すると、次の状態になる可能性があります。

```text
1日料金：保存済み
2日料金：保存済み
3日料金：保存済み
4日料金：失敗
5日以降：未保存
```

画面上では一括保存に見えても、サーバー側では部分的にしか保存されない可能性があります。

---

# 料金削除

削除時には次の組み合わせを送信します。

```text
vehicle_type_id
days
```

日単位で料金を削除します。

---

# 料金設定の認証

|API|認証|
|---|---|
|バイククラスAPI|なし|
|車種API|なし|
|日次料金GET|なし|
|日次料金PUT|なし|
|日次料金DELETE|なし|

料金の登録・変更・削除にも管理者認証がありません。

---

# 料金設定のリスク

料金APIを直接操作できる場合、次の問題が起こり得ます。

```text
料金を0円に変更
異常に高い料金へ変更
特定日数の料金を削除
予約料金計算を停止させる
```

売上に直接影響するため、高優先度の修正対象です。

---

# 料金設定の改善案

一括更新APIを用意します。

```text
PUT /api/admin/vehicle-rental-prices/:vehicleTypeId
```

入力例：

```json
{
  "prices": [
    {
      "days": 1,
      "price": 10000
    },
    {
      "days": 2,
      "price": 18000
    }
  ]
}
```

サーバー側では、可能な範囲でトランザクションまたは一括書き込みを利用します。

```text
全件検証
   │
   ▼
一括保存
   │
   ├── 全件成功
   └── 全件失敗
```

# 共通管理者認証関数

```text

```

概念例：

```ts
export async function requireAdmin(
  req: NextApiRequest,
  res: NextApiResponse,
) {
  const token = req.cookies.cognito_id_token;

  if (!token) {
    res.status(401).json({
      message: "Unauthorized",
    });

    return null;
  }

  const payload =
    await verifyCognitoIdToken(token);

  const groups =
    payload["cognito:groups"];

  if (
    !Array.isArray(groups) ||
    !groups.includes("Admin")
  ) {
    res.status(403).json({
      message: "Forbidden",
    });

    return null;
  }

  return payload;
}
```

現在の管理画面は、運用に必要な主要機能を幅広く備えています。

```text
② Cognito Groupsによる管理者ロール判定
```

全体としては、**管理機能そのものは充実している一方、画面とAPIの認証境界が分断されており、重要な管理操作をAPI単体では保護できていない状態**です。
