# 予約システムの料金計算と決済の仕組み

## 概要

この予約システムでは、料金計算の中心を予約フロー2の `ReserveFlowStep2` が担当しています。

合計金額は、次の式で計算されます。

```text
合計金額
= レンタル料金
+ 用品料金
+ 補償料金
+ 繁忙期料金
- クーポン割引
```

計算した金額は `sessionStorage` を通じて予約フロー3へ渡され、次の用途にそのまま利用されます。

- 予約確認画面の金額表示
    
- Pay.JPの決済金額
    
- 予約データの決済金額
    
- DynamoDBへ保存する `payment_amount`
    

通常の画面操作では同じ `totalAmount` を使うため、表示額と決済額は一致します。

ただし、サーバー側では料金表を使った再計算をしていません。そのため、正しい料金であることをサーバーが保証する構造にはなっていません。

---

# 料金計算の全体フロー

```text
貸出日時・返却日時を選択
          │
          ▼
利用時間から料金日数を算出
          │
          ▼
車両管理番号からモデルIDを取得
          │
          ▼
車種・日数別料金表を取得
          │
          ▼
用品料金・補償料金を計算
          │
          ▼
繁忙期料金を加算
          │
          ▼
クーポン割引を適用
          │
          ▼
国際料金倍率を適用
          │
          ▼
totalAmountを計算
          │
          ▼
sessionStorageへ保存
          │
          ▼
Pay.JP決済・予約保存
```

---

# 主要な料金項目

|料金項目|現在の仕組み|
|---|---|
|レンタル料金|車種と料金日数に対応する料金表から取得|
|時間料金|なし。利用時間を24時間単位で切り上げる|
|日数料金|料金日数と完全一致する料金表を使用|
|車種料金|車種ごとに別の料金表を持つ|
|店舗料金|なし|
|用品料金|選択した用品と数量から計算|
|補償料金|車両補償・盗難補償の選択から計算|
|繁忙期料金|対象日数×550円|
|クーポン|レンタル料金だけを対象に割引|
|消費税|別計算なし。税込登録されている前提|
|国際料金|対象ユーザーの場合は料金を2倍|

---

# 1. レンタル料金

コード上には、独立した「基本料金」という項目はありません。

例えば、次のような計算ではありません。

```text
基本料金
+ 1日ごとの追加料金
+ 時間超過料金
```

代わりに、車種と料金日数に対応する完成済みの料金を料金表から取得します。

```text
レンタル料金
= 車種IDと日数に登録されたprice
```

料金データは、主に次の組み合わせで管理されています。

```text
vehicle_type_id
days
price
```

例：

|車種ID|日数|料金|
|---|--:|--:|
|model-a|1日|3,980円|
|model-a|2日|7,000円|
|model-a|3日|9,500円|
|model-b|1日|5,500円|

車種や日数によって料金表そのものが異なる設計です。

---

# 2. 料金日数の計算

時間単価による料金計算はありません。

貸出日時と返却日時の差を計算し、24時間単位で切り上げます。

```text
利用時間 = 返却日時 - 貸出日時

料金日数 = ceil（利用時間 ÷ 24時間）
```

最低料金日数は1日です。

|利用時間|料金日数|
|---|--:|
|1時間|1日|
|10時間|1日|
|24時間|1日|
|24時間1分|2日|
|48時間|2日|
|48時間1分|3日|

したがって、数分だけ24時間を超えた場合でも2日料金になります。

---

# 3. 日数別料金

通常は、計算した料金日数と完全に一致する料金レコードを検索します。

```ts
prices.find((item) => item.days === rentalDays)
```

例えば料金日数が3日なら、`days: 3` の料金を使用します。

## 31日を超える場合

31日を超える場合のみ、31日料金から1日あたりの金額を求めます。

```text
1日あたりの金額
= 31日料金 ÷ 31

レンタル料金
= round（1日あたりの金額 × 利用日数）
```

ただし、予約API側には最大31日という期間制限があります。

そのため、画面側には31日超の料金計算が存在していても、通常の予約処理ではAPIに拒否される可能性があります。

---

# 4. 料金未登録時のフォールバック

料金日数に一致する料金が登録されていない場合は、フォールバックとして `3,980円` が使用されます。

```text
料金表に一致する料金なし
          │
          ▼
エラーメッセージを表示
          │
          ▼
3,980円を仮の料金として使用
```

この実装では、料金設定が見つからなくても金額が0円にはなりません。

一方で、正しい料金が取得できていない状態でも、フォールバック金額で決済へ進める可能性があります。

そのため、料金未登録時は決済を停止する設計の方が安全です。

---

# 5. 車種料金の決定方法

車種料金は、次の2段階で決まります。

## ① 車両管理番号からモデルIDを取得

```text
managementNumber
        │
        ▼
GET /api/vehicles/{managementNumber}
        │
        ▼
modelId
```

## ② モデルIDで料金表を取得

```text
modelId
   │
   ▼
GET /api/vehicle-rental-prices
    ?vehicle_type_id={modelId}
   │
   ▼
車種・日数別料金
```

つまり、料金の決定経路は次のとおりです。

```text
車両管理番号
↓
車両モデルID
↓
車種別料金表
↓
利用日数に一致する料金
```

独立した「車種追加料金」を加算するのではなく、車種ごとに料金表全体が異なります。

---

# 6. 店舗料金

現在、店舗ごとの料金計算はありません。

店舗情報は次の用途に使用されています。

- 予約画面への表示
    
- 予約データへの保存
    
- 空き状況の確認
    
- Pay.JPの決済説明文
    
- Pay.JPのメタデータ
    
- 店舗固有処理の判定
    

ただし、合計金額の計算には店舗名が含まれていません。

そのため、同じ車種・日程・オプションであれば、店舗が異なっても料金は同じです。

```text
足立小台店
三ノ輪店
その他の店舗

↓

同じ車種・日数なら同じ料金
```

---

# 7. 用品料金

用品料金は、利用期間の区分と選択数量に応じて計算されます。

用品には、主に次のような種類があります。

- ハーフキャップ
    
- ジェットヘルメット
    
- ブランドヘルメット
    
- グローブ
    

用品の料金期間は、次のような区分で管理されています。

```text
24時間
2日
4日
1週間
2週間
1か月
```

レンタル期間に応じた用品料金を選び、数量を掛けて合計します。

```text
用品料金
= 各用品の期間料金 × 数量
```

---

# 8. 補償料金

補償には主に次の2種類があります。

- 車両補償
    
- 盗難補償
    

初期状態では、どちらも加入状態になっています。

```text
車両補償：加入
盗難補償：加入
```

選択内容に応じて補償料金を合計します。

```text
補償料金
= 車両補償料金
+ 盗難補償料金
```

補償料金もレンタル料金とは別に合計金額へ加算されます。

---

# 9. 繁忙期料金

繁忙期料金は、繁忙期として登録されている利用日数に応じて加算されます。

```text
繁忙期料金
= 繁忙期対象日数 × 550円
```

例：

|利用期間|繁忙期対象日数|追加料金|
|---|--:|--:|
|3日間|0日|0円|
|3日間|1日|550円|
|3日間|2日|1,100円|
|5日間|5日|2,750円|

## 繁忙期日の取得

貸出月から返却月まで、月単位でAPIを呼び出します。

```text
GET /api/high-season?month=YYYY-MM
```

APIから取得した日付のうち、`isHighSeason: true` の日が対象です。

画面上にはゴールデンウィーク、お盆、年末年始などの説明がありますが、実際の判定は固定の日付ではありません。

管理データとして登録された繁忙期日が基準です。

---

# 10. クーポン

クーポン処理では、入力コードに一致するクーポンルールを検索します。

主な処理関数は次のとおりです。

```text
handleApplyCoupon
calculateCouponDiscount
```

## 適用条件

クーポンを利用するには、次の条件を満たす必要があります。

1. 入力コードとクーポンコードが一致している
    
2. クーポンの利用期間とレンタル期間が重なっている
    
3. 貸出日・返却日が正常である
    
4. 対象車両クラスに含まれている
    

対象車両クラスが未指定の場合は、全車両クラスが対象です。

---

# クーポンの割引対象

クーポンが割り引くのは、レンタル料金のみです。

```text
割引対象
└── レンタル料金

割引対象外
├── 用品料金
├── 補償料金
└── 繁忙期料金
```

したがって、クーポンでレンタル料金が0円になっても、用品や補償などの料金は残ります。

---

# 定額クーポン

定額クーポンでは、クーポンの有効期間がレンタル期間の一部だけに重なる場合、期間に応じて割引額を按分します。

```text
適用割引額
= round(
    設定割引額
    × クーポン有効日数
    ÷ 全レンタル日数
  )
```

例：

```text
レンタル期間：4日
クーポン有効期間：2日
クーポン額：2,000円
```

```text
適用割引額
= 2,000円 × 2日 ÷ 4日
= 1,000円
```

割引額はレンタル料金を超えないよう制限されます。

---

# 割引率クーポン

割引率クーポンは、対象レンタル料金に割引率を掛けます。

```text
割引額
= round（対象レンタル料金 × 割引率 ÷ 100）
```

例：

```text
対象レンタル料金：10,000円
割引率：20%
```

```text
割引額
= 10,000円 × 20%
= 2,000円
```

こちらも、割引額がレンタル料金を超えないように制限されます。

---

# 11. 消費税

コード上には、消費税を個別計算する処理はありません。

次のような処理は確認されていません。

```text
税抜金額 × 1.1
消費税額の計算
税率定数
税額の端数処理
```

画面には「合計（税込）」と表示されます。

そのため、料金データはあらかじめ税込金額で登録されている前提です。

```text
料金テーブルのprice
用品料金
補償料金
繁忙期料金
クーポン金額

↓

すべて税込金額として扱う
```

---

# 12. 国際料金倍率

通常の合計計算に加えて、利用者のロケールやユーザー属性に応じた料金倍率があります。

```text
日本向け料金：1倍
国際料金：2倍
```

倍率は主に次の料金へ反映されます。

- レンタル料金
    
- 繁忙期料金
    
- 用品料金
    
- 補償料金
    

各料金を倍率で調整し、四捨五入したうえで合計します。

```text
調整後料金
= round（通常料金 × 料金倍率）
```

日本語ページを表示していても、ユーザー情報が国際利用者として判定される場合は、2倍料金になる可能性があります。

---

# 13. 合計金額の計算

最終的な合計金額は、予約フロー2で計算されます。

```text
合計金額
= 調整後レンタル料金
+ 調整後用品料金
+ 調整後補償料金
+ 調整後繁忙期料金
- クーポン割引額
```

コード上では `totalAmount` として管理されます。

```ts
const totalAmount =
  adjustedRentalFee +
  accessoryTotal +
  protectionTotal +
  adjustedHighSeasonFee -
  couponDiscount;
```

画面には次の内訳が表示されます。

- バイクレンタル料金
    
- 用品オプション料金
    
- 補償オプション料金
    
- ハイシーズン追加料金
    
- クーポン割引
    
- 合計（税込）
    

---

# 14. 予約フロー2から3への受け渡し

予約フロー2で計算した料金情報は、`sessionStorage` に保存されます。

使用するキーは次のとおりです。

```text
reserve-flow-step3-payload
```

保存される主な情報は次のとおりです。

```text
店舗
車種
車両管理番号
貸出日時
返却日時
クーポンコード
クーポン割引額
用品料金
用品選択
補償料金
補償選択
合計金額
```

予約フロー3へはURLクエリではなく、ブラウザ内の `sessionStorage` を使って渡します。

---

# 15. 予約フロー3での金額利用

予約フロー3では、`sessionStorage` からデータを読み込みます。

```text
sessionStorage
        │
        ▼
JSONとして解析
        │
        ▼
payload.totalAmount
        │
        ▼
画面のtotalAmount
```

ここでは料金を再計算していません。

予約フロー2で計算した `totalAmount` をそのまま使用します。

---

# 16. Pay.JP決済

予約フロー3では、同じ `totalAmount` をPay.JPへ送信します。

```text
POST /api/payments/payjp
```

主な送信内容は次のとおりです。

```text
token
amount
description
email
metadata
```

金額部分は次のようになります。

```ts
amount: totalAmount
```

サーバー側の決済APIも、受け取った `amount` をそのままPay.JPへ渡します。

```text
ブラウザのtotalAmount
        │
        ▼
決済APIのbody.amount
        │
        ▼
Pay.JPのamount
```

通貨は日本円で、決済は即時売上として実行されます。

---

# 17. 予約データへの保存

Pay.JPで決済が成功すると、予約保存APIを呼び出します。

```text
POST /api/reservations
```

このときも、同じ `totalAmount` を `paymentAmount` として送信します。

```text
totalAmount
     │
     ▼
paymentAmount
     │
     ▼
createReservation
     │
     ▼
DynamoDBのpayment_amount
```

したがって、通常の操作では次の金額がすべて同じになります。

1. 予約フロー2の表示金額
    
2. 予約フロー3の表示金額
    
3. Pay.JPの決済金額
    
4. 予約APIへ送る金額
    
5. DynamoDBへ保存する金額
    

---

# 表示額と決済額が一致する理由

通常の操作では、同じ `totalAmount` を最後まで引き継いでいます。

```text
ReserveFlowStep2
      │
      │ totalAmount
      ▼
sessionStorage
      │
      ▼
ReserveFlowStep3
      │
      ├── 画面表示
      ├── Pay.JP Checkout
      ├── 決済API
      └── 予約保存API
```

それぞれが別々に料金計算しているわけではないため、画面間で計算結果がずれる可能性は低くなっています。

---

# サーバー側で保証されていないこと

現在の決済APIや予約APIでは、次の再計算をしていません。

- 車種別料金の取得
    
- 利用日数の再計算
    
- 料金表との照合
    
- 用品料金の再計算
    
- 補償料金の再計算
    
- 繁忙期料金の再計算
    
- クーポンの再検証
    
- 国際料金倍率の再判定
    
- 消費税の確認
    

つまり、サーバーはクライアントから送信された金額を信用しています。

```text
クライアントが送った金額
          │
          ▼
そのままPay.JPへ送信
          │
          ▼
同じ金額を予約データへ保存
```

---

# 想定される問題

## 1. sessionStorageの改ざん

ブラウザの開発者ツールなどから、`totalAmount` を書き換えられる可能性があります。

```text
本来の料金：10,000円

↓

sessionStorageを変更

↓

送信金額：1,000円
```

サーバー側で正しい料金を再計算しないため、改ざんされた金額を検知できない可能性があります。

---

## 2. 料金APIの直接操作

決済APIへ直接リクエストを送信し、任意の `amount` を指定される可能性があります。

フロント画面を通らなくても、認証情報とPay.JPトークンがあれば、不正な金額を送信できる余地があります。

---

## 3. クーポンの不正利用

クーポンの適用可否や割引額は、予約フロー2で計算されます。

予約保存時にサーバーで再検証しないため、次の値を改ざんされる可能性があります。

```text
couponCode
couponDiscount
paymentAmount
```

---

## 4. 料金未設定時の決済

料金表に該当するレコードがなくても、フォールバックの3,980円を使用します。

そのため、本来は料金設定ミスとして停止すべき状態でも、決済へ進む可能性があります。

---

## 5. 国際料金判定の不一致

国際料金倍率はフロント側で判定されています。

サーバー側でユーザー属性を確認して再計算しないため、国際料金対象者が通常料金で決済できる可能性があります。

---

## 6. Pay.JPレスポンス金額との照合不足

Pay.JPからは、実際に決済した金額が返されます。

しかし、フロント側では主に次の値だけを利用しています。

```text
chargeId
paidAt
```

Pay.JPが返した `amount` と、予約データへ保存する `paymentAmount` の一致確認は行っていません。

---

# 改善案

## 1. サーバー側で料金を再計算する

決済APIまたは専用の料金計算APIで、正しい料金を算出します。

```text
クライアント
│
│ 車両・日時・オプションを送信
▼
サーバー
│
├── 料金表取得
├── 日数計算
├── 繁忙期計算
├── クーポン検証
├── 用品料金計算
├── 補償料金計算
└── 国際料金判定
│
▼
正しいtotalAmount
```

クライアントからは合計金額を信用して受け取らず、選択内容だけを受け取る形が安全です。

---

## 2. 決済APIで正規料金を使用する

現在は次のようになっています。

```text
クライアントのamount
↓
Pay.JP
```

改善後は次のようにします。

```text
車両・日時・オプション
↓
サーバーで料金計算
↓
正規のamount
↓
Pay.JP
```

---

## 3. 料金計算処理を共通化する

料金計算を `lib` などに共通関数として切り出します。

例：

```text
lib/calculateReservationPrice.ts
```

```ts
calculateReservationPrice({
  vehicleModelId,
  pickupAt,
  returnAt,
  accessories,
  protections,
  couponCode,
  memberId,
});
```

フロントとサーバーで共通のルールを利用できれば、計算ロジックのずれを減らせます。

ただし、最終的な決済金額は必ずサーバー側の結果を正とします。

---

## 4. 料金未登録時は決済を止める

料金が見つからない場合は、フォールバック料金で進めるのではなく、エラーとして決済を停止します。

```text
料金設定なし
↓
決済不可
↓
管理者へ通知
```

---

## 5. Pay.JP決済結果を照合する

Pay.JPが返した金額と、サーバーが計算した正規料金を比較します。

```text
Pay.JPのcharge.amount
        =
サーバー計算のtotalAmount
```

一致しない場合は、予約保存を行わず、返金またはエラー処理へ進めます。

# 現在の設計の良い点

## 1. 画面間で金額がずれにくい

同じ `totalAmount` を利用するため、フロント画面同士では金額が一致しやすい設計です。

## 2. 料金項目が分かれている

次の料金が個別に管理されています。

- レンタル料金
    
- 用品料金
    
- 補償料金
    
- 繁忙期料金
    
- クーポン割引
    

画面上で内訳を表示しやすい構造です。

## 3. 車種別料金に対応している

車両管理番号からモデルIDを取得し、車種ごとの料金表を利用しています。

新しい車種を追加する場合も、料金表を登録することで対応できます。

## 4. 繁忙期を管理データで変更できる

繁忙期をコードに直接書かず、APIで登録された日付から取得しています。

年ごとのゴールデンウィークや年末年始の変更に対応しやすい設計です。

## 5. クーポンの期間と車両クラスを確認している

単純なコード一致だけではなく、期間や対象車両クラスも確認しています。

# 最終整理

現在の料金計算は、予約フロー2の `ReserveFlowStep2` に集中しています。

```text
レンタル料金
+ 用品料金
+ 補償料金
+ 繁忙期料金
- クーポン割引
= totalAmount
```

この `totalAmount` を予約フロー3へ渡し、画面表示・Pay.JP決済・予約保存に利用しています。

そのため、通常の画面操作では表示金額と決済金額は一致します。

一方で、サーバー側では正しい料金を再計算していません。

現在の状態を整理すると次のとおりです。

|確認項目|評価|
|---|---|
|画面間の金額一致|同じ変数を使うため一致しやすい|
|Pay.JP決済額との一致|同じクライアント値を送るため通常は一致|
|料金表との一致|決済時に再確認していない|
|クーポンの再検証|サーバー側では行っていない|
|国際料金の再検証|サーバー側では行っていない|
|改ざん耐性|十分ではない|
|Pay.JP結果との照合|行っていない|
|料金未設定時の制御|フォールバック金額で進む可能性あり|

今後は、クライアントから送られた `totalAmount` を信用せず、サーバー側で車種・日数・用品・補償・繁忙期・クーポン・ユーザー属性を基に正規料金を再計算する設計が望ましいです。
