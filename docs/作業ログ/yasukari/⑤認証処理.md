# Cognito認証とAPI認可の仕組み

## 概要

このシステムでは、一般ユーザーのログインに **Amazon Cognito Hosted UI** を使用しています。

アプリケーション自身がパスワードを受け取るのではなく、ユーザー認証をCognitoへ委譲する設計です。

ログイン成功後は、Cognitoから返された次のトークンをブラウザのHttpOnly Cookieへ保存します。

- ID Token
    
- Access Token
    

APIを利用するときは、Cookieに保存されたID Tokenをサーバー側で検証し、検証済みJWTの `sub` をユーザーIDとして利用します。

```text
ログイン画面
    │
    ▼
Cognito Hosted UI
    │
    ▼
ID Token・Access Tokenを取得
    │
    ▼
HttpOnly Cookieへ保存
    │
    ▼
APIリクエスト
    │
    ▼
JWT署名・Claimを検証
    │
    ▼
subをユーザーIDとして処理
```

認証の基本的な仕組みは実装されていますが、APIごとの認可にばらつきがあります。

特に、次のAPIは重大な注意が必要です。

- 全予約一覧API
    
- 予約ID指定の取得・更新API
    
- 管理画面API
    
- 予約延長通知API
    
- 返金API
    

---

# 認証フローの全体像

```text
[1] ログインボタンを押す
        │
        ▼
[2] OAuth stateを生成
        │
        ▼
[3] Cognito Hosted UIへ移動
        │
        ▼
[4] Cognitoで本人認証
        │
        ▼
[5] Callback URLへトークンを返す
        │
        ▼
[6] stateを照合
        │
        ▼
[7] トークン保存APIを呼ぶ
        │
        ▼
[8] HttpOnly Cookieへ保存
        │
        ▼
[9] APIがID Tokenを検証
        │
        ▼
[10] JWTのsubでユーザーを識別
```

---

# 1. ログイン開始

ユーザーがログインボタンを押すと、ブラウザ側でOAuthの `state` を生成します。

生成された値は、次のキーで `sessionStorage` に保存されます。

```text
cognito_oauth_state
```

ログイン画面では、おおむね次の処理を行います。

```text
以前の登録状態を削除
        │
        ▼
ランダムなstateを生成
        │
        ▼
sessionStorageへ保存
        │
        ▼
Cognito認証URLを作成
        │
        ▼
Cognito Hosted UIへ移動
```

`state` は、ログインを開始したブラウザとCallbackの対応を確認するために利用されます。

---

# 2. Cognito Hosted UIへの遷移

Cognitoの認証URLには、主に次の情報を設定します。

```text
client_id
response_type
scope
redirect_uri
state
lang
```

現在の `response_type` は次のとおりです。

```text
response_type=token
```

これは **Implicit Flow** と呼ばれる方式です。

認証成功後、ID TokenとAccess Tokenがブラウザへ直接返されます。

---

## 使用しているスコープ

主なスコープは次のとおりです。

```text
openid
email
phone
profile
aws.cognito.signin.user.admin
```

それぞれの役割は次のようになります。

|スコープ|主な用途|
|---|---|
|`openid`|OpenID Connectを利用する|
|`email`|メールアドレス情報を取得する|
|`phone`|電話番号情報を取得する|
|`profile`|プロフィール情報を取得する|
|`aws.cognito.signin.user.admin`|CognitoのGetUserなどを利用する|

---

# 3. Cognito側での本人認証

ブラウザはCognitoの次のようなURLへ移動します。

```text
/oauth2/authorize
```

Cognito Hosted UI側で、ユーザーは次のような方法で認証します。

- メールアドレスとパスワード
    
- Cognitoに設定されたソーシャルログイン
    
- ユーザープールに設定された認証方式
    

アプリケーション側は、ユーザーのパスワードを直接受け取りません。

```text
ユーザー
    │
    │ パスワード
    ▼
Cognito

アプリ
    │
    └── パスワードを保持しない
```

---

# 4. Callback URL

認証成功後、CognitoはアプリケーションのCallback画面へ戻します。

Callback URLは次の形式です。

```text
/auth/callback
```

デフォルトでは、次のURLが使用されます。

```text
https://yasukari.com/auth/callback
```

---

# 5. URLフラグメントからトークンを取得

Implicit Flowでは、トークンがURLのフラグメント部分に含まれます。

例：

```text
/auth/callback
#id_token=...
&access_token=...
&expires_in=3600
&state=...
```

Callback画面は `window.location.hash` を解析し、次の情報を取得します。

- `id_token`
    
- `access_token`
    
- `expires_in`
    
- `state`
    
- エラー情報
    

ID Tokenが存在しない場合は、ログイン失敗として扱います。

Access Tokenについては、コード上は必須ではありません。

---

# 6. OAuth stateの照合

Callback画面では、Cognitoから返された `state` と、ログイン開始時に保存した値を比較します。

```text
Cognitoから返されたstate
            =
sessionStorageのstate
```

次の場合は認証エラーになります。

- Callbackに `state` がない
    
- `sessionStorage` にstateがない
    
- 2つのstateが一致しない
    

一致しない場合は、保存済みのstateを削除して処理を停止します。

---

## stateの役割

`state` は、悪意あるサイトなどから勝手に認証処理を開始されることを防ぐための仕組みです。

簡単に表すと、次の確認です。

```text
このログイン結果は、
本当にこのブラウザが開始したログインか
```

これはOAuthログインにおけるCSRF対策の一つです。

---

# 7. トークン保存API

stateの照合に成功すると、Callback画面はトークン保存APIを呼び出します。

```text
POST /api/auth/store-tokens
```

送信内容は次のようなJSONです。

```json
{
  "idToken": "...",
  "accessToken": "...",
  "expiresIn": 3600
}
```

リクエストでは、次の指定が使用されています。

```text
credentials: include
```

これにより、APIレスポンスのCookieをブラウザが保存できます。

---

# 8. HttpOnly Cookieへの保存

トークンは、次のCookie名で保存されます。

|用途|Cookie名|
|---|---|
|ID Token|`cognito_id_token`|
|Access Token|`cognito_access_token`|

Cookieには、主に次の属性が設定されます。

```text
Path=/
HttpOnly
SameSite=Lax
Max-Age=<有効秒数>
Expires=<有効期限>
Secure（本番環境のみ）
```

---

## HttpOnlyとは

`HttpOnly` を指定したCookieは、通常のブラウザJavaScriptから読み取れません。

```js
document.cookie
```

を使っても、HttpOnly Cookieの値は取得できません。

これにより、XSSなどでJavaScriptが実行された場合でも、トークンを直接盗まれにくくなります。

---

## Secureとは

`Secure` が設定されたCookieは、HTTPS通信でのみ送信されます。

現在は本番環境でのみ `Secure` が設定されます。

```text
本番環境
└── Secureあり

開発環境
└── Secureなし
```

---

## SameSite=Laxとは

`SameSite=Lax` は、他サイトからの一部のクロスサイトリクエストにCookieを送らないための設定です。

CSRFのリスクを減らす効果があります。

ただし、これだけですべてのCSRFを防げるわけではありません。

---

# 9. トークン保存時の問題

`/api/auth/store-tokens` では、受け取ったID Tokenを保存する前にJWT検証を行っていません。

主に確認しているのは次の内容です。

- POSTリクエストである
    
- ID Tokenが空ではない
    
- `expiresIn` が正数である
    

一方、次の確認は保存時点では行っていません。

```text
JWT署名
issuer
audience
有効期限
token_use
```

そのため、APIへ任意の文字列を送信すると、その値自体はCookieへ保存される可能性があります。

ただし、認証が必要なAPIでは後からJWT検証を行うため、不正な文字列を保存しただけでログイン済みとして扱われるわけではありません。

---

## 改善案

Cookieへ保存する前に、サーバー側でID Tokenを検証します。

```text
CallbackからID Tokenを受信
        │
        ▼
JWT署名を検証
        │
        ▼
issuer・audience・expを検証
        │
        ▼
正常な場合だけCookieへ保存
```

これにより、不正な値をCookieへ保存すること自体を防げます。

---

# 10. ログイン後の画面遷移

Cookie保存成功後は、次の画面へ移動します。

```text
/mypage/profile-setup?fromLogin=1
```

新規登録から来た場合は、次のパラメーターも追加されます。

```text
fromSignup=1
```

遷移には、クライアント側の画面切り替えではなく、フルページ遷移を使用しています。

これは、次のページ読み込み時にCookieを確実に送信するための設計です。

---

# 11. Refresh Token

現在の認証フローでは、Refresh Tokenを保存していません。

保存しているのは次の2つです。

```text
ID Token
Access Token
```

これは `response_type=token` のImplicit Flowを使っているためです。

---

## Refresh Tokenとは

Refresh Tokenは、ID TokenやAccess Tokenの有効期限が切れた際に、新しいトークンを取得するために利用します。

```text
ID Token期限切れ
        │
        ▼
Refresh Tokenを送信
        │
        ▼
新しいID Tokenを取得
```

現在はRefresh Tokenがないため、Cookieの期限が切れた場合は基本的に再ログインが必要です。

---

# 12. ログアウト

ログアウトAPIは、次のCookieを削除します。

- `cognito_id_token`
    
- `cognito_access_token`
    

削除時には、次の値を設定します。

```text
Max-Age=0
Expires=過去の日付
```

これにより、ブラウザからCookieが削除されます。

---

## JavaScriptからのCookie削除

ログアウト画面側でも `document.cookie` による削除を試しています。

しかし、認証Cookieは `HttpOnly` です。

そのため、ブラウザJavaScriptからの削除には依存できません。

確実なログアウト処理は、APIレスポンスの `Set-Cookie` による削除です。

---

# 13. APIでのID Token取得

認証が必要なAPIは、リクエストCookieからID Tokenを取得します。

概念的には次の処理です。

```ts
const token = req.cookies?.cognito_id_token;
const payload = await verifyCognitoIdToken(token);

if (!payload?.sub) {
  return res.status(401).json({
    message: "Unauthorized",
  });
}
```

認証に成功すると、JWTの `sub` をユーザーIDとして利用します。

---

# 14. JWTとは

JWTは、認証結果やユーザー情報を含むトークン形式です。

JWTは次の3つの部分で構成されます。

```text
Header.Payload.Signature
```

例：

```text
eyJhbGciOiJSUzI1NiIs...
.
eyJzdWIiOiIxMjM0NTY3ODkwIiw...
.
署名データ
```

---

## Header

主に次の情報が入ります。

```text
alg
kid
```

- `alg`：署名アルゴリズム
    
- `kid`：署名検証に使う公開鍵の識別子
    

---

## Payload

ユーザー情報や有効期限などが入ります。

主なClaimは次のとおりです。

```text
sub
aud
iss
exp
token_use
email
```

---

## Signature

JWTがCognitoによって発行され、その後改ざんされていないことを確認するための署名です。

---

# 15. Cognito JWKS

JWTの署名検証には、CognitoのJWKSを使用します。

JWKSは、JWT署名を検証する公開鍵の一覧です。

取得URLは次の形式です。

```text
https://cognito-idp.<region>.amazonaws.com/
<userPoolId>/.well-known/jwks.json
```

取得したJWKSは、プロセス内で1時間キャッシュされます。

```text
最初のJWT検証
    │
    ▼
CognitoからJWKS取得
    │
    ▼
1時間キャッシュ
    │
    ▼
以降はキャッシュを利用
```

---

# 16. JWT署名検証

JWTのヘッダーについて、まず次を確認します。

```text
alg === RS256
kidが存在する
```

その後、JWKSの中から同じ `kid` を持つ公開鍵を取得します。

```text
JWTのkid
    │
    ▼
JWKSから対応する公開鍵を探す
    │
    ▼
RSA SHA-256で署名検証
```

署名が一致しない場合は、不正なJWTとして拒否します。

---

# 17. JWT Claimの検証

署名検証に成功した後、さらにJWTの中身を確認します。

|Claim|確認内容|
|---|---|
|`token_use`|`id` であること|
|`aud`|Cognito Client IDと一致すること|
|`iss`|対象ユーザープールのissuerであること|
|`exp`|有効期限が切れていないこと|

すべて正常な場合だけ、JWT PayloadをAPI処理に利用します。

---

# 18. subをユーザーIDとして利用

JWTの `sub` は、Cognitoユーザーを一意に識別するIDです。

```text
payload.sub
```

メールアドレスは変更される可能性がありますが、`sub` は基本的に同じユーザーを識別し続けます。

そのため、サーバー側では次のように利用しています。

```text
Cognito JWT
    │
    ▼
payload.sub
    │
    ▼
会員ID・予約所有者ID
```

---

# 19. ID TokenとAccess Tokenの違い

## ID Token

ID Tokenは、ログインユーザーが誰かをアプリケーションへ伝えるためのトークンです。

主に次の情報を含みます。

- ユーザーID
    
- メールアドレス
    
- ユーザー属性
    
- 発行元
    
- 有効期限
    

このシステムの自前APIでは、主にID Tokenを利用してユーザーを識別します。

---

## Access Token

Access Tokenは、CognitoのユーザーAPIなどを利用するためのトークンです。

例えば次の処理で使います。

```text
Cognito GetUser
Cognito UpdateUserAttributes
```

Access Tokenはアプリ側で署名検証するのではなく、Cognitoへ渡し、Cognito側が有効性を確認する処理があります。

---

# 20. MiddlewareでのJWT利用

MiddlewareでもID Tokenを読み取っています。

ただし、MiddlewareではJWTの署名検証を行っていません。

JWT PayloadをBase64URLデコードし、主に次の値を確認しています。

```text
custom:locale
```

その値を使って、英語ページなどへリダイレクトします。

---

## 重要な点

MiddlewareでのJWT解析は、認証処理ではありません。

```text
署名検証あり
└── 認証判断に利用可能

単なるBase64デコード
└── 認証判断には利用不可
```

JWTのPayload部分は誰でも作成できるため、署名検証せずに権限判断へ使用してはいけません。

現在は言語切り替えに使っているだけなので、認証とは分離して考える必要があります。

---

# 21. 認証とは

認証は、次の確認です。

> このリクエストを送ったユーザーは誰か。

このシステムでは、次の処理が認証に相当します。

```text
ID Token Cookieを取得
        │
        ▼
Cognito公開鍵でJWT検証
        │
        ▼
payload.subを取得
```

JWTが正しく、`sub` が存在すれば、ログインユーザーを識別できます。

---

# 22. 認可とは

認可は、次の確認です。

> 認証されたユーザーが、このデータを操作してよいか。

例えば、ログイン済みだからといって、すべての予約を変更してよいわけではありません。

```text
認証
└── 丸山さんであることを確認

認可
└── この予約が丸山さんの予約か確認
```

---

# 23. 安全な認可の例

本人予約一覧APIでは、リクエストからユーザーIDを受け取りません。

JWTを検証して得た `sub` をそのまま検索条件に使います。

```text
JWTのsub
    │
    ▼
fetchReservationsByMember(sub)
```

この方式では、クライアントが別ユーザーのIDを指定できません。

---

## 予約作成

予約作成でも、予約所有者をクライアントの入力値から決めていません。

サーバー側で次のように固定します。

```text
memberId = payload.sub
```

これにより、別ユーザーのIDを指定して予約を作成することを防いでいます。

---

# 24. 全予約一覧APIの問題

`GET /api/reservations` は、JWT検証を行わず、全予約を取得します。

```text
未認証リクエスト
        │
        ▼
GET /api/reservations
        │
        ▼
fetchAllReservations()
```

この状態では、ログインしていない利用者でも全予約情報を取得できる可能性があります。

これは、個別予約の所有者チェック以前に、一覧API自体が公開されている問題です。

---

## 改善案

全予約一覧は管理者専用にします。

```text
一般ユーザー
└── GET /api/reservations/me

管理者
└── GET /api/admin/reservations
```

一般ユーザーには、自分の予約だけを返すAPIを利用させます。

---

# 25. 予約詳細APIの問題

`/api/reservations/[reservationId]` のGETでは、予約IDを受け取った後、認証せずに予約データを返します。

```text
予約IDを指定
    │
    ▼
認証なし
    │
    ▼
予約情報を返す
```

予約IDを知っている利用者が、他人の予約情報を取得できる可能性があります。

---

## 必要な処理

```text
1. ID Tokenを検証
2. payload.subを取得
3. 予約データを取得
4. reservation.memberIdと比較
5. 一致しなければ403
```

概念的には次のようになります。

```ts
if (
  reservation.memberId !== payload.sub &&
  !isAdmin(payload)
) {
  return res.status(403).json({
    message: "Forbidden",
  });
}
```

---

# 26. 予約更新APIの問題

同じ `/api/reservations/[reservationId]` のPATCHも、認証・所有者確認なしで更新処理を実行します。

PATCHには、次のような重大な処理が含まれる可能性があります。

- 予約日時変更
    
- 車両状態変更
    
- キャンセル
    
- PAY.JP返金
    
- 予約ステータス変更
    

```text
予約IDを知っている
        │
        ▼
PATCHを送信
        │
        ▼
予約変更・返金
```

認証・認可がなければ、他人の予約に対して操作できる可能性があります。

決済にも関わるため、最優先で対策が必要です。

---

# 27. 延長通知APIの問題

予約延長通知APIでは、ID Tokenを検証しています。

したがって、未ログインユーザーは拒否されます。

一方で、指定された予約がログインユーザー本人のものかは確認していません。

```text
ログイン済み
    │
    ▼
任意のreservationIdを指定
    │
    ▼
予約を取得して通知
```

必要なのは、次の確認です。

```text
reservation.memberId === payload.sub
```

認証されているだけでは不十分で、対象予約に対する認可が必要です。

---

# 28. 返金APIの問題

返金APIでもID Tokenを検証しているため、ログインは必要です。

しかし、リクエスト本文の `chargeId` が、ログインユーザーの予約に属しているかは確認していません。

```text
ログインユーザー
    │
    ▼
任意のchargeIdを送信
    │
    ▼
PAY.JP返金処理
```

そのため、他人のCharge IDを知っている場合、その決済を返金できる可能性があります。

---

## 安全な返金フロー

クライアントからCharge IDを直接受け取って信用するのではなく、予約IDを受け取ります。

```text
予約IDを受信
    │
    ▼
予約データを取得
    │
    ▼
reservation.memberIdを確認
    │
    ▼
予約内のchargeIdを取得
    │
    ▼
PAY.JP返金
```

これにより、ログインユーザーと返金対象をサーバー側で関連付けられます。

---

# 29. 管理画面の認証

管理画面ページは、Next.js MiddlewareでHTTP Basic認証されています。

対象は次のような画面です。

```text
/admin
/admin/dashboard
/admin/reservations
```

Middlewareは `Authorization` ヘッダーを読み、環境変数の値と比較します。

```text
ADMIN_BASIC_USER
ADMIN_BASIC_PASS
```

一致しない場合は、次のレスポンスを返します。

```text
401 Unauthorized
WWW-Authenticate: Basic
```

# 30. Basic認証の特徴

現在の管理者判定は、次の条件だけです。

```text
共通ユーザー名・パスワードを知っている
```

Cognitoのユーザー単位の管理者権限ではありません。

そのため、次の機能はありません。

- 管理者ごとのアカウント
    
- 管理者ごとの操作履歴
    
- ロール別権限
    
- 退職者だけを無効化
    
- 多要素認証
    
- Cognito Groupsによる管理
    

---

# 31. 管理画面APIの重大な問題

Middlewareのmatcherは、`/api` を対象外にしています。

```text
matcher: ['/((?!api|wait).*)']
```

そのため、次のようになります。

|対象|Basic認証|
|---|---|
|`/admin/...` の画面|対象|
|`/api/admin/...`|対象外|

管理画面のページはBasic認証で保護されていますが、管理画面から呼び出すAPIは保護されていない可能性があります。

```text
ブラウザで管理画面を開く
└── Basic認証あり

API URLを直接呼ぶ
└── 認証なし
```

これは、管理画面認証における最重要の問題です。

---

# 32. なぜ画面保護だけでは不十分か

フロント画面をBasic認証で隠しても、APIのURLを調べて直接呼び出すことは可能です。

```text
管理画面UI
    │
    └── Basic認証で保護

管理API
    │
    └── API内認証なし
```

攻撃者は管理画面を表示せず、HTTPリクエストを直接送信できます。

したがって、権限確認は必ずAPI側で行う必要があります。

# 現在の設計の良い点

## 1. Cognitoへ認証を委譲している

アプリがパスワードを直接受け取らないため、パスワード管理の責任を減らせます。

---

## 2. OAuth stateを検証している

ログイン開始時とCallback時のstateを比較し、不正な認証レスポンスを拒否しています。

---

## 3. トークンをHttpOnly Cookieへ保存している

認証後のトークンをJavaScriptから読み取れないようにし、トークン窃取のリスクを減らしています。

---

## 4. JWT署名を検証している

CognitoのJWKSを使ってRS256署名を検証しています。

単純にJWTをデコードするだけではなく、Cognitoが発行したトークンか確認しています。

---

## 5. JWT Claimを検証している

次のClaimを確認しています。

```text
token_use
aud
iss
exp
```

別のCognito Clientや別ユーザープールのトークン、有効期限切れトークンを拒否できます。

---

## 6. 一部APIはsubをサーバー側で固定している

予約作成や本人予約一覧では、JWTの `sub` をユーザーIDとして利用しています。

クライアントが任意の会員IDを指定する方式より安全です。

---

# 現在の主な問題点

## 1. 管理画面APIが認証されていない

`/api/admin/*` がMiddlewareの対象外で、API内にも認証が確認できません。

---

## 2. 予約詳細・更新APIに認証がない

予約IDを知っていれば、予約情報の取得・変更・キャンセル・返金ができる可能性があります。

---

## 3. 全予約一覧APIが公開されている

未認証ユーザーでも、全予約情報を取得できる可能性があります。

---

## 4. 延長通知に所有者確認がない

ログイン済みであれば、他人の予約IDを指定できる可能性があります。

---

## 5. 返金対象の所有者確認がない

ログイン済みであれば、任意のCharge IDを返金対象に指定できる可能性があります。

---

## 6. トークン保存前のJWT検証がない

不正な文字列も一度Cookieへ保存される可能性があります。

---

## 7. Implicit Flowを使用している

トークンがURLフラグメントを経由してブラウザへ直接返ります。

---

## 8. Refresh Tokenがない

トークン期限切れ後は、基本的に再ログインが必要です。

---

## 9. 認証処理がAPIごとに分散している

各APIで個別にJWT検証を実装しているため、認証処理を付け忘れる可能性があります。

実際に、認証済みAPIと未認証APIが混在しています。

---

## 最優先1：管理画面APIを保護する

`/api/admin/*` のすべてで、API側の管理者認証を行います。

## 中優先度1：Authorization Code Flow + PKCEへ移行する

現在のImplicit Flowから、Authorization Code Flow + PKCEへ移行します。

```text
    │
```

## 中優先度4：認証・認可を共通化する

APIごとに手書きするのではなく、共通関数を作ります。

例：


### requireUser

```ts
const authUser = await requireUser(req, res);

```

### requireReservationOwner

```ts
await requireReservationOwner({
  reservation,
  user: authUser,
});
```

共通化することで、認証処理の付け忘れを減らせます。

# 最終整理

現在の一般ユーザー認証は、次の流れです。

```text
OAuth stateを生成
    │
    ▼
Cognito Hosted UIで認証
    │
    ▼
ID Token・Access Tokenを取得
    │
    ▼
HttpOnly Cookieへ保存
    │
    ▼
APIでJWTを検証
    │
    ▼
payload.subでユーザーを識別
```

この基本フローでは、次の対策が実装されています。

- Cognitoへの認証委譲
    
- OAuth state照合
    
- HttpOnly Cookie
    
- Cognito JWKSによる署名検証
    
- issuer・audience・有効期限の検証
    
- JWTの `sub` によるユーザー識別
    

一方で、認証後に「そのデータを操作してよいか」を確認する認可に不足があります。

特に重要なのは次の3点です。

```text
① /api/admin/* をAPI側で保護する
② 予約詳細・更新で所有者確認を行う
③ 全予約一覧を管理者限定にする
```

加えて、次の対応も必要です。

- 延長通知の予約所有者確認
    
- 返金対象Chargeの所有者確認
    
- トークン保存前のJWT検証
    
- Implicit FlowからAuthorization Code Flow + PKCEへの移行
    
- 管理者認証のCognito Groups化
    
- 認証・認可処理の共通ガード化
    

このシステムでは、**「誰がアクセスしているかを確認する認証」は比較的実装されていますが、「そのユーザーが対象データを操作してよいかを確認する認可」がAPIによって不足している**、というのが全体的な評価です。
