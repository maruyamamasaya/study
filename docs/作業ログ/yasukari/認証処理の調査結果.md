## 結論

このシステムでは、一般ユーザーの認証に **Amazon Cognito Hosted UI** を使用しています。

大まかな流れは次のとおりです。

1. ログイン画面で OAuth `state` を生成する
2. Cognito Hosted UI にリダイレクトする
3. Cognito が ID Token / Access Token を URL フラグメントで返す
4. Callback 画面が `state` を照合する
5. Callback 画面から `/api/auth/store-tokens` にトークンを送る
6. サーバーが ID Token / Access Token を HttpOnly Cookie に保存する
7. APIが ID Token Cookieを取り出す
8. CognitoのJWKSを使ってJWT署名・issuer・audience・有効期限を検証する
9. 検証済みの `sub` をユーザーIDとしてAPI処理を行う

ただし、調査上、次の重要な問題があります。

- `/api/reservations/[reservationId]` のGET/PATCHには認証も予約所有者チェックもありません。
- `/api/reservations` のGETは認証なしで全予約を返します。
- `/api/admin/*` はMiddlewareのBasic認証対象外です。
- 予約延長通知や返金APIは「ログイン済み」の確認だけで、対象予約・決済がそのユーザーのものか確認していません。
- `/api/auth/store-tokens` は受け取ったJWTを検証せず、そのままCookieへ保存します。ただし、通常のAPI利用時には改めてJWT検証が行われます。
- CognitoのImplicit Flow（`response_type=token`）を利用しており、Refresh Tokenは保存していません。

# 1. ログインからAPI利用までの時系列

## 1-1. ログイン開始

ユーザーがログインボタンを押すと、ブラウザ側でランダムなOAuth `state` を作り、`sessionStorage` の `cognito_oauth_state` に保存します。ログインと新規登録は、`signup.` プレフィックスの有無で区別されています。cognitoHostedUi.ts (33～57行)

実際のログイン画面では、次の順番で処理されます。

1. 以前の新規登録意図を削除
2. `createAndStoreOauthState()` を実行
3. `buildAuthorizeUrl(state)` でHosted UIのURLを生成
4. `window.location.href` でCognitoへ移動

日本語ログイン画面の実装です。login.tsx (69～77行)

Hosted UIへのリクエストには、次の値が入ります。

- `client_id`
- `response_type=token`
- `scope`
- `redirect_uri`
- `state`
- `lang`

つまりAuthorization Code Flowではなく、トークンがブラウザへ直接返る **Implicit Flow** です。cognitoHostedUi.ts (59～74行)

デフォルトスコープは次のとおりです。

- `openid`
- `email`
- `phone`
- `profile`
- `aws.cognito.signin.user.admin`

最後のスコープは、Access Tokenを使ったCognitoの `GetUser` / `UpdateUserAttributes` に必要なものです。cognitoHostedUi.ts (17～31行)

## 1-2. Cognito Hosted UIでの認証

ブラウザはCognitoの `/oauth2/authorize` に移動します。そこでCognito側が、メールアドレス、ソーシャルログインなど、ユーザープールに設定された方法で本人を認証します。

アプリケーション側ではパスワードを直接受け取っていません。認証そのものはCognito Hosted UIに委譲されています。

認証成功後、Cognitoは設定された次のCallback URLへ戻します。

```
/auth/callback
```

デフォルトは `https://yasukari.com/auth/callback` です。cognitoHostedUi.ts (1～15行)

## 1-3. CallbackでURLフラグメントを解析

Implicit Flowなので、Callbackにはおおむね次の形式でトークンが返ります。

```
/auth/callback#id_token=...&access_token=...&expires_in=3600&state=...
```

Callback画面は `window.location.hash` を解析します。ハッシュが空、または認証用パラメーターが一つもない場合は、ログイン画面へ戻します。callback.tsx (11～35行)

Cognitoが `error` を返した場合は、トークン保存へ進まず、画面にエラーを表示します。callback.tsx (37～43行)

## 1-4. OAuth state照合

Callbackは、Cognitoから返った `state` と、ログイン開始時に `sessionStorage` へ保存した `state` を比較します。

次のいずれかなら失敗です。

- 戻り値に `state` がない
- `sessionStorage` に期待値がない
- 両者が一致しない

一致しない場合は保存済みstateを削除し、認証エラーを表示します。callback.tsx (45～54行)

このチェックは、ログイン開始元とCallbackの対応を確認するCSRF対策です。ただし、stateはCookieではなくブラウザの `sessionStorage` に保存されています。

照合成功後、stateは削除されます。また、`signup.` プレフィックスがあれば新規登録フローとして扱われます。callback.tsx (56～65行)

## 1-5. ID Token / Access Tokenの取り出し

CallbackはURLフラグメントから次の値を取得します。

- `id_token`
- `access_token`
- `expires_in`

ID Tokenがなければログイン失敗になります。一方、Access Tokenは必須ではありません。callback.tsx (67～75行)

## 1-6. トークン保存APIの呼び出し

Callbackは、取得したトークンをJSON本文に入れて次のAPIへ送ります。

```
POST /api/auth/store-tokens
Content-Type: application/json

{
  "idToken": "...",
  "accessToken": "...",
  "expiresIn": 3600
}
```

`credentials: 'include'` を指定しているため、レスポンスのCookieをブラウザが受け取ります。callback.tsx (77～93行)

保存に成功すると、クライアントサイドルーティングではなくフルページ遷移で次の画面へ移動します。

```
/mypage/profile-setup?fromLogin=1
```

新規登録フローでは `fromSignup=1` も付きます。フルページ遷移にしている理由は、次のリクエストにCookieが確実に含まれるようにするためです。callback.tsx (95～102行)

# 2. Token保存とCookie

## 2-1. 保存されるトークン

Cookie名は次のとおりです。

|用途|Cookie名|
|---|---|
|Cognito ID Token|`cognito_id_token`|
|Cognito Access Token|`cognito_access_token`|

Cookie名はHosted UI共通ライブラリに定義されています。cognitoHostedUi.ts (33～35行)

## 2-2. Cookie属性

`/api/auth/store-tokens` は、ID Tokenを必須として受け取ります。

Cookieには次の属性が設定されます。

- `Path=/`
- `HttpOnly`
- `SameSite=Lax`
- `Max-Age=<expires_in>`
- `Expires=<expires_inから算出>`
- 本番のみ `Secure`

ID Tokenは必ず保存し、Access Tokenは値がある場合だけ保存します。store-tokens.ts (18～40行)

`HttpOnly` なので、保存後は通常のブラウザJavaScriptからCookie値を読み取れません。CallbackだけはCookie保存前なので、URLフラグメントから取得したトークンをJavaScriptで扱っています。

## 2-3. 保存時点ではJWTを検証していない

`/api/auth/store-tokens` が確認しているのは、主に次の点だけです。

- POSTである
- `idToken` が空文字列ではない
- `expiresIn` が正数である

署名、issuer、audience、有効期限、`token_use` はこの段階では検証していません。store-tokens.ts (18～40行)

したがって、このAPIへ任意の文字列をPOSTすると、その文字列自体はID Token Cookieとして保存できます。ただし、JWT検証を実施するAPIでは後段の `verifyCognitoIdToken()` によって拒否されます。

## 2-4. Refresh Tokenは存在しない

Hosted UIが `response_type=token` のImplicit Flowなので、実装上は次の2つしか保存していません。

- ID Token
- Access Token

Refresh Tokenの保存・更新処理はありません。cognitoHostedUi.ts (59～66行)store-tokens.ts (24～39行)

Cookieが期限切れになった場合は、基本的に再ログインが必要です。

## 2-5. ログアウト

`POST /api/logout` は、ID Token CookieとAccess Token Cookieへ `Max-Age=0` と過去の `Expires` を設定して削除します。logout.ts (5～18行)

これはローカルCookieの削除です。APIレスポンスにも「Cognito logoutへ次にリダイレクトする」と明記されています。

なお、`/auth/logout` の画面側でも `document.cookie` による削除を試していますが、保存Cookieは `HttpOnly` なので、JavaScriptによる削除には依存できません。logout.tsx (6～23行)  
確実な削除処理は `/api/logout` の `Set-Cookie` レスポンスです。

# 3. JWT検証

## 3-1. APIがID Token Cookieを取得

認証を必要とするAPIは、基本的に次の処理を行っています。

```
const token = req.cookies?.[COGNITO_ID_TOKEN_COOKIE];
const payload = await verifyCognitoIdToken(token);

if (!payload?.sub) {
  return res.status(401)...
}
```

例えば本人予約一覧APIがこの方式です。me.ts (19～28行)

## 3-2. Cognito JWKS取得

JWT検証では、Cognitoユーザープールの次のURLからJWKSを取得します。

```
https://cognito-idp.<region>.amazonaws.com/<userPoolId>/.well-known/jwks.json
```

取得結果はプロセス内で1時間キャッシュされます。cognitoServer.ts (41～58行)

## 3-3. 署名検証

JWTを3セグメントに分割し、ヘッダーについて次を確認します。

- `alg === RS256`
- `kid` が存在する

その後、`kid` に対応するJWKを選び、RSA SHA-256で署名を検証します。cognitoServer.ts (87～113行)

## 3-4. Claim検証

署名成功後、さらに次を検証します。

|Claim|検証内容|
|---|---|
|`token_use`|`id` であること|
|`aud`|設定されたCognito Client IDと一致すること|
|`iss`|対象リージョン・ユーザープールのissuerと一致すること|
|`exp`|現在時刻より後であること|

すべて成功するとpayloadを返します。cognitoServer.ts (115～134行)

APIは、この検証済みpayloadの `sub` をユーザー識別子として利用します。

## 3-5. MiddlewareのJWT利用は認証ではない

MiddlewareもID Tokenを読みますが、ここでは署名検証していません。JWT payloadを単にBase64URLデコードし、`custom:locale` を取り出して英語ページへリダイレクトするためだけに使っています。middleware.ts (15～34行)middleware.ts (131～145行)

したがってMiddlewareのこの処理は、認証・認可判断ではありません。

# 4. API認証

## 4-1. 認証されているAPI

以下のようなユーザーAPIは、ID Token Cookieを検証しています。

- `/api/me`
- `/api/reservations/me`
- 予約作成 `POST /api/reservations`
- 決済
- 返金
- レンタル延長通知
- 事故報告
- 返却報告
- 通知
- 登録ユーザー情報
- 貸渡約款同意情報

`/api/me` はJWTを検証し、成功時に `sub`、ユーザー名、メールアドレスを返します。未認証の場合は401ではなく、`200 { user: null }` を返します。me.ts (14～28行)

予約作成ではJWT検証後、検証済みの `payload.sub` を予約の `memberId` として強制的に保存します。index.ts (276～285行)index.ts (352～382行)

この部分では、クライアントが任意の `memberId` を指定して別ユーザーの予約を作る構造にはなっていません。

## 4-2. ID TokenとAccess Tokenの使い分け

通常の自前APIではID Tokenを検証してユーザーを識別します。

一方、Access Tokenは主にCognito自身のユーザーAPIへ渡します。例えば `/api/user/attributes` はAccess Token Cookieの存在を確認し、Cognitoの `GetUser` を呼び出します。attributes.ts (123～135行)

ここではアプリ側でAccess TokenをJWT検証していませんが、Cognitoへ直接渡しており、Cognito側が有効性を判断します。

# 5. 認証と認可の違い

## 5-1. 認証

この実装における認証は、次の確認です。

> このリクエストを送ったユーザーは誰か。

一般ユーザーでは、Cognito ID Tokenを検証し、`payload.sub` を取得する処理が認証に相当します。

例えば本人予約一覧は、JWTが有効で `sub` が存在するか確認しています。me.ts (19～25行)

## 5-2. 認可

認可は次の確認です。

> 認証されたユーザーが、この予約や操作を実行してよいか。

実装されている代表例は、`payload.sub` をDynamoDBのキーや検索条件として使い、本人のデータだけを操作する方式です。

本人予約一覧では、クライアントが指定したユーザーIDを使わず、JWT由来の `payload.sub` で予約を検索します。me.ts (20～28行)

貸渡約款情報も同様に、JWT由来の `payload.sub` をDynamoDBの `user_id` として使用します。rental-terms.ts (16～30行)

事故報告も、保存先のDynamoDBキーを `payload.sub` に固定しています。accident-report.ts (121～131行)

これらは「本人のIDをサーバー側で確定する」ため、比較的安全な認可方式です。

# 6. 管理画面認証

## 6-1. 管理画面ページはBasic認証

`/admin` で始まる画面アクセスは、Next.js MiddlewareでHTTP Basic認証されます。

Middlewareはリクエストの `Authorization` ヘッダーを読み、環境変数の次の値と照合します。

- `ADMIN_BASIC_USER`
- `ADMIN_BASIC_PASS`

不一致またはヘッダーなしなら401を返し、`WWW-Authenticate` ヘッダーを設定します。middleware.ts (36～57行)middleware.ts (65～74行)

Basic認証値には環境変数がない場合のデフォルト値もコード上に存在します。basicAuth.ts (1～14行)

管理画面トップ `/admin` は、認証後に `/admin/dashboard` へリダイレクトします。index.tsx (1～12行)

## 6-2. 管理者ロールの判定はない

管理画面認証はCognitoユーザーのグループ・ロール・claimではありません。

つまり現在の管理者判定は、

> 共通のBasic認証ユーザー名・パスワードを知っているか

だけです。

ユーザー単位の管理者アカウント、Cognito `groups`、RBAC、操作権限の段階分けは確認できませんでした。

## 6-3. `/api/admin/*` はBasic認証の対象外

Middlewareのmatcherは次の設定です。

```
matcher: ['/((?!api|wait).*)']
```

このため、`/api` で始まるリクエストにはMiddleware自体が動きません。middleware.ts (151～153行)

一方、管理画面API側にはBasic認証やCognito JWT検証が実装されていません。

したがって、現在の構成では次の差があります。

|対象|認証|
|---|---|
|`/admin/dashboard/...` の画面|Basic認証あり|
|`/api/admin/...`|Middleware対象外、API内認証も確認できない|

つまり、管理画面UIを開く際にはBasic認証が必要ですが、API URLを直接呼び出した場合の保護にはなっていません。

これは管理画面認証における最重要の問題です。

# 7. 予約所有者チェック

## 7-1. 本人予約一覧

`GET /api/reservations/me` は安全な方向の実装です。

1. ID Tokenを検証
2. `payload.sub` を取得
3. `fetchReservationsByMember(payload.sub)` を実行

リクエストから任意の会員IDを受け取らないため、本人予約だけを取得できます。me.ts (19～28行)

## 7-2. 予約作成

`POST /api/reservations` も、予約所有者をJWTの `sub` に固定します。

```
memberId: payload.sub
```

したがって、予約作成時の所有者設定は認証ユーザーに紐づきます。index.ts (352～373行)

## 7-3. 全予約一覧は未認証

一方、同じ `/api/reservations` のGETは、JWT検証を行わず `fetchAllReservations()` を実行しています。index.ts (262～274行)

つまり、現状では未認証リクエストでも全予約一覧を取得できる構造です。

これは所有者チェック以前に、一覧APIそのものが保護されていない状態です。

## 7-4. 予約ID指定GET/PATCHは未認証

`/api/reservations/[reservationId]` は、予約IDを受け取った後、認証処理を行わず予約を読み込んで返します。[reservationId].ts (180～201行)

PATCHについても、

1. `reservationId` で予約を取得
2. リクエスト本文から更新内容を作成
3. 車両・日程・返金等を処理
4. 予約を更新

という処理で、ID Token検証も `existingReservation.memberId === payload.sub` の確認もありません。[reservationId].ts (203～239行)

したがって、予約IDを知っているユーザーに対するサーバー側の所有者チェックがありません。

## 7-5. 延長通知にも所有者チェックがない

予約延長通知APIはID Tokenを検証しているため、未ログインユーザーは拒否します。notify.ts (27～40行)

しかし、その後はリクエスト本文の `reservationId` で予約を取得するだけで、

```
reservation.memberId === payload.sub
```

を確認していません。notify.ts (42～67行)

つまり「ログイン済みである」ことは確認しますが、「その予約の所有者である」ことは確認していません。

## 7-6. 返金にも対象決済の所有者チェックがない

返金APIもID Tokenを検証しますが、本文で受け取った `chargeId` をそのままPay.jpの返金対象にします。payjp-refund.ts (11～25行)payjp-refund.ts (28～44行)

`chargeId` が `payload.sub` の予約・決済に属することをサーバー側で照合していません。

したがって、このAPIも「認証」はありますが、対象リソースに対する「認可」が不足しています。

# 9. 認証・認可の評価

|項目|現状|
|---|---|
|Hosted UI|Cognito Hosted UIを使用|
|OAuth Flow|Implicit Flow|
|Callback state検証|あり|
|ID Token保存|HttpOnly Cookie|
|Access Token保存|HttpOnly Cookie|

|Cookie SameSite|Lax|

# 10. 優先度順の注意点

## 最優先

1. **`/api/admin/*` にサーバー側認証を追加する必要があります。**
    
    - 現在のBasic認証MiddlewareはAPIを除外しています。
2. **`/api/reservations/[reservationId]` に認証・認可を追加する必要があります。**
    
    - 一般ユーザーなら `reservation.memberId === payload.sub`
    - 管理者なら明示的な管理者権限確認
    - GET/PATCH双方が対象です。
3. **`GET /api/reservations` を管理者限定にする必要があります。**
    
    - 一般ユーザーは `/api/reservations/me` のみ使用する構成が妥当です。

## 高優先度

4. **延長通知で予約所有者を確認する必要があります。**
5. **返金APIでcharge IDと予約・ユーザーの紐付けを確認する必要があります。**
6. **管理者認証を共通Basic認証からユーザー単位の認証・ロールへ移行することを推奨します。**

## 中優先度

7. **Implicit FlowからAuthorization Code Flow + PKCEへの移行を検討すべきです。**
8. **トークン保存APIでもCognito JWTを検証してからCookieへ保存するのが安全です。**
9. **Refresh Tokenまたは明示的な再認証方針を設計する必要があります。**
10. **認証・認可処理をAPIごとの手書きから共通ガードへ集約した方が、未適用APIを防止できます。**
