# 予約システム全体の設計から見えてくること

## システム全体像

```text
利用者
   │
   ▼
Step1（日時選択）
   │
   ▼
利用規約確認（必要時のみ）
   │
   ▼
Step2（料金・オプション）
   │
   ▼
Step3（決済）
   │
   ▼
予約API
   │
   ▼
createReservation
   │
   ├── DynamoDB（予約保存）
   ├── Vehicles更新
   ├── KeyBox PIN発行（三ノ輪店）
   └── メール送信
```

---

# 処理の責務分割

この予約システムは比較的きれいに責務が分離されています。

|層|役割|
|-------|----------------------|
|画面（Step1〜3）|ユーザー入力・表示|
|API|入力チェック・予約可否判定|
|lib/reservations.ts|DynamoDBへの保存|
|Pay.JP API|決済|
|Vehiclesテーブル|空き状況管理|
|Reservationテーブル|予約情報管理|

つまり

```
画面
↓
API
↓
DB
```

という一般的なWebアプリ構成になっています。

---

# フロントエンドの役割

フロント側は

- 日時入力
- オプション選択
- 合計金額計算
- バリデーション
- 決済

まで担当しています。

つまり

「予約データを作る」

ことが仕事です。

---

# APIの役割

APIは

「本当に予約していいのか」

だけを判断しています。

例えば

- ログイン済みか
- 必須項目があるか
- 31日以内か
- 車両が存在するか
- 空いているか

などを確認します。

つまり

```
入力チェック担当
```

と言えます。

---

# DB保存処理は完全に分離

APIは直接DynamoDBを書きません。

```
POST /api/reservations

↓

createReservation()

↓

DynamoDB
```

となっています。

これは非常に保守しやすい構造です。

---

# Stepごとのデータ受け渡し

## Step1 → Step2

URLクエリ

```
?store=
?pickupDate=
?returnDate=
```

で渡しています。

メリット

- リロードに強い
- URL共有可能

デメリット

- 長くなる

---

## Step2 → Step3

sessionStorage

```
reserve-flow-step3-payload
```

へ保存しています。

保存されるのは

- 金額
- オプション
- 補償
- クーポン

などです。

つまり

Step2以降はURLではなくブラウザ内部に保存しています。

---

# 決済の流れ

かなり慎重な流れになっています。

```
Step3

↓

予約可能か再確認

↓

Pay.JP決済

↓

予約保存

↓

完了画面
```

ここで重要なのは

決済前に

```
validateOnly
```

を呼んでいることです。

つまり

「決済だけ成功した」

という事故を減らそうとしています。

---

# DynamoDBの使い方

テーブルは2種類あります。

## Reservations

予約情報

```
reservation_id
member
payment
日時
オプション
```

を保存

---

## Vehicles

こちらは

```
空き状況

AVAILABLE

↓

RENTED
```

へ変更しています。

つまり

予約情報と

車両管理は

別テーブルです。

---

# createReservationの責務

createReservationは

かなりシンプルです。

```
予約データ受取

↓

項目整形

↓

PutCommand

↓

Reservation返却
```

つまり

保存専門です。

予約可否などは一切判断していません。

---

# バリデーションの場所

実は3段階あります。

## Step1

画面入力チェック

- 時刻
- 規約
- 必須項目

---

## Step3

sessionStorage検証

```
JSON

↓

必要データ存在
```

---

## API

サーバ側検証

- 認証
- 期間
- 車両
- 空き

# エラー処理

かなり丁寧です。

例えば

予約保存失敗

↓

自動返金

↓

ユーザーへ案内

という流れがあります。

つまり

```
課金成功

↓

予約失敗

↓

返金
```

まで考えられています。

---

# 三ノ輪店だけ特別処理

店舗名が

```
三ノ輪店
```

なら

```
KeyBox PIN発行
```

があります。

つまり

店舗ごとの業務ロジックが存在します。

---

# メール送信

最後に

```

```

を送っています。

メール送信が失敗しても

予約成功は維持されます。

つまり

メールは

"付加機能"

として扱われています。

# 気になる設計

調査結果から見ると改善候補もあります。

## ① 二重予約の可能性

```
空き確認

↓

保存
```

がトランザクションではありません。

同時アクセスでは

競合可能性があります。

---

## ② Vehicles更新失敗

Reservation保存後

Vehicles更新失敗

↓

返金

↓

Reservationだけ残る可能性

があります。

---

## ③ 金額を信用している

APIは

```
paymentAmount
```

を再計算していません。

クライアント値を信用しています。

サーバ側で料金再計算した方が安全です。

---

## ④ 個別予約API

予約IDだけで取得可能です。

所有者確認がありません。

予約IDは推測しにくいですが

セキュリティ上は改善余地があります。

---

# このシステムの設計思想

この予約システムは

```
画面
↓
API
↓
createReservation
↓
DynamoDB
```

というシンプルなレイヤー構造になっています。

また

- フロントはUIと入力管理
- APIは認証・検証
- libはDB操作
- DynamoDBはデータ保存
- Vehiclesは在庫管理

と役割が明確に分離されており、拡張性・保守性を意識した設計になっています。

一方で、

- 排他制御
- トランザクション
- サーバ側料金再計算
- 所有者チェック

など、実運用を考えると改善できるポイントも確認できます。
