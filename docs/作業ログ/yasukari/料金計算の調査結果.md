## 結論

料金計算の中心は、予約フロー2画面の `ReserveFlowStep2` コンポーネントです。

現在の合計金額は、次の式で算出されています。

> **合計金額 = 車種・日数別レンタル料金 + 用品料金 + 補償料金 + 繁忙期料金 − クーポン割引**

この計算結果を `sessionStorage` 経由で予約フロー3へ渡し、同じ `totalAmount` を画面表示、Pay.JP決済API、予約データの `paymentAmount` に利用しています。step2.tsx (403～411行)step2.tsx (745～773行)step3.tsx (275～315行)

ただし、**サーバー側では料金の再計算・照合をしていません**。したがって、通常操作では表示額と決済額は同じ変数なので一致しますが、改ざん耐性を含めた「サーバー保証された一致」にはなっていません。

## 1. 基本料金

コード上には、次のような独立した基本料金計算はありません。

- 基本料金
- 日数追加料金
- 時間超過料金

代わりに、車種と日数をキーにして、料金テーブルから完成済みのレンタル料金を取得します。

初期値・取得失敗時のフォールバックとして `3,980円` が設定されていますが、これは通常の料金計算ルールというより、料金が読み込めなかった場合の代替値です。step2.tsx (41～44行)step2.tsx (647～676行)

したがって、実態としては以下です。

> **基本レンタル料金 = `vehicle_type_id` と `days` に登録された `price`**

料金APIのデータ構造も、`vehicle_type_id`、`days`、`price` の組み合わせです。vehicle-rental-prices.ts (23～29行)

---

## 2. 時間料金

### 計算方法

貸出日時と返却日時の差を時間に変換し、24時間単位で切り上げています。

```
利用時間 = 返却日時 − 貸出日時
料金日数 = ceil（利用時間 ÷ 24時間）
```

最低料金日数は1日です。step2.tsx (240～254行)

例：

|利用時間|料金日数|
|---|---|
|1時間|1日|
|24時間|1日|
|24時間1分|2日|
|48時間|2日|
|48時間1分|3日|

### 結論

**時間単価 × 時間数という時間料金は存在しません。**

時間は、以下にのみ使用されます。

1. 24時間単位の料金日数を決める。
2. 用品料金の期間キーを決める。
3. 決済確認画面に「想定レンタル時間」を表示する。

用品料金用の期間キーは、24時間、2日、4日、1週間、2週間、1か月の区分です。step2.tsx (219～238行)

## 3. 日数料金

### 通常の計算

`loadRentalFee` が `/api/vehicle-rental-prices` から車種別料金一覧を取得し、算出済みの `rentalDays` と完全一致する `days` のレコードを探します。

```
matched = prices.find(item => item.days === rentalDays)
レンタル料金 = matched.price
```

step2.tsx (631～656行)

### 31日を超える場合

31日超の場合に限り、31日料金を31で割った日額を利用日数に掛け、四捨五入します。

```
日額 = 31日料金 ÷ 31
レンタル料金 = round（日額 × 利用日数）
```

step2.tsx (659～667行)

### 料金未登録の場合

- 日数と完全一致する料金がない
- 31日超だが31日料金もない

この場合はフォールバックの3,980円を使用し、画面に「レンタル料金が設定されていません」と表示します。step2.tsx (670～676行)

このため、**料金未登録時にも決済へ進める可能性がある点には注意が必要**です。

## 4. 車種料金

処理は二段階です。

### ① 管理番号から車両モデルIDを取得

`loadVehicle` が、選択車両の管理番号を使って `/api/vehicles/{managementNumber}` を取得し、レスポンスの `modelId` を `vehicleModelId` に保存します。step2.tsx (595～623行)

### ② モデルIDを料金表の車種IDとして検索

次に、以下のAPIを呼び出します。

```
/api/vehicle-rental-prices?vehicle_type_id={vehicleModelId}
```

step2.tsx (631～650行)

料金APIでは `vehicle_type_id` をパーティションキーとして料金レコードを取得し、日数順に返します。vehicle-rental-prices.ts (70～104行)

つまり車種料金は、

> **車両管理番号 → モデルID → 車種・日数別料金表**

の順で決まります。

独立した「車種加算額」があるわけではなく、**車種ごとに料金表そのものが異なる**構造です。

したがって、現在は、

> **足立小台店とほかの店舗で、同じ車種・日程・オプションなら同じ料金**

となります。

## 6. 繁忙期料金

### 繁忙期日の取得

貸出月から返却月までの月一覧を作り、月単位で次のAPIを呼びます。

```
/api/high-season?month=YYYY-MM
```

そのうち `isHighSeason: true` の日付を集合として保持します。step2.tsx (256～308行)

### 対象日数の計算

貸出日を起点に、`rentalDays` 日分の日付を確認し、繁忙期設定日に一致した日数を数えます。step2.tsx (387～401行)

### 金額

```
繁忙期料金 = 繁忙期対象日数 × 550円
```

step2.tsx (403～404行)

画面にも「ハイシーズン追加料金（N日）」として表示されます。step2.tsx (1012～1015行)

なお、画面説明にはゴールデンウィーク、お盆休み、年末年始と記載されていますが、実際の判定は固定期間ではなく、**ハイシーズンAPIに登録された日付**が基準です。step2.tsx (1027～1030行)

## 7. クーポン

計算関数は主に次の2つです。

- 適用処理：`handleApplyCoupon`
- 割引計算：`calculateCouponDiscount`

### 適用条件

`handleApplyCoupon` は `/api/coupon-rules` から全ルールを取得し、入力コードと完全一致するルールを探します。step2.tsx (522～543行)

その後、次を確認します。

1. クーポン期間とレンタル期間が重なっているか。
2. 貸出・返却日が正常か。
3. 対象バイククラスに含まれるか。

対象バイククラスが未指定なら全クラス対象、指定されていれば現在の `vehicleClassId` が含まれる必要があります。step2.tsx (435～493行)step2.tsx (545～563行)

### 割引対象

割引対象は `adjustedRentalFee`、すなわち**レンタル料金だけ**です。

以下はクーポン割引の対象外です。

- 用品料金
- 補償料金
- 繁忙期料金

適用期間がレンタル期間の一部だけの場合、カレンダー日数の比率で対象レンタル料金を按分します。step2.tsx (565～573行)

### 定額クーポン

```
期間按分済み割引額
  = round（設定割引額 × クーポン有効日数 ÷ 全レンタル日数）
```

割引額は対象レンタル料金を超えないように制限されます。step2.tsx (496～515行)

### 割引率クーポン

```
割引額 = round（対象レンタル料金 × 割引率 ÷ 100）
```

こちらも対象レンタル料金を超えないように制限されます。step2.tsx (516～519行)

## 9. 合計金額

`ReserveFlowStep2` 内で直接計算されています。

```
合計金額
  = 調整後レンタル料金
  + 用品オプション料金
  + 補償オプション料金
  + 調整後繁忙期料金
  - クーポン割引額
```

step2.tsx (403～411行)

ここでいう「調整後」はユーザーのロケールによる料金倍率です。日本語ページまたは日本ユーザーは1倍、国際ロケール判定時は2倍にして四捨五入します。pricing.ts (1～8行)pricing.ts (19～20行)useInternationalPricingMultiplier.ts (14～18行)

日本語予約画面でもユーザー属性が国際ロケールの場合は2倍になる設計です。useInternationalPricingMultiplier.ts (23～39行)

# 表示額と決済額の一致について

## 通常操作で一致する理由

通常の画面操作では、以下がすべて同じ `totalAmount` を使用します。

1. 予約フロー2の合計表示
2. `sessionStorage` に保存する金額
3. 予約フロー3の合計表示
4. Pay.JP Checkoutに表示する金額
5. `/api/payments/payjp` へ送る決済金額
6. 予約データに保存する `paymentAmount`

したがって、**通常操作上は画面表示額と決済額が一致する構造**です。

---

## ただし、サーバー保証はない

現状、決済APIは次を実施していません。

- 車種・日数別料金の再取得
- 繁忙期料金の再計算
- クーポンの再検証
- 用品・補償料金の再計算
- 税込金額の再検証
- 画面金額とサーバー計算金額の照合

決済APIが確認しているのは、認証、トークン、`amount` の存在などであり、受け取った `body.amount` をそのままPay.JPへ送っています。payjp.ts (40～65行)

また、決済前に呼ぶ予約検証APIも空き状況は検証しますが、金額は受け取らず、料金計算・照合をしていません。step3.tsx (247～273行)index.ts (317～350行)

そのため、厳密な評価は以下です。

- **画面間の一致：同一変数を引き継ぐため一致**
- **Pay.JP決済額との一致：同じクライアント値を送るため通常は一致**
- **正しい料金表との一致：決済時には再検証されない**
- **改ざん耐性：なし**
- **Pay.JPが返した実決済額との照合：なし**  
    Pay.JPレスポンスには `amount` が含まれますが、フロント側は `chargeId` と `paidAt` しか利用していません。payjp.ts (84～102行)step3.tsx (299～301行)

# 最終整理

現在、実装されている料金は次のとおりです。

- **基本料金**：独立計算なし。車種・日数別料金表の金額を利用。
- **時間料金**：なし。24時間ごとに日数を切り上げるだけ。
- **日数料金**：車種・日数別料金表から完全一致で取得。31日超のみ日割り。
- **車種料金**：車両管理番号からモデルIDを特定し、車種別料金表を選択。
- **店舗料金**：なし。
- **繁忙期料金**：繁忙期設定日数 × 550円。
- **クーポン**：レンタル料金のみを対象に、期間・車両クラスを確認して定額または率で割引。
- **消費税**：計算なし。全料金が税込登録されている前提。
- **合計金額**：レンタル＋用品＋補償＋繁忙期−クーポン。
- **表示・決済の一致**：同じ `totalAmount` を引き継ぐため通常は一致するが、サーバー側の再計算・照合はない。
