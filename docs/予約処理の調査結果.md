## 1. 処理フローを時系列で説明

### 1-1. Step1を開く

**画面パス**

- `/reserve/flow/step1`

**ファイル／主要関数**

- `pages/reserve/flow/step1.tsx`
- `ReserveFlowStep1`
- `verifySession`
- `fetchRegistration`
- `buildStepParams`

#### ① ログイン状態を確認する

画面表示時に `GET /api/me` を実行します。

- Cookieを含めてセッションを確認する。
- `user` が存在しなければ `/login` にリダイレクトする。
- APIエラーの場合は画面上に「ログイン状態の確認に失敗しました」と表示し、処理を継続できない状態にする。セッション確認リクエストは `AbortController` でアンマウント時に中断されます。step1.tsx (63～97行)

#### ② URLクエリから予約候補を復元する

`router.query` から次の値を読み込み、Step1のstateに設定します。

- `store`
- `modelName`
- `managementNumber`
- `pickupDate`
- `returnDate`
- `customerName`
- `email`

ただし、`pickupTime` と `returnTime` はこの復元処理ではURLクエリから読み込まれていません。Step2からStep1へ戻る際には時刻もクエリへ付けていますが、Step1側では復元しないため、戻った場合に時刻選択が失われる実装です。step1.tsx (99～110行)step2.tsx (779～790行)

#### ③ 本登録情報を取得する

セッション確認後、`GET /api/register/user` を実行します。

- `401`：`/login` にリダイレクト。
- `404`：本登録情報なしとして扱う。
- 成功時：
    - `registration` を保持。
    - `name1` と `name2` から `customerName` を構築。
    - 登録メールアドレスを `email` に設定。
- その他の失敗：本登録情報取得エラーを画面表示する。step1.tsx (112～161行)

#### ④ 日付・時刻を選択する

店舗に応じて時刻候補が異なります。

- 三ノ輪を含む店舗：`00:00`～`23:00`
- 足立を含む店舗：`10:00`～`18:00`
- その他：`08:00`～`17:00`step1.tsx (46～54行)

貸出日を変更したとき、返却日が貸出日より後でなければ、自動的に貸出日の翌日へ補正します。また、貸出時刻を変更すると返却時刻も同じ時刻に設定します。店舗変更などによって現在の貸出時刻が選択肢外になった場合は、貸出・返却時刻を両方クリアします。step1.tsx (192～223行)

#### ⑤ 「次へ」でフロント側バリデーションを行う

`handleNext` は次の順で判定します。

1. 本登録情報の取得が完了しているか。
2. `REQUIRED_REGISTRATION_FIELDS` がすべて埋まっているか。
3. 貸出時刻・返却時刻が選択されているか。
4. レンタル利用規約へ同意済みか。

未登録または日時未指定の場合は `window.alert` で止めます。step1.tsx (172～179行)step1.tsx (225～246行)

#### ⑥ 利用規約が未同意なら規約画面を経由する

未同意の場合は、予約基本情報をクエリ文字列にして次へ遷移します。

```

```

同意済みなら直接Step2へ進みます。

```
/reserve/flow/step2
```

Step1から引き渡す値は次の7項目です。

- `store`
- `modelName`
- `managementNumber`
- `pickupDate`
- `returnDate`
- `pickupTime`
- `returnTime`step1.tsx (181～190行)step1.tsx (238～246行)

## 3. `POST /api/reservations` の処理とバリデーション

**ファイル／関数**

- `pages/api/reservations/index.ts`
- `handler`
- `normalizeAccessorySelection`
- `normalizeCoverageOption`
- `isWithinReservationWindow`
- `isReservationRangeAvailable`
- `buildDateKeysInRange`
- `buildRenterNote`

### ① Cognito認証

CookieからCognito IDトークンを取得し、`verifyCognitoIdToken` で検証します。

`payload.sub` がなければ次を返します。

- HTTP `401`
- `{ error: "認証が必要です" }`index.ts (276～283行)

### ② 必須フィールド

通常保存時の必須項目は以下です。

- `storeName`
- `vehicleModel`
- `vehicleCode`
- `pickupAt`
- `returnAt`
- `paymentAmount`
- `paymentId`

`validateOnly=1` の場合は、決済関連の `paymentAmount` と `paymentId` を要求しません。index.ts (285～302行)

注意点として、必須判定は `!body[field]` です。このため空文字だけでなく、`paymentAmount: 0` も未指定として扱われます。

### ③ 予約期間

`isWithinReservationWindow` で次を検証します。

- 日付として解釈可能か。
- 返却日時が貸出日時より後か。
- 貸出日時が現在から3か月先以内か。
- 返却日時が貸出日時から31日以内か。

違反時はHTTP `400` です。index.ts (236～260行)index.ts (304～308行)

一方、過去日時でないことは検証していません。したがって、車両のavailabilityが合えば、APIレベルでは過去の貸出開始日時が通る可能性があります。

### ④ paymentIdによる重複防止

通常保存時は `paymentId` を予約IDとして既存予約を検索します。

すでに存在すれば新規保存せず、既存予約をHTTP `200`で返します。index.ts (310～315行)

これはリトライ時の二重登録防止として機能します。

### ⑤ 車両存在確認

DynamoDBの `Vehicles` テーブルから、次のキーで取得します。

```
managementNumber = body.vehicleCode
```

見つからなければHTTP `404`です。index.ts (317～328行)

### ⑥ 車両の予約可能日を確認

車両の `rentalAvailability` を正規化し、貸出日から返却日までの全日が `AVAILABLE` か確認します。

1日でも `AVAILABLE` 以外ならHTTP `409`です。index.ts (194～234行)index.ts (330～346行)

`rentalAvailability` 自体が存在しない場合も予約不可です。

### ⑦ 用品と補償を正規化

用品はオブジェクトから数値変換でき、かつ0より大きい値だけを残します。ただし、許可キーのホワイトリスト検証はAPI側にないため、任意のキーが正の数値なら残ります。index.ts (76～95行)

補償は文字列ならtrimし、それ以外は空文字へ変換します。「加入」「未加入」などの許容値検証はありません。index.ts (97～98行)

## 4. `createReservation` までの流れ

`POST /api/reservations` の `handler` は、認証・必須項目・期間・重複・車両・空き状況の検証後、`createReservation` を呼びます。index.ts (276～352行)

APIから `createReservation` へ渡す際、次の補完が行われます。

- `vehiclePlate`
    1. Vehiclesテーブルの `licensePlateNumber`
    2. リクエストの `vehiclePlate`
    3. `vehicleCode`
    4. `"未設定"`
- `status`：未指定なら `"予約受付完了"`
- `memberId`：リクエスト値ではなく、認証済みCognitoの `payload.sub`
- `memberName`：リクエスト、Cognitoの `name`、空文字の順
- `memberEmail`：リクエスト、Cognitoの `email`、空文字の順
- `reservationCompletedFlag`：未指定なら `false`index.ts (352～382行)

## 7. 実装上の注意点

### ① 決済前検証と実保存は排他的ではない

Step3で `validateOnly=1` を実施した後、Pay.JP決済を行い、さらに通常の予約APIでもavailabilityを確認しています。ただし、availabilityの確認から予約保存・Vehicles更新までをDynamoDBトランザクションや条件付き更新でまとめていません。step3.tsx (247～301行)index.ts (317～409行)

そのため、同じ車両・日程に対する並行リクエストでは、両方が `AVAILABLE` を確認してから双方の予約レコードを保存する競合余地があります。

### ② 予約テーブルとVehiclesテーブルの更新が非原子的

処理順は次のとおりです。

1. `createReservation` で予約テーブルへ保存。
2. Vehiclesテーブルのavailabilityを `RENTED` へ変更。

Vehicles更新に失敗するとAPI全体は `500` になり、フロントはPay.JP返金処理を実行します。しかし、先に保存済みの予約レコードを削除またはキャンセルする処理はありません。index.ts (352～409行)index.ts (430～433行)

つまり、返金済みでも予約レコードだけ残る可能性があります。

### ③ Vehicles更新のConditionExpressionは競合防止になっていない

Vehicles更新時の条件は次だけです。

```
attribute_exists(managementNumber)
```

対象車両が存在することは保証しますが、対象日の状態が引き続き `AVAILABLE` であることは保証しません。index.ts (399～408行)

### ④ 金額をAPI側で再計算していない

`paymentAmount`、`couponDiscount`、補償・用品選択はクライアントから渡された値を使用しています。予約APIは金額と料金表の整合性を再計算・検証していません。index.ts (25～50行)index.ts (352～382行)

Pay.JPへの課金額と予約保存額は同じStep3 stateを使うため通常操作では一致しますが、サーバー側で正規料金を保証する構造ではありません。

### ⑤ 個別予約GETに所有者チェックがない

`GET /api/reservations/{reservationId}` はIDだけで予約を取得し、Cognito認証や `memberId` の一致確認をしていません。[reservationId].ts (180～200行)

一方、マイページ向けの `GET /api/reservations/me` はCognito認証後、`payload.sub` に一致する予約だけを返します。me.ts (10～31行)

予約IDがPay.JP charge IDであり推測困難であるとしても、個人情報を含む予約詳細APIとしてはアクセス制御上の注意点です。

### ⑥ `/reserve/flow/complete` と実際の完了遷移が一致していない

予約フロー配下に完了画面がありますが、Step3は `/reserve/thanks` へ移動します。step3.tsx (349～364行)

このため、`pages/reserve/flow/complete.tsx` は現在の主要予約導線から外れている可能性があります。
