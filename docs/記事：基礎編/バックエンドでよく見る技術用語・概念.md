## バックエンドでよく見る技術用語・概念

|用語|超ざっくり意味|よく出る場面|
|---|---|---|
|**API**|システム同士の窓口|フロント↔バックエンド|
|**REST API**|HTTPを使った代表的なAPI設計|Web API|
|**エンドポイント**|APIの具体的なURL|`/api/users`|
|**リクエスト**|クライアント→サーバーへの要求|HTTP|
|**レスポンス**|サーバー→クライアントへの返答|HTTP|
|**HTTPメソッド**|GET・POST・PUT・PATCH・DELETE|API|
|**ステータスコード**|`200` `404` `500` などの結果|API|
|**JSON**|APIでよく使うデータ形式|API通信|
|**認証**|「あなたは誰？」を確認|ログイン|
|**認可**|「何をしていい？」を確認|権限管理|
|**セッション**|ログイン状態などをサーバー側で管理|認証|
|**Cookie**|ブラウザに保存される小さなデータ|認証|
|**JWT**|認証情報などを持たせるトークン|API認証|
|**Middleware**|本処理の前後に共通処理を挟む|認証・ログ|
|**Controller**|リクエストを受け取る層|MVC|
|**Service**|業務ロジックを担当する層|レイヤー設計|
|**Repository**|DBアクセスを担当する層|DB・設計|
|**ORM**|SQLを直接書かずDBを扱いやすくする|Prisma / Hibernate等|
|**CRUD**|作成・取得・更新・削除|DB・API|
|**SQL**|RDBを操作する言語|MySQL / PostgreSQL|
|**クエリ**|DBに対する問い合わせ|SQL|
|**JOIN**|複数テーブルを結合|SQL|
|**インデックス**|DB検索を高速化する仕組み|DB性能改善|
|**N+1問題**|DBアクセスが大量発生する問題|ORM・性能改善|
|**トランザクション**|複数処理をひとまとまりにする|DB更新|
|**COMMIT**|DB変更を確定|トランザクション|
|**ROLLBACK**|DB変更を取り消す|トランザクション|
|**ACID**|トランザクションの重要な性質|DB|
|**ロック**|同時更新などを制御|DB|
|**デッドロック**|お互いのロック解除を待って止まる|DB|
|**コネクションプール**|DB接続を使い回す|DB性能|
|**キャッシュ**|データを一時保存して高速化|Redisなど|
|**バリデーション**|入力値が正しいか確認|API|
|**例外処理**|エラー発生時の処理|バックエンド全般|
|**ロギング**|動作・エラーなどを記録|運用・障害調査|
|**環境変数**|設定値をコードの外で管理|`.env`|
|**マイグレーション**|DB構造の変更を管理|DB開発|
|**スキーマ**|データ構造の定義|DB|
|**冪等性**|同じ処理を複数回しても結果が変わらない性質|API・決済|
|**非同期処理**|完了を待たず別処理を進める|メール・重い処理|
|**ジョブ / Queue**|後で実行する処理を並べる|バッチ・非同期|
|**バッチ処理**|データなどをまとめて処理|定期処理|
|**Cron**|処理を定期実行する仕組み|バッチ|
|**Webhook**|イベント発生を別システムへ通知|決済など|
|**DI（依存性注入）**|部品同士の依存関係を外から与える|設計|
|**疎結合**|部品同士の依存を小さくする|設計|
|**責務**|そのクラス・関数が担当する仕事|設計|
|**リファクタリング**|動作を変えずコードを改善|保守|
|**技術的負債**|後回しにした問題による将来コスト|開発全般|
|**アンチパターン**|よくある「避けたい設計・実装」|設計|

## 特に重要なのは「処理の流れ」

バックエンドの記事を読むなら、単語をバラバラに覚えるより、この流れを理解すると一気につながります。

```
ブラウザ
   │
   │ POST /api/users
   ▼
┌───────────────────┐
│   Backend Server  │
│                   │
│ Middleware        │
│   ↓               │
│ Controller        │
│   ↓               │
│ Service           │
│   ↓               │
│ Repository / ORM  │
└────────┬──────────┘
         │
         │ SQL
         ▼
    ┌──────────┐
    │ Database │
    └──────────┘
```

例えば、

```
POST /api/users
```

が来たら、

```
① Request
   ↓
② Middleware
   認証など
   ↓
③ Controller
   リクエストを受け取る
   ↓
④ Validation
   入力値をチェック
   ↓
⑤ Service
   実際の業務ロジック
   ↓
⑥ Repository / ORM
   DB操作
   ↓
⑦ Database
   INSERT
   ↓
⑧ Response
   ↓
200 / 201 + JSON
```

という感じです。

## DB系の記事なら、このセット

バックエンドではDBの知識がかなり重要なので、

```
SQL
 ↓
CRUD
 ↓
Primary Key / Foreign Key
 ↓
JOIN
 ↓
正規化
 ↓
トランザクション
 ↓
COMMIT / ROLLBACK
 ↓
ACID
 ↓
ロック / 排他制御
 ↓
インデックス
 ↓
EXPLAIN
 ↓
N+1問題
```

この流れで覚えると実務につながりやすいです。

## API系なら、このセット

```
HTTP
 ↓
Request / Response
 ↓
GET / POST / PUT / PATCH / DELETE
 ↓
Endpoint
 ↓
Status Code
 ↓
JSON
 ↓
REST API
 ↓
Validation
 ↓
認証 / 認可
 ↓
Cookie / Session / JWT
 ↓
CORS
 ↓
冪等性
```

特に**「冪等性（べきとうせい）」**は技術ブログで突然出てきて「何それ？」となりやすい用語です。

例えば決済APIで、

```
「支払う」ボタン
     ↓
POST /payments
     ↓
通信エラー
     ↓
ユーザーがもう一度押す
     ↓
POST /payments
```

となったときに、

```
❌ 2回決済される

⭕ 同じリクエストだと判断して
   1回だけ決済する
```

のように、**同じ操作を繰り返しても意図しない結果にならないようにする考え方**です。

```
責務
疎結合 / 密結合
DI
レイヤー
Controller
Service
Repository
ドメイン
ビジネスロジック
MVC
クリーンアーキテクチャ
DDD
依存関係
アンチパターン
技術的負債
```

あたりが一気に増えてきます。

特に、

> **「責務」「依存関係」「疎結合」「レイヤー」**

この4つを理解すると、**「なぜControllerとServiceを分けるの？」みたいな設計記事がかなり読みやすくなります。**
