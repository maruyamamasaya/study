## データベースとは

データベースとは、**大量のデータを整理して保存し、必要なときに取り出せるようにする仕組み**です。

例えばWebサービスでは、

- ユーザー情報
    
- 商品情報
    
- 予約情報
    
- 注文情報
    
- 決済情報
    

など、さまざまなデータを扱います。

これらを単純なファイルとして保存するのではなく、検索・更新・削除しやすい形で管理するためにデータベースを使います。

---

## なぜデータベースが必要なのか

例えば予約サービスを考えてみます。

ユーザーが予約すると、

```text
ユーザー
   ↓
予約する
   ↓
Webアプリ
   ↓
データベース
   ↓
予約情報を保存
```

という流れになります。

保存されるデータは、例えば次のようなものです。

```text
予約ID
ユーザーID
予約日時
商品ID
料金
ステータス
```

データベースを使うことで、

「このユーザーの予約だけ取得する」

「今日の予約を一覧表示する」

「予約をキャンセル済みに変更する」

といった処理がしやすくなります。

---

# データベースの代表的な種類

データベースにはいくつか種類があります。

大きく分けると、

**リレーショナルデータベース**

と

**NoSQLデータベース**

があります。

---

# リレーショナルデータベース

リレーショナルデータベースは、データを**表形式**で管理します。

代表的なものには、

- MySQL
    
- PostgreSQL
    
- Oracle Database
    
- Microsoft SQL Server
    

などがあります。

例えばユーザー情報なら、

```text
users

+----+--------+----------------------+
| id | name   | email                |
+----+--------+----------------------+
| 1  | Tanaka | tanaka@example.com   |
| 2  | Suzuki | suzuki@example.com   |
+----+--------+----------------------+
```

のように管理します。

この表を**テーブル**と呼びます。

---

# テーブル・行・列

リレーショナルデータベースでは、

```text
テーブル
 ├── 行
 └── 列
```

という考え方があります。

例えば、

```text
usersテーブル

id | name   | age
------------------
1  | Tanaka | 30
2  | Suzuki | 25
```

なら、

`id`、`name`、`age`

が**列（カラム）**です。

一方、

```text
1 | Tanaka | 30
```

という1件分のデータが**行（レコード）**です。

---

# 主キー

データベースでは、それぞれのデータを区別する必要があります。

そこで使われるのが**主キー（Primary Key）**です。

例えば、

```text
id
```

を主キーにします。

```text
id | name
---------
1  | Tanaka
2  | Suzuki
3  | Sato
```

この場合、`id = 1`のユーザーは1人だけです。

主キーは、

**データを一意に特定するための値**

と考えると分かりやすいです。

---

# テーブル同士の関係

リレーショナルデータベースでは、複数のテーブルを関連付けることができます。

例えば、

```text
users

id | name
---------
1  | Tanaka
```

と、

```text
reservations

id | user_id | date
------------------------
1  | 1       | 2026-08-01
2  | 1       | 2026-08-10
```

があるとします。

`reservations.user_id = 1`

を見ることで、

```text
Tanakaさんの予約
```

だと分かります。

このように、テーブル同士を関連付けて管理します。

---

# 外部キー

別のテーブルのデータを参照するために使われるのが、

**外部キー（Foreign Key）**

です。

例えば、

```text
reservations.user_id
```

が、

```text
users.id
```

を参照します。

関係としては、

```text
users
  ↓
 id
  ↑
user_id
  ↑
reservations
```

となります。

---

# SQLとは

リレーショナルデータベースを操作するために使われる代表的な言語が、

**SQL**

です。

SQLを使うことで、

- データを取得する
    
- データを追加する
    
- データを更新する
    
- データを削除する
    

といった操作ができます。

---

# SELECT

データを取得するときは、

```sql
SELECT * FROM users;
```

のように書きます。

これは、

```text
usersテーブルのデータを取得する
```

という意味です。

条件を付ける場合は、

```sql
SELECT * FROM users
WHERE id = 1;
```

と書きます。

---

# INSERT

データを追加する場合は、

```sql
INSERT INTO users (name, age)
VALUES ('Tanaka', 30);
```

のように書きます。

---

# UPDATE

データを更新する場合は、

```sql
UPDATE users
SET age = 31
WHERE id = 1;
```

と書きます。

---

# DELETE

データを削除する場合は、

```sql
DELETE FROM users
WHERE id = 1;
```

と書きます。

これらはまとめて、

```text
Create
Read
Update
Delete
```

と呼ばれ、

**CRUD**

と表現されることがあります。

---

# JOIN

リレーショナルデータベースで重要なのが、

**JOIN**

です。

JOINを使うと、複数のテーブルをつなげてデータを取得できます。

例えば、

```text
users
+
reservations
```

をつなげて、

```text
ユーザー名
予約日
```

をまとめて取得できます。

イメージとしては、

```text
users
   ↓
 user_id
   ↓
reservations
```

という関係を使ってデータを結合します。

---

# インデックス

データが増えると、検索に時間がかかることがあります。

例えば1000万件のユーザーデータから、

```text
email = tanaka@example.com
```

を探す場合です。

そこで使われるのが、

**インデックス**

です。

インデックスは、

**本の索引**

のようなものです。

本を最初から全部読むのではなく、索引から目的のページを探すように、データベースも高速に検索できるようになります。

ただし、インデックスを増やしすぎると、

- データ追加
    
- 更新
    
- ディスク使用量
    

などに影響が出るため、適切に設定する必要があります。

---

# トランザクション

データベースでは、複数の処理をひとまとまりとして扱いたい場合があります。

例えば銀行振込なら、

```text
Aさん
-10,000円

Bさん
+10,000円
```

という2つの処理が必要です。

もし途中でエラーが起きて、

```text
Aさんだけ -10,000円
Bさんには入金されない
```

となると困ります。

そこで使うのが、

**トランザクション**

です。

```text
処理開始
   ↓
Aさんから減額
   ↓
Bさんへ追加
   ↓
全部成功
   ↓
確定
```

もし途中で失敗したら、

```text
元の状態へ戻す
```

ということができます。

---

# COMMITとROLLBACK

トランザクションでは、

**COMMIT**

と

**ROLLBACK**

という言葉がよく登場します。

### COMMIT

処理を正式に確定します。

### ROLLBACK

途中まで行った処理を取り消して元に戻します。

```text
BEGIN
 ↓
処理
 ↓
成功
 ↓
COMMIT
```

失敗した場合は、

```text
BEGIN
 ↓
処理
 ↓
エラー
 ↓
ROLLBACK
```

となります。

---

# ACID

データベースのトランザクションを理解するときによく出てくるのが、

**ACID**

という考え方です。

簡単にいうと、

**データを安全・正確に扱うための性質**

です。

代表的には、

```text
Atomicity
Consistency
Isolation
Durability
```

の4つがあります。

最初は、

**「途中で壊れた状態を残さず、正しいデータを保つ仕組み」**

くらいの理解で問題ありません。

---

# NoSQLとは

NoSQLは、リレーショナルデータベースとは異なる方法でデータを管理するデータベースです。

代表的なものには、

- DynamoDB
    
- MongoDB
    
- Redis
    

などがあります。

例えばDynamoDBでは、

```text
Key
 ↓
Value
```

のような形でデータを管理できます。

NoSQLは、

- 大量アクセスに対応しやすい
    
- 柔軟なデータ構造を扱いやすい
    
- 水平分散しやすい
    

といった特徴を持つものがあります。

---

# SQLとNoSQLの違い

簡単に比較すると、

|項目|SQL|NoSQL|
|---|---|---|
|データ構造|表形式|柔軟|
|関係性|得意|製品による|
|JOIN|得意|基本的に使わないものも多い|
|構造|厳密|柔軟|
|代表例|MySQL|DynamoDB|

どちらが優れているというより、

**用途に合わせて選ぶ**

ことが重要です。

---

# データベースサーバー

データベースもサーバー上で動きます。

例えば、

```text
Webサーバー
    ↓
DBサーバー
    ↓
MySQL
```

という構成があります。

オンプレミスなら、

```text
Linux
 ↓
MySQL
```

を自分たちでインストールして管理することがあります。

---

# AWSとデータベース

AWSでは、データベースを利用するためのさまざまなサービスがあります。

代表的なのが、

**RDS**

です。

RDSでは、

- MySQL
    
- PostgreSQL
    
- MariaDB
    
- Oracle
    
- SQL Server
    

などを利用できます。

例えば、

```text
ユーザー
   ↓
ALB
   ↓
EC2
   ↓
RDS
```

という構成があります。

---

# RDSのメリット

EC2上に自分でMySQLをインストールする場合、

```text
OS管理
DBインストール
バックアップ
アップデート
障害対応
```

などを自分たちで行います。

RDSでは、その一部をAWSに任せることができます。

そのため、

**データベースの運用負担を減らしやすい**

というメリットがあります。

---

# DynamoDB

AWSには、

**DynamoDB**

というNoSQLデータベースもあります。

DynamoDBはAWSが管理しているサービスなので、

```text
サーバーを作る
OSを管理する
DBをインストールする
```

といった作業を基本的に行う必要がありません。

このようなサービスは、

**マネージドサービス**

と呼ばれます。

---

# バックアップ

データベースで非常に重要なのが、

**バックアップ**

です。

もし、

- 操作ミス
    
- 障害
    
- システム不具合
    
- データ破損
    

などが発生したときに、データを復旧できるようにします。

例えば、

```text
本番DB
 ↓
定期バックアップ
 ↓
バックアップデータ
```

を保存しておきます。

---

# リストア

バックアップからデータを戻すことを、

**リストア**

と呼びます。

重要なのは、

**バックアップを取るだけではなく、本当に復旧できるか確認すること**

です。

---

# 可用性

データベースが停止すると、Webサービス全体が利用できなくなる場合があります。

そのため、

**可用性**

も重要です。

例えば、

```text
DB-A
 ↓
障害
 ↓
DB-Bへ切り替え
```

のように、複数の環境を用意して障害に備えることがあります。

AWS RDSでは、Multi-AZなどの仕組みを利用できます。

---

# レプリケーション

データベースのデータを別のDBへ複製する仕組みを、

**レプリケーション**

と呼びます。

例えば、

```text
Primary DB
    ↓
データ複製
    ↓
Replica DB
```

という構成です。

これにより、

- 障害対策
    
- 読み取り負荷の分散
    

などに利用できます。

---

# パフォーマンス

データベースでは、データ量やアクセス数が増えると処理が遅くなることがあります。

そのため、

- SQL
    
- インデックス
    
- CPU
    
- メモリ
    
- ディスクI/O
    
- 接続数
    

などを確認します。

例えば、

```text
Webサイトが遅い
    ↓
アプリは正常？
    ↓
DBへのSQLが遅い？
    ↓
インデックスはある？
    ↓
CPU・メモリは足りている？
```

というように原因を調査します。

---

# コネクション

Webアプリがデータベースを利用するときは、

**DBへ接続**

します。

この接続を、

**コネクション**

と呼びます。

```text
Webアプリ
    ↓
DB Connection
    ↓
Database
```

アクセスが増えて接続数が多くなると、データベースに負荷がかかることがあります。

そのため、

**Connection Pool**

などを使って接続を効率的に管理することがあります。

---

# データベースとセキュリティ

データベースには重要な情報が保存されています。

そのため、インターネットから直接アクセスできる状態にするのは危険です。

例えばAWSなら、

```text
インターネット
     ↓
ALB
     ↓
Webサーバー
     ↓
RDS
```

のようにします。

```text
インターネット
     ↓
RDS
```

と直接接続させるのではなく、

**必要なサーバーだけがDBへアクセスできる**

ようにします。

---

# PublicとPrivate

クラウド環境では、DBサーバーをPrivate Subnetに配置することがよくあります。

```text
VPC
│
├── Public Subnet
│      └── Web
│
└── Private Subnet
       └── Database
```

外部からデータベースへ直接アクセスできないようにすることで、安全性を高めます。

---

# インフラエンジニアに必要なDB知識

インフラエンジニアの場合、アプリケーションエンジニアほど複雑なSQLを書くことが中心ではありません。

その代わり、

- DBサーバーの構築
    
- 接続設定
    
- ユーザー・権限
    
- バックアップ
    
- リストア
    
- 監視
    
- CPU・メモリ
    
- ディスク容量
    
- 接続数
    
- 障害対応
    
- 冗長化
    
- セキュリティ
    

などの知識が重要になります。

---

# 障害対応のイメージ

例えば、

```text
WebサービスからDBへ接続できない
```

という障害が起きたとします。

その場合、

```text
DBサーバーは起動している？
       ↓
ネットワークは正常？
       ↓
DBポートは許可されている？
       ↓
ユーザー・パスワードは正しい？
       ↓
接続数の上限に達していない？
       ↓
CPU・メモリは正常？
       ↓
DBログにエラーはある？
```

というように原因を切り分けます。

ここでも、

**Linux・ネットワーク・セキュリティの知識**

がつながってきます。

---

Webサービス全体を見ると、

```text
ユーザー
   ↓
DNS
   ↓
ALB
   ↓
Webサーバー
   ↓
アプリケーション
   ↓
データベース
```

という構成になります。

データベースは、

**システムの一番奥で重要なデータを管理する役割**

を持っています。

# まとめ

データベースとは、

**システムで利用するデータを安全に保存し、必要なときに検索・更新できる仕組み**

です。

Webサービスでは、

```text
アプリケーション
       ↓
データベース
       ↓
データ保存
```

という形で利用されます。

インフラエンジニアにとって重要なのは、SQLだけではありません。

**データベースを安全かつ安定して動かし続けるために、バックアップ・監視・性能・セキュリティ・障害対応まで理解すること**

が重要です。

そして、

```text
Linux
 ↓
ネットワーク
 ↓
サーバー
 ↓
データベース
 ↓
クラウド
```

というように、データベースも他のインフラ技術とつながっています。

データベース単体で考えるのではなく、

**「Webサービスの中で、どこに存在し、誰からアクセスされ、どのようにデータを守るのか」**

まで考えられるようになることが、インフラエンジニアとして重要です。
