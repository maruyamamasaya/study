## 1. SSL/TLS証明書とは

**SSL/TLS証明書**とは、HTTPS通信で使用される電子的な証明書です。

主に次の2つの目的があります。

1. **接続先のサーバーが本物であることを確認する**
    
2. **ブラウザとサーバー間の通信を安全に暗号化する**
    

例えば、

```text
https://example.com
```

へアクセスしたとき、ブラウザは単に通信を暗号化するだけではありません。

```text
ブラウザ
   │
   │ 「example.comに接続したい」
   ▼
サーバー
   │
   │ SSL/TLS証明書を提示
   ▼
ブラウザ
   │
   ├─ 信頼できる認証局が発行した？
   ├─ example.com用の証明書？
   ├─ 有効期限内？
   └─ 証明書は改ざんされていない？
```

こうした確認をしたうえでHTTPS通信を開始します。

---

# 2. なぜ証明書が必要なのか

インターネット通信には、大きく次のリスクがあります。

## なりすまし

攻撃者が、

```text
「私がexample.comです」
```

と偽サイトを用意しても、何も確認する仕組みがなければブラウザは本物か判断できません。

そこで第三者である**認証局（CA）**が、

```text
この証明書は
example.comのために発行しました
```

と署名します。

---

## 盗聴・改ざん

HTTP通信では通信内容が暗号化されません。

```text
ブラウザ
   │
   │ ID / Password
   │
   ▼
インターネット
   │
   │ ← 途中で盗聴・改ざんされる可能性
   ▼
サーバー
```

HTTPSではTLSによって暗号化します。

```text
ブラウザ
   │
   │ 🔐 暗号化
   ▼
インターネット
   │
   │ 暗号化されたデータ
   ▼
サーバー
```

つまりHTTPSでは、

**認証 + 暗号化 + 改ざん検知**

によって通信を保護します。

---

# 3. 証明書には何が入っている？

TLS証明書は主に **X.509** という規格に従っています。

代表的な情報は次の通りです。

|情報|意味|
|---|---|
|Subject / SAN|証明書の対象となるドメインなど|
|Public Key|公開鍵|
|Issuer|証明書を発行した認証局|
|Validity|有効期間|
|Digital Signature|認証局による電子署名|

イメージとしては、

```text
┌──────────────────────┐
│ TLS Certificate      │
│                      │
│ example.com           │
│                      │
│ 公開鍵                │
│ 有効期限              │
│ 発行者：○○ CA         │
│                      │
│ CAの電子署名          │
└──────────────────────┘
```

という**インターネット上の身分証明書**に近いものです。

---

# 4. 誰が証明書を発行するの？

証明書を発行する組織を、

**CA（Certificate Authority：認証局）**

と呼びます。

代表例として、

- Let's Encrypt
    
- DigiCert
    
- Sectigo
    

などがあります。

証明書はサーバー運営者が勝手に、

```text
「私はexample.comです！」
```

と名乗るだけでは意味がありません。

信頼された第三者であるCAから、

```text
CA
 │
 │ 電子署名
 ▼
example.comの証明書
```

と保証してもらうことで意味を持ちます。

---

# 5. CAはどうやってドメインを確認する？

証明書を発行する前にCAは、

> 「この人、本当にexample.comを管理しているの？」

を確認します。

代表的なのが **ACME Challenge** です。

## HTTP-01

指定されたデータを、

```text
http://example.com/.well-known/acme-challenge/...
```

から取得できるようにします。

CAがアクセスできれば、

```text
このサーバーを管理できている
        ↓
ドメインを管理している可能性が高い
```

と判断できます。

---

## DNS-01

DNSへ指定されたTXTレコードを登録します。

```text
_acme-challenge.example.com
        ↓
TXTレコード
        ↓
指定された値
```

CAがDNSを確認できれば認証成功です。

DNS-01は、

```text
*.example.com
```

のような**ワイルドカード証明書**にも利用できます。

---

# 6. 信頼の連鎖（Chain of Trust）

ここがTLS証明書を理解するうえで重要です。

証明書には階層があります。

```text
Root CA
   │
   │ 署名
   ▼
Intermediate CA
   │
   │ 署名
   ▼
Server Certificate
   │
   ▼
example.com
```

## ルート証明書

信頼の一番上にある証明書です。

ブラウザやOSには、

```text
「このCAは信頼してよい」
```

というルート証明書の一覧があらかじめ登録されています。

これを**トラストストア（Trust Store）**と呼びます。

---

## 中間証明書

ルートCAから署名された証明書です。

通常、ルートCAが直接すべてのサーバー証明書を発行するのではなく、

```text
Root CA
   ↓
Intermediate CA
   ↓
Server Certificate
```

という階層構造にします。

---

## サーバー証明書

実際に、

```text
example.com
```

などのサーバーで利用する証明書です。

**リーフ証明書（Leaf Certificate）**とも呼ばれます。

---

# 7. ブラウザはどうやって信用する？

ブラウザは、

```text
example.comの証明書
        ↓
誰が署名した？

Intermediate CA
        ↓
誰が署名した？

Root CA
        ↓

ブラウザのTrust Storeに存在する？

        ↓
       YES
        ↓
信頼できる
```

というように確認します。

これが、

**Chain of Trust（信頼の連鎖）**

です。

---

# 8. 公開鍵と秘密鍵

TLSでは**公開鍵暗号**が重要になります。

サーバーには、

```text
公開鍵 🔓
秘密鍵 🔑
```

というペアがあります。

### 公開鍵

他人に公開してよい鍵です。

証明書にも公開鍵の情報が含まれています。

### 秘密鍵

サーバー運営者だけが厳重に管理する鍵です。

```text
公開鍵
   ↕
ペア
   ↕
秘密鍵
```

秘密鍵が漏洩すると、サーバーになりすますなどの重大な問題につながるため、**秘密鍵は絶対に外部へ公開してはいけません。**

---

# 9. TLSハンドシェイク

HTTPS通信を開始するときには、

**TLS Handshake**

という手続きが行われます。

大まかには、

```text
ブラウザ
   │
   │ Client Hello
   ▼
サーバー
   │
   │ Server Hello
   │ Certificate
   ▼
ブラウザ
```

ブラウザは証明書について、

```text
✓ 信頼できるCA？
✓ 電子署名は正しい？
✓ 有効期限内？
✓ 接続先ドメインと一致？
```

などを確認します。

問題なければ安全な鍵共有を行い、その後の通信を暗号化します。

```text
TLS Handshake
      ↓
鍵を安全に共有
      ↓
共通鍵を確立
      ↓
HTTPS通信
      ↓
🔐 暗号化された通信
```

実際のTLS 1.3などでは、証明書の公開鍵そのもので通信データを暗号化するというより、**証明書によってサーバーを認証し、鍵交換によって共通鍵を安全に確立する**と理解すると正確です。

---

# 10. なぜ共通鍵を使う？

公開鍵暗号は安全ですが、処理が比較的重いという特徴があります。

そのため、

```text
最初
↓
公開鍵暗号などを利用して
安全に鍵交換

↓

共通鍵を作る

↓

その後
↓
高速な共通鍵暗号で通信
```

という方式が使われます。

つまり、

```text
公開鍵暗号
→ 認証・鍵交換を安全にする

共通鍵暗号
→ 実際の大量通信を高速に暗号化
```

という役割分担です。

---

# 11. 証明書の種類

## DV（Domain Validation）

ドメインを管理していることを確認します。

```text
example.comを管理できる？
        ↓
YES
        ↓
証明書発行
```

Let's Encryptも基本的にこのタイプです。

---

## OV（Organization Validation）

ドメインだけでなく、

**組織が実在すること**

も確認します。

---

## EV（Extended Validation）

さらに厳格な組織確認を行います。

以前はブラウザのアドレスバーで特別な表示がされることもありましたが、現在の主要ブラウザでは表示上の差はかなり小さくなっています。

---

# 12. ワイルドカード証明書

例えば、

```text
*.example.com
```

という証明書を取得すると、

```text
api.example.com
admin.example.com
shop.example.com
www.example.com
```

など、複数のサブドメインをまとめてカバーできます。

ただし通常、

```text
example.com
```

そのものは `*.example.com` とは別扱いなので、必要なら両方を証明書の対象に含めます。

---

# 13. 自己署名証明書

CAを利用せず、自分自身で署名することもできます。

これが、

**自己署名証明書（Self-Signed Certificate）**

です。

暗号化自体はできますが、

```text
ブラウザ

「この証明書を発行した人を
 信頼していいのか分からない」
```

となります。

そのため一般的なブラウザでは警告が表示されます。

開発環境や社内システムなどでは利用されることがあります。

---

# 14. 証明書には有効期限がある

証明書には有効期限があります。

期限切れになると、

```text
ブラウザ
   ↓
証明書を確認
   ↓
期限切れ
   ↓
⚠ 安全な接続ではありません
```

となります。

そのため実務では、

**証明書の自動更新**

が非常に重要です。

Let's EncryptなどではACMEを利用して更新を自動化するのが一般的です。

---

# 15. AWSではどうなる？

AWSでは **AWS Certificate Manager（ACM）** を利用すると、証明書の発行・管理をかなり自動化できます。

例えば、

```text
Internet
   ↓
Route 53
   ↓
ALB
   │
   │ TLS証明書
   │ （ACM）
   ↓
EC2
   ↓
Application
```

という構成があります。

この場合、HTTPS通信のTLS処理をALBで終わらせる、

**TLS Termination（TLS終端）**

という構成も一般的です。

```text
Browser
   │
   │ HTTPS :443
   ▼
ALB
   │
   │ TLS証明書
   │ TLS終端
   ▼
EC2
```

そのため、必ずしもEC2自体に公開用証明書を直接配置する必要はありません。

---

# 16. HTTPとHTTPSの違い

最終的にはここにつながります。

```text
HTTP
Browser
   │
   │ 平文通信
   ▼
Server


HTTPS
Browser
   │
   │ TLS
   │ 🔐 暗号化
   ▼
Server
```

HTTPSとは、

**HTTP over TLS**

つまり、

> HTTP通信をTLSによって安全にしたもの

と考えると分かりやすいです。

---

# 17. 全体像

証明書の仕組みを一枚でまとめると、

```text
        Certificate Authority
               CA
                │
                │ 証明書を発行・署名
                ▼
        ┌──────────────┐
        │ example.com  │
        │ Certificate  │
        └──────────────┘
                │
                │ 設置
                ▼
             Server
                ▲
                │
                │ HTTPS
                │
             Browser
                │
                ├─ CAを信頼できる？
                ├─ 署名は正しい？
                ├─ ドメインは一致？
                └─ 有効期限内？
                         │
                         ▼
                        OK
                         │
                         ▼
                 TLS Handshake
                         │
                         ▼
                  共通鍵を確立
                         │
                         ▼
                  🔐 HTTPS通信
```

## 最低限これだけ覚える

```text
HTTPS
 │
 └─ TLS
     │
     ├─ 証明書
     │    └─「このサーバーは本物？」
     │
     ├─ CA
     │    └─「この証明書を保証します」
     │
     ├─ 公開鍵 / 秘密鍵
     │    └─ 認証や安全な鍵交換
     │
     └─ 共通鍵
          └─ 実際の通信を高速に暗号化
```

**「証明書＝暗号化そのもの」ではなく、TLSの中で相手の身元を確認し、安全な暗号化通信を成立させるための重要な仕組み**と理解しておくのがポイントです。
