## エンジニアにおける「設計」とは？

**設計**とは、

> **システムをどのような構成・仕組み・ルールで作るかを、実装前に決めること**です。

簡単に言うと、

**「いきなりコードを書くのではなく、先に作り方を決める作業」**です。

---

## なぜ設計が必要？

設計せずに作り始めると、

- 後から仕様が合わない
- 同じ処理を何度も作る
- 修正しにくいコードになる
- 開発者ごとに作り方がバラバラになる
- セキュリティや性能の問題が起きる

といったトラブルが起こりやすくなります。

設計を行うことで、**チーム全員が同じ完成イメージを持って開発できる**ようになります。

---

## 設計で決めること

例えば、予約システムを作る場合は次のようなことを決めます。

| 設計する内容  | 具体例               |
| ------- | ----------------- |
| 画面      | 予約画面、確認画面、完了画面    |
| データ     | ユーザー、予約、商品、決済情報   |
| 処理の流れ   | 予約入力 → 決済 → 予約確定  |
| [[API]] | 予約登録API、予約取得API   |
| 権限      | 一般ユーザーと管理者で何ができるか |
| インフラ    | AWS、サーバー、データベース構成 |
| エラー処理   | 決済だけ成功した場合に返金するか  |

---

## 設計の主な種類

### 1. 基本設計

**ユーザーや顧客から見える部分を決める設計**です。

例：

- どんな画面があるか
- どんな機能があるか
- 画面をどう移動するか
- 入力項目や表示内容
- 外部システムとの連携

「何を作るか」を決める段階です。

---

### 2. 詳細設計

**エンジニアが実際にどう作るかを決める設計**です。

例：

- テーブル構成
- APIのURLやリクエスト内容
- クラスや関数の構成
- エラー処理
- SQL
- 処理の手順

「どう作るか」を具体化する段階です。

---

## 設計から実装までの流れ

```
要件定義
「何が必要か」
    ↓
基本設計
「どんな仕組みにするか」
    ↓
詳細設計
「どう実装するか」
    ↓
実装
「実際にコードを書く」
    ↓
テスト
「正しく動くか確認する」
```

---

## 具体例

「予約一覧を表示する機能」を作る場合です。

### 要件

- ユーザーは自分の予約を確認できる

### 基本設計

- マイページに予約一覧画面を作る
- 予約日時、商品名、金額、状態を表示する
- 新しい予約から順番に表示する

### 詳細設計

- `reservations` テーブルから取得する
- ログインユーザーのIDで絞り込む
- `created_at DESC` で並び替える
- `/api/reservations` APIを作る

### 実装

```
SELECT *
FROM reservations
WHERE user_id = 100
ORDER BY created_at DESC;
```

このように、**設計で決めた内容をコードに落とし込む**のが実装です。

---

## 良い設計とは？

良い設計は、単に動くだけではなく、

- 分かりやすい
- 修正しやすい
- 機能を追加しやすい
- 再利用しやすい
- 障害が起きにくい
- セキュリティを考慮している

といった特徴があります。

---

## 設計書とは？

設計した内容を記録した資料を**設計書**と呼びます。

代表例：

- 画面設計書
- 画面遷移図
- ER図
- テーブル定義書
- API仕様書
- シーケンス図
- インフラ構成図
- バッチ処理設計書

ただし、実務では必ずしも大きな文書を作るとは限りません。小規模開発では、Markdown、Figma、Notion、OpenAPI、コード上の型定義などで設計を残すこともあります。

---

## 一言でいうと

**エンジニアにおける設計 =「システムを安全・効率的・保守しやすく作るために、実装前に構成や処理方法を決めること」**です。

特に重要なのは、次の違いです。

- **要件定義**：何が必要か
- **設計**：どういう仕組みにするか
- **実装**：実際にコードを書く
