| **ルーティング**         | 通信をどこへ送るか決める       | ネットワーク            |

| **DNS**            | ドメイン→IPなどを変換       | Route 53          |

| **HTTP / HTTPS**   | Web通信のプロトコル        | Web               |
| **TLS**            | HTTPSの暗号化を支える仕組み   | 証明書               |
| **Firewall**       | 通信を許可・拒否           | セキュリティ            |
| **Security Group** | AWSの仮想ファイアウォール     | EC2               |
| **Load Balancer**  | アクセスを複数サーバーへ分散     | ALBなど             |
| **Reverse Proxy**  | リクエストを代理で後ろへ渡す     | nginx             |
| **冗長化**            | 同じ役割を複数用意          | 障害対策              |
| **可用性**            | システムが使い続けられる度合い    | インフラ設計            |
| **HA**             | 高い可用性を実現する考え方      | サーバー              |
| **フェイルオーバー**       | 障害時に予備へ切り替える       | 冗長化               |
| **フェイルバック**        | 復旧後に元へ戻す           | 障害復旧              |
| **スケールアップ**        | 1台を強くする            | CPU・メモリ増強         |
| **スケールアウト**        | サーバー台数を増やす         | Webサーバー           |
| **オートスケーリング**      | 負荷に応じて台数を自動変更      | AWS               |
| **プロビジョニング**       | サーバーなどを準備する        | インフラ構築            |
| **IaC**            | インフラをコードで管理        | Terraform         |
| **コンテナ**           | アプリ実行環境をまとめる       | Docker            |
| **オーケストレーション**     | 大量のコンテナを管理         | Kubernetes        |
| **CI/CD**          | テスト・デプロイなどを自動化     | GitHub Actions    |
| **デプロイ**           | 作ったものを実際の環境へ配置     | 本番リリース            |
| **監視**             | システムが正常か確認         | CloudWatch        |
| **メトリクス**          | CPU使用率などの数値        | 監視                |
| **ログ**             | システムの動作記録          | 障害調査              |
| **アラート**           | 異常時に通知する           | 監視                |
| **死活監視**           | サーバーが生きているか確認      | 運用                |
| **ヘルスチェック**        | サービスが正常応答するか確認     | ALBなど             |
| **バックアップ**         | データを別に保存           | 障害対策              |

## バックエンドとインフラは結構つながる

完全に別物というより、

```
ユーザー
   ↓
DNS
   ↓
Load Balancer
   ↓
Web / Backend Server
   ↓
API
   ↓
Database
```

という一つのシステムを**違うレイヤーから見ている**感じです。

例えば、

```
https://example.com/api/users
```

にアクセスした場合、

```
ブラウザ
   │
   │ DNS
   ▼
example.com → IPアドレス
   │
   ▼
Internet
   │
   ▼
Firewall / Security Group
   │
   ▼
Load Balancer
   │
   ▼
nginx
   │
   ▼
Backend
   │
   │ SQL
   ▼
Database
```

となります。

ここで、

**バックエンドエンジニア**は、

```
API
Controller
Service
Repository
SQL
Transaction
Cache
```

あたりを深く見る。

一方、**インフラ・クラウドエンジニア**は、

```
DNS
IP
Subnet
Routing
Firewall
Load Balancer
Server
冗長化
監視
Backup
```

あたりを深く見る、という違いがあります。

## インフラ記事を読むなら特に重要な「セット」

最初はこの順番で理解するとかなりつながります。

```
① ネットワーク

IPアドレス
 ↓
サブネット
 ↓
CIDR
 ↓
ルーティング
 ↓
デフォルトゲートウェイ
 ↓
DNS
 ↓
ポート
 ↓
TCP / UDP
 ↓
Firewall
```

次に、

```
② サーバー

Linux
 ↓
プロセス
 ↓
サービス
 ↓
SSH
 ↓
Webサーバー
 ↓
nginx
 ↓
ログ
```

そしてクラウド。

```
③ AWS

リージョン / AZ
 ↓
VPC
 ↓
Subnet
 ↓
Route Table
 ↓
Internet Gateway
 ↓
NAT Gateway
 ↓
Security Group
 ↓
EC2
 ↓
ALB
 ↓
Route 53
```

さらに運用・設計。

```
④ インフラ設計・運用

冗長化
 ↓
HA
 ↓
Load Balancing
 ↓
Auto Scaling
 ↓
Monitoring
 ↓
Backup
 ↓
Failover
 ↓
RTO / RPO
 ↓
Disaster Recovery
```

最後に今のモダンなインフラだと、

```
⑤ Infrastructure as Code / DevOps

Git
 ↓
CI/CD
 ↓
Docker
 ↓
Terraform
 ↓
IaC
 ↓
Kubernetes
 ↓
Observability
```

あたりが出てきます。

特に技術ブログを読むうえでは、**「SPOF」「冗長化」「可用性」「冪等性」「疎結合」「ステートレス」「ボトルネック」「オブザーバビリティ」**みたいな、製品名ではない**「考え方を表す技術用語」**を覚えていくと理解力が一段上がります。

このあたりは「アンチパターン」と同じく、AWSのサービス名を覚えるよりも、いろんな技術記事で横断的に使える知識です。
