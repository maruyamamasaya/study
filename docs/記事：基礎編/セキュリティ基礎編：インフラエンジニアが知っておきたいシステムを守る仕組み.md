## セキュリティとは

インフラにおけるセキュリティとは、簡単にいうと、

**「許可された人だけが、許可された方法で、必要なシステムやデータを利用できる状態を作ること」**

です。

Webサービスはインターネットにつながっているため、世界中のコンピュータから通信できる可能性があります。

何も対策しなければ、

- 不正アクセスされる
    
- パスワードを盗まれる
    
- データを閲覧される
    
- データを書き換えられる
    
- サーバーを不正利用される
    

といった問題につながります。

そのためインフラエンジニアは、

```text
誰がアクセスできるのか

どこからアクセスできるのか

何を操作できるのか

通信内容は安全なのか
```

といったことを考えてインフラを設計します。

---

# セキュリティの基本的な考え方

インフラのセキュリティでは、

**「全部禁止して、必要なものだけ許可する」**

という考え方が基本です。

例えばWebサーバーなら、

```text
インターネット
      ↓
443 HTTPS → 許可
80 HTTP   → HTTPSへ転送
22 SSH    → 管理者のみ
3306 MySQL → 外部から禁止
```

といった設定にします。

「必要になるかもしれないから全部開けておく」

のではなく、

**必要な通信だけを許可する**

ことが重要です。

---

# 1. Firewall

Firewallは、

**ネットワーク通信を許可するか、拒否するかを制御する仕組み**

です。

日本語では「防火壁」という意味があります。

ネットワークの入口に壁を作り、

```text
この通信 → 通してよい

この通信 → 通してはいけない
```

と判断するイメージです。

---

## Firewallとポート

Firewallを理解するには、ネットワーク基礎で学んだ**ポート**が重要です。

例えばサーバーでは、

|ポート|用途|
|--:|---|
|22|SSH|
|80|HTTP|
|443|HTTPS|
|3306|MySQL|
|5432|PostgreSQL|

などが使われます。

Webサーバーなら、

```text
443
↓
インターネットから許可
```

とする一方、

データベースの

```text
3306
↓
インターネットから禁止
```

とすることができます。

---

## なぜDBを直接公開しないのか

例えば、

```text
インターネット
      ↓
MySQL :3306
```

という構成にすると、世界中からDBへの接続を試される可能性があります。

そのため、

```text
インターネット
      ↓
Webサーバー
      ↓
MySQL
```

という構成にします。

さらに、

```text
Webサーバー
→ MySQLへの接続を許可

その他
→ MySQLへの接続は禁止
```

と制限します。

これによって、攻撃される範囲を小さくできます。

---

# AWSのSecurity Group

AWSでは、EC2やRDSなどの通信を制御するために、

**Security Group**

がよく利用されます。

例えばWebサーバーなら、

```text
Security Group

443
→ インターネットから許可

22
→ 管理用ネットワークのみ許可
```

DBなら、

```text
3306
→ Webサーバーからのみ許可
```

といった設定ができます。

つまりSecurity Groupは、

**AWS上のFirewallのような役割**

と考えると分かりやすいです。

---

# 2. HTTPとHTTPS

Webサイトでは、

```text
http://
```

または、

```text
https://
```

というURLを使います。

HTTPは、

**ブラウザとWebサーバーが通信するためのルール**

です。

しかしHTTPだけでは、通信内容が安全に保護されません。

そこで使われるのがHTTPSです。

---

# HTTPSとは

HTTPSは、

**HTTP通信をTLSという仕組みで保護したもの**

です。

例えば、

```text
ブラウザ
    ↓
HTTPS
    ↓
Webサーバー
```

では、通信内容が暗号化されます。

そのため途中で通信を見られても、内容を簡単に読み取られないようにできます。

---

## HTTPの場合

例えばログインするとき、

```text
メールアドレス
パスワード
```

などをサーバーへ送信します。

通信が適切に保護されていないと、途中で情報を盗み見られる危険があります。

---

## HTTPSの場合

HTTPSでは、

```text
ブラウザ
   ↓
🔒 暗号化
   ↓
インターネット
   ↓
🔒 復号
   ↓
Webサーバー
```

という形で通信します。

そのため、

- ログイン情報
    
- 個人情報
    
- 決済情報
    
- API通信
    

などを安全にやり取りするためにHTTPSが重要になります。

現在のWebサービスでは、HTTPSを利用することが基本です。

---

# TLS証明書

HTTPSを利用するために重要なのが、

**TLS証明書**

です。

以前は「SSL証明書」という呼び方も広く使われていました。

証明書には、

**「このWebサイトは、このドメインの正当な接続先である」**

ことを確認する役割があります。

例えば、

```text
https://example.com
        ↓
証明書確認
        ↓
example.com用の正しい証明書？
        ↓
OK
        ↓
暗号化通信
```

という流れになります。

---

# AWSでHTTPSを使う場合

AWSでは、

**AWS Certificate Manager（ACM）**

を利用して証明書を管理できます。

例えば、

```text
ユーザー
   ↓
HTTPS
   ↓
ALB
   ↓
EC2
```

という構成なら、

```text
ACM
 ↓
TLS証明書
 ↓
ALB
```

という形で証明書を設定できます。

---

# 3. 認証と認可

セキュリティでは、

**認証**

と

**認可**

という言葉がよく登場します。

似ていますが意味が違います。

---

## 認証

認証とは、

**「あなたは誰ですか？」**

を確認することです。

例えば、

```text
メールアドレス
+
パスワード
```

でログインするのが認証です。

ほかにも、

- パスワード
    
- ワンタイムパスワード
    
- MFA
    
- 生体認証
    

などがあります。

---

## 認可

認可とは、

**「あなたは何をしていいですか？」**

を決めることです。

例えば、

```text
一般ユーザー
→ 商品を見る
→ 予約する

管理者
→ 商品を見る
→ 商品を編集する
→ ユーザーを管理する
```

という違いです。

つまり、

```text
認証
↓
誰なのか確認

認可
↓
何を許可するか決める
```

と覚えると分かりやすいです。

---

# 4. 権限管理

Linux、AWS、データベースなど、インフラのさまざまな場所で権限管理が行われます。

例えばLinuxなら、

```text
一般ユーザー
↓
通常のファイルだけ操作

管理者
↓
システム設定も変更可能
```

といった権限があります。

Linuxでは、

```text
root
sudo
chmod
chown
```

などが関係します。

---

# 最小権限の原則

セキュリティで非常に重要なのが、

**最小権限の原則**

です。

これは、

**「仕事に必要な最低限の権限だけを与える」**

という考え方です。

例えば、

```text
開発者A

必要：
S3のファイルを見る

不要：
EC2削除
RDS削除
IAM変更
```

なら、S3を見る権限だけを与えます。

```text
必要だから管理者権限を全部与える
```

という運用は避けます。

---

# AWS IAM

AWSでは、

**IAM（Identity and Access Management）**

を使って権限を管理します。

例えば、

```text
開発者A
→ EC2を見るだけ

開発者B
→ S3を操作可能

管理者
→ AWS全体を管理
```

といった設定ができます。

AWSでは非常に多くのサービスを操作できるため、IAMによる権限管理が重要になります。

---

# 5. パスワードと秘密情報

システムでは、

- パスワード
    
- APIキー
    
- DB接続情報
    
- アクセストークン
    
- 秘密鍵
    

などの重要な情報を扱います。

こうした情報を、

**Secrets（シークレット）**

と呼ぶことがあります。

---

## ソースコードに書かない

例えば、

```javascript
const password = "mypassword123";
```

のようにパスワードを直接コードへ書いてGitHubへpushするのは危険です。

代わりに、

```text
環境変数
Secrets Manager
GitHub Secrets
```

などを利用します。

例えば、

```text
アプリ
 ↓
環境変数
 ↓
DB_PASSWORD
```

という形で取得します。

---

# 6. SSHのセキュリティ

Linuxサーバーへ接続するときによく利用されるのがSSHです。

```text
自分のPC
   ↓
SSH :22
   ↓
Linuxサーバー
```

SSHも誰でも接続できる状態にするのではなく、

- SSH鍵を利用する
    
- 接続元IPを制限する
    
- 不要なrootログインを制限する
    
- 必要なユーザーだけ許可する
    

などの対策を行います。

---

# 7. アップデート

OSやソフトウェアには、後からセキュリティ上の問題が見つかることがあります。

この問題を、

**脆弱性**

と呼びます。

例えば、

```text
Linux
nginx
Node.js
ライブラリ
Docker Image
```

などに脆弱性が見つかることがあります。

そのため、

```text
脆弱性発見
   ↓
修正版公開
   ↓
アップデート
```

という対応が必要になります。

---

# 8. ログと監視

セキュリティでは、

**何が起きたのか記録すること**

も重要です。

例えば、

```text
誰がログインしたか

どこからアクセスされたか

何を操作したか

ログインに何回失敗したか
```

などをログとして記録します。

異常なアクセスを検知した場合、

```text
大量のログイン失敗
       ↓
監視システム
       ↓
アラート
       ↓
管理者が確認
```

といった対応ができます。

---

# 9. バックアップもセキュリティ

セキュリティというと「攻撃を防ぐこと」だけを考えがちですが、データを守ることも重要です。

例えば、

```text
誤操作
ランサムウェア
システム障害
データ破損
```

などによってデータが失われる可能性があります。

そのため、

```text
本番DB
   ↓
バックアップ
   ↓
別の場所へ保存
```

などの対策を行います。

問題が発生した場合に、

**正常な状態へ戻せること**

も重要なセキュリティ対策です。

---

# セキュリティは何重にも作る

セキュリティでは、一つの対策だけに頼らないことが重要です。

例えば、

```text
インターネット
      ↓
Firewall
      ↓
HTTPS
      ↓
認証
      ↓
権限管理
      ↓
アプリケーション
      ↓
Private Network
      ↓
データベース
      ↓
バックアップ
```

というように、複数の対策を組み合わせます。

これを、

**多層防御**

と呼びます。

一つの対策が突破されても、次の対策で守れるようにする考え方です。

---

# AWSで考えるセキュリティ

AWSでWebサービスを作る場合なら、

```text
インターネット
      ↓
Route 53
      ↓
HTTPS
      ↓
ALB
      ↓
Security Group
      ↓
EC2
      ↓
Security Group
      ↓
RDS
```

といった構成があります。

さらに、

```text
IAM
→ AWS操作の権限管理

ACM
→ TLS証明書

CloudWatch
→ ログ・監視

Secrets Manager
→ パスワードなどの管理
```

といった仕組みを組み合わせます。

---

# セキュリティ事故を考えるときの基本

例えば、

```text
Webサーバーへ不正アクセスされた
```

場合を考えてみます。

確認することは、

```text
どこからアクセスされた？
       ↓
どのポートから入った？
       ↓
どのユーザーが使われた？
       ↓
どの権限を持っていた？
       ↓
何を操作された？
       ↓
他のサーバーへアクセスされた？
       ↓
データは変更された？
```

などです。

ここでも、

- Linux
    
- ネットワーク
    
- ログ
    
- AWS
    
- データベース
    

といった知識が必要になります。

---

# セキュリティで最初に覚えたいこと

最初は、

```text
セキュリティとは
      ↓
IP・ポート
      ↓
Firewall
      ↓
HTTP / HTTPS
      ↓
TLS証明書
      ↓
認証・認可
      ↓
ユーザー・権限
      ↓
最小権限
      ↓
秘密情報
      ↓
ログ・監視
      ↓
バックアップ
```

という順番で理解すると分かりやすくなります。

---

# インフラ全体とのつながり

セキュリティは独立した技術ではありません。

```text
Linux
→ ユーザー・ファイル権限

ネットワーク
→ Firewall・ポート

Web
→ HTTPS・TLS

AWS
→ Security Group・IAM

データベース
→ 接続制限・DB権限

Docker
→ コンテナ・Imageの安全性

CI/CD
→ Secrets・デプロイ権限
```

というように、**すべてのインフラ技術にセキュリティが関係します。**

---

# まとめ

インフラにおけるセキュリティとは、

**システムやデータを、不正なアクセスや操作から守るための仕組み**

です。

特に基本となるのが、

```text
Firewall
↓
どの通信を許可するか

HTTPS
↓
通信内容を安全にする

認証
↓
誰なのか確認する

権限管理
↓
何を操作できるか決める
```

という考え方です。

そして最も重要なのは、

**「必要な通信・ユーザー・権限だけを許可する」**

という考え方です。

インフラエンジニアは、サーバーを「動く状態」にするだけではなく、

**安全に動かし続けられる状態を作ること**

まで考える必要があります。
