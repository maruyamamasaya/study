冗長化とは、

> **同じ役割を持つ機器やシステムを複数用意して、1つが故障してもサービスを継続できるようにすること**

です。

簡単に言うと、

**「予備を用意して、止まりにくくする仕組み」**

です。

---

# なぜ冗長化が必要なのか

サーバーが1台だけの場合、その1台が故障するとサービス全体が止まります。

```
利用者
   │
   ▼
EC2 1台
   │
   × 故障
   │
   ▼
サイト停止
```

これを**単一障害点**といいます。

英語では、

```
SPOF
Single Point of Failure
```

と呼びます。

冗長化では、同じ役割のサーバーを複数用意します。

```
          ALB
        ／   ＼
       ▼     ▼
    EC2①   EC2②
```

EC2①が故障しても、EC2②が処理を続けられます。

---

# 冗長化とフェイルオーバーの違い

この2つはセットで使われますが、意味は少し違います。

|用語|意味|
|---|---|
|冗長化|予備を用意しておくこと|
|フェイルオーバー|障害時に予備へ切り替えること|

例えば、

```
EC2①
EC2②
```

を用意するのが**冗長化**です。

EC2①が故障したときに、

```
EC2① ×
   ↓
EC2②へ切り替え
```

となるのが**フェイルオーバー**です。

つまり、

> 冗長化は「構成」、フェイルオーバーは「切り替え動作」

と考えると分かりやすいです。

---

# 冗長化の基本構成

## アクティブ・アクティブ

複数のサーバーを、普段から同時に使う構成です。

```
             ALB
          ／     ＼
         ▼       ▼
     EC2①稼働  EC2②稼働
```

両方のサーバーが利用者の処理を担当します。

### メリット

- サーバーを無駄なく使える
- 負荷分散できる
- 1台が故障しても残りで継続できる

### デメリット

- データやセッションの共有が必要
- システム構成が複雑になる

Webサーバーでは、アクティブ・アクティブがよく使われます。

---

## アクティブ・スタンバイ

普段使うメインと、待機する予備を用意する構成です。

```
メインサーバー：稼働中

予備サーバー：待機中
```

障害時に予備へ切り替えます。

```
メイン ×
   ↓
予備サーバーが稼働
```

### メリット

- 構成が比較的分かりやすい
- データベースなどに向いている

### デメリット

- 待機中のサーバーを普段は活用しにくい
- 切り替えに少し時間がかかる場合がある

RDSのMulti-AZなどが代表例です。

---

# AWSでの冗長化

## 1. EC2の冗長化

EC2を複数台用意し、ALBでアクセスを分散します。

```
利用者
   │
   ▼
  ALB
 ／   ＼
▼     ▼
EC2① EC2②
```

ALBはヘルスチェックを行い、異常なEC2にはアクセスを送らなくなります。

---

## 2. AZを分けた冗長化

同じAZにEC2を2台置くだけでは、AZ全体の障害に弱くなります。

```
東京リージョン

AZ-a
├─ EC2①
└─ EC2②
```

AZ-aが停止すると、両方とも使えません。

そのため、実務では別のAZに配置します。

```
東京リージョン

AZ-a            AZ-c
EC2①            EC2②
  └──── ALB ─────┘
```

これを**Multi-AZ構成**と呼びます。

---

## 3. RDSの冗長化

RDSでは、Multi-AZを有効にすると、別AZに待機用データベースが用意されます。

```
AZ-a                    AZ-c
プライマリDB  ─同期→  スタンバイDB
```

プライマリDBに障害が起きると、

```
プライマリDB ×
       ↓
スタンバイDBへ切り替え
```

となります。

これは主に**可用性を高めるための構成**です。

読み取り性能を上げるRead Replicaとは目的が異なります。

---

## 4. S3の冗長化

S3は、利用者が通常は意識しなくても、データを複数の設備に分散して保存します。

```
S3へファイル保存
      │
      ├─ 保存先①
      ├─ 保存先②
      └─ 保存先③
```

1つの設備に障害が起きても、データを失いにくい仕組みになっています。

ただし、利用者による誤削除対策には、

- バージョニング
- ライフサイクル
- 別リージョンへのコピー

なども必要です。

---

## 5. Route 53による冗長化

リージョン単位で予備環境を用意する場合は、Route 53を使えます。

```
通常
利用者
   │
   ▼
東京リージョン
```

東京側に障害が起きた場合、

```
利用者
   │
   ▼
大阪リージョン
```

へ切り替える構成です。

これは大規模な災害対策、つまりDRで使われます。

---

# 冗長化する対象

冗長化はサーバーだけではありません。

|対象|冗長化の例|
|---|---|
|Webサーバー|EC2を複数台配置|
|データベース|RDS Multi-AZ|
|ネットワーク|回線やルーターを複数用意|
|ストレージ|データを複数箇所に保存|
|DNS|Route 53で複数接続先を用意|
|リージョン|東京と大阪に環境を用意|
|電源|UPSや非常用電源を用意|

---

# 冗長化のレベル

## サーバー冗長化

```
EC2①
EC2②
```

1台の故障に備えます。

---

## AZ冗長化

```
AZ-a：EC2①
AZ-c：EC2②
```

データセンター単位の障害に備えます。

---

## リージョン冗長化

```
東京リージョン
大阪リージョン
```

大規模障害や災害に備えます。

冗長化の範囲が広いほど、障害には強くなりますが、費用と構築難易度も上がります。

---

# 冗長化しても完全に止まらないわけではない

冗長化すれば絶対に停止しない、というわけではありません。

例えば、EC2を2台にしても、両方が同じデータベースを利用している場合、

```
EC2① ─┐
       ├─ DB 1台
EC2② ─┘
```

データベースが故障するとサービスは止まります。

```
EC2① ─┐
       ├─ DB ×
EC2② ─┘
```

そのため、システム全体を見て、単一障害点をなくす必要があります。

```
Route 53
   │
   ▼
  ALB
 ／   ＼
EC2①  EC2②
   │
   ▼
RDS Multi-AZ
```

---

# バックアップとの違い

冗長化とバックアップも目的が違います。

|項目|冗長化|バックアップ|
|---|---|---|
|主な目的|サービスを止めない|データを元に戻す|
|障害時|予備へ切り替える|保存データから復元する|
|復旧速度|比較的速い|復元に時間がかかる|
|誤削除への対応|弱い場合がある|過去データから戻せる|

例えばデータを誤って削除すると、その削除内容まで予備DBへ同期されることがあります。

```
プライマリDBで削除
       ↓
スタンバイDBにも同期
```

そのため、

> **冗長化とバックアップは両方必要**

です。

---

# 冗長化のメリット

- サーバーが故障してもサービスを継続しやすい
- メンテナンス中も別サーバーで対応できる
- 負荷分散できる
- 災害やデータセンター障害に備えられる
- システムの可用性を高められる

---

# 冗長化のデメリット

- サーバー台数が増えて料金が上がる
- 設定や監視が複雑になる
- データ同期を考える必要がある
- 切り替えテストが必要になる
- 障害時に正しく切り替わらない可能性もある

冗長化は、機器を2台置くだけで完成ではありません。

実際に障害を想定して、

```
EC2を停止する
   ↓
ALBが切り離すか確認
   ↓
サービスが継続するか確認
```

というテストも重要です。

---

# Yasukariのような予約サイトで考えると

冗長化していない場合は、

```
利用者
   │
   ▼
ALB
   │
   ▼
EC2 1台
   │
   ▼
予約システム
```

EC2が停止すると、予約できなくなります。

冗長化すると、

```
利用者
   │
   ▼
ALB
 ／   ＼
▼     ▼
EC2① EC2②
AZ-a  AZ-c
   │
   ▼
DynamoDB
```

EC2①が停止しても、EC2②で予約を続けられます。

ただし、EC2を複数台にする場合は、

- アプリのファイルを両方へ配布する
- セッションをEC2内だけに保存しない
- 画像はS3に保存する
- ログはCloudWatchへ送る

などの工夫も必要です。

# 関連用語

|用語|意味|
|---|---|
|冗長化|予備を用意する|
|フェイルオーバー|障害時に予備へ切り替える|
|フェイルバック|復旧後に元へ戻す|
|高可用性・HA|サービスを止まりにくくする|
|SPOF|そこが壊れると全体が止まる箇所|
|Multi-AZ|複数のAZに分散する|
|レプリケーション|データを別環境へ複製する|
|DR|大規模災害から復旧する仕組み|

---

# まとめ

- **冗長化は、同じ役割のシステムを複数用意すること**
- **目的は、障害が起きてもサービスを止めないこと**
- **障害時の切り替え処理をフェイルオーバーという**
- **AWSではALB、複数EC2、RDS Multi-AZなどで実現する**
- **サーバーだけでなく、DBやネットワークも含めて考える**
- **冗長化とバックアップは別物なので、両方必要**

## 一言でまとめると

> **冗長化は「1つ壊れても大丈夫なように、予備を用意しておく設計」です。**
