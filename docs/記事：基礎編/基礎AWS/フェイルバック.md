フェイルバック（Failback）とは、

> **障害時に予備環境へ切り替えたあと、元の環境が復旧したら元へ戻すこと**

です。

---

## 全体の流れ

```
通常運転
メインサーバー

   ↓ 障害発生

予備サーバーへ切り替え
＝ フェイルオーバー

   ↓ メイン復旧

元のメインサーバーへ戻す
＝ フェイルバック
```

---

## 具体例

通常はEC2①を使っています。

```
利用者
   │
   ▼
EC2①（メイン）
```

EC2①に障害が起きると、EC2②へ切り替えます。

```
利用者
   │
   ▼
EC2②（予備）
```

その後、EC2①が復旧したら元へ戻します。

```
利用者
   │
   ▼
EC2①（復旧済み）
```

この「元へ戻す処理」がフェイルバックです。

---

## フェイルオーバーとの違い

|用語|意味|
|---|---|
|フェイルオーバー|障害時に予備へ切り替える|
|フェイルバック|復旧後に元の環境へ戻す|

覚え方は、

```
Failover
壊れたので、別環境へ移る

Failback
直ったので、元へ戻る
```

です。

---

## データベースでの例

```
通常

プライマリDB
      │
      ▼
スタンバイDB
```

プライマリDBに障害が起きると、

```
スタンバイDBが
新しいプライマリへ昇格
```

します。

元のDBが復旧したあと、そのDBを再びメインとして使う場合、データを同期して切り戻します。

```
現在のプライマリDB
        │
        ▼
復旧した元のDBへデータ同期
        │
        ▼
接続先を元のDBへ戻す
```

---

## フェイルバックで注意すること

元のサーバーが復旧したからといって、すぐ戻せるとは限りません。

確認することは主に次のとおりです。

- 元のサーバーが本当に正常か
- 予備側で更新されたデータが反映されているか
- 接続先を戻しても問題ないか
- 再び障害が起きないか
- 利用者への影響がないか

特にデータベースでは、予備環境へ切り替えている間にもデータが更新されます。

```
予備DBで予約情報を更新
       ↓
元のDBには最新データがない
```

この状態でそのまま元へ戻すと、データが古くなる可能性があります。

そのため、フェイルバック前には**データ同期**が重要です。

---

# バックアップとは？

バックアップ（Backup）とは、

> **障害や誤操作に備えて、データのコピーを別の場所へ保存すること**

です。

簡単に言うと、

**「何かあったときに戻せるように、データを取っておくこと」**

です。

---

## イメージ

```
現在のデータ
   │
   ▼
コピーを保存
   │
   ▼
バックアップ
```

例えば、

```
予約データ
会員データ
商品データ
画像
設定ファイル
```

などを保存します。

---

## バックアップが必要な理由

例えば、予約データを誤って削除した場合を考えます。

```
予約データ

   ↓ 誤操作

全件削除
```

冗長化していても、削除内容が予備側にも同期される場合があります。

```
メインDBで削除
      ↓
予備DBにも削除が反映
```

この場合、予備DBへ切り替えてもデータは戻りません。

そこで、過去のバックアップから復元します。

```
昨日のバックアップ
      ↓
データを復元
```

---

# リストアとは？

バックアップからデータを戻すことを、

> **リストア（Restore）**

といいます。

```
バックアップを取る
＝ Backup

バックアップから戻す
＝ Restore
```

---

## 例

```
7月30日
データをバックアップ

7月31日
データを誤って削除

   ↓

7月30日の状態へ戻す
＝ リストア
```

---

# バックアップの種類

## 1. フルバックアップ

すべてのデータをコピーします。

```
データ全体
   ↓
すべて保存
```

### メリット

- 復元が分かりやすい
- 1つのバックアップから戻せる

### デメリット

- 時間がかかる
- 保存容量が大きい

---

## 2. 差分バックアップ

最後のフルバックアップから変更されたデータを保存します。

```
月曜日：フルバックアップ
火曜日：月曜日からの変更分
水曜日：月曜日からの変更分
```

復元するときは、

```
月曜日のフル
＋
最新の差分
```

を使います。

---

## 3. 増分バックアップ

前回のバックアップ以降に変更されたデータだけ保存します。

```
月曜日：フル
火曜日：月曜からの変更
水曜日：火曜からの変更
木曜日：水曜からの変更
```

### メリット

- 保存容量が少ない
- バックアップが速い

### デメリット

- 復元時に複数のバックアップが必要
- 復元処理が複雑になりやすい

---

# AWSでのバックアップ例

## RDS

RDSでは、自動バックアップやスナップショットを利用できます。

```
RDS
 │
 ├─ 自動バックアップ
 └─ 手動スナップショット
```

特定時点へ戻すポイントインタイムリカバリも利用できます。

```
10:00 正常
10:15 データ削除
      ↓
10:14の状態へ復元
```

---

## EBS

EC2のディスクであるEBSは、スナップショットを取得できます。

```
EC2
 │
 ▼
EBS
 │
 ▼
スナップショット
```

障害時には、スナップショットから新しいEBSを作成できます。

---

## S3

S3では、バージョニングを有効にすると、古いファイルを残せます。

```
document.pdf
   │
   ├─ バージョン1
   ├─ バージョン2
   └─ バージョン3
```

誤って上書き・削除した場合でも、以前のバージョンへ戻せます。

---

## AWS Backup

AWS Backupは、複数のAWSサービスのバックアップをまとめて管理するサービスです。

```
AWS Backup
   │
   ├─ EBS
   ├─ RDS
   ├─ DynamoDB
   ├─ EFS
   └─ その他
```

バックアップのスケジュールや保存期間を一元管理できます。

---

# 冗長化・フェイルオーバー・バックアップの違い

|用語|目的|例|
|---|---|---|
|冗長化|予備を用意する|EC2を2台配置|
|フェイルオーバー|障害時に予備へ切り替える|EC2①からEC2②へ切替|
|フェイルバック|復旧後に元へ戻す|EC2②からEC2①へ戻す|
|バックアップ|データのコピーを保存する|RDSスナップショット|
|リストア|バックアップから戻す|昨日のDBを復元|

---

# 一連の流れで見ると

```
通常運転
   │
   ▼
障害発生
   │
   ▼
予備環境へ切り替え
＝ フェイルオーバー
   │
   ▼
元の環境を修復
   │
   ▼
元の環境へ戻す
＝ フェイルバック
```

一方、データを失った場合は、

```
データ消失
   │
   ▼
バックアップを確認
   │
   ▼
バックアップから復元
＝ リストア
```

となります。

# Yasukariのような予約サイトで考えると

## サーバー障害

```
EC2①で障害
   │
   ▼
EC2②へ切り替える
＝ フェイルオーバー
   │
   ▼
EC2①を修復
   │
   ▼
EC2①へ戻す
＝ フェイルバック
```

## データ誤削除

```
予約データを誤って削除
   │
   ▼
DynamoDBのバックアップを確認
   │
   ▼
削除前の状態を復元
＝ リストア
```

つまり、

- サーバーが壊れたときはフェイルオーバー
- 元のサーバーへ戻すのがフェイルバック
- データを失ったときはバックアップからリストア

という違いがあります。

# まとめ

## フェイルバック

> **障害時に予備へ切り替えたあと、復旧した元の環境へ戻すこと**

## バックアップ

> **データが消えたり壊れたりした場合に備えて、コピーを保存しておくこと**

## 覚え方

```
フェイルオーバー
壊れたので予備へ行く

フェイルバック
直ったので元へ戻る

バックアップ
データを保存しておく

リストア
保存したデータから戻す
```

冗長化はサービスを止めないための仕組みで、バックアップはデータを失わないための仕組みです。両方を組み合わせることで、障害に強いシステムになります。
