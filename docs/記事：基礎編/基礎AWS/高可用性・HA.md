# 高可用性・HAとは？

HAは、

> **High Availability（ハイ・アベイラビリティ）**

の略です。

日本語では、**高可用性**といいます。

簡単にいうと、

> **システムをできるだけ止まりにくくする考え方・設計**

です。

---

# 可用性とは？

可用性とは、

**「必要なときにシステムを使える状態か」**

という意味です。

例えば予約サイトなら、

```
利用者が予約したい
        ↓
サイトが正常に開く
        ↓
予約できる
```

この状態なら、可用性が保たれています。

反対に、

```
サーバー障害
    ↓
サイトが開かない
    ↓
予約できない
```

となると、可用性が低い状態です。

---

# 高可用性のイメージ

サーバーが1台だけの場合、故障するとサービスが止まります。

```
利用者
   │
   ▼
EC2 1台
   │
   × 障害
   │
   ▼
サービス停止
```

高可用性を考えた構成では、複数のサーバーを用意します。

```
           ALB
         ／   ＼
        ▼     ▼
     EC2①   EC2②
```

EC2①が故障しても、EC2②が処理を続けます。

```
EC2① ×

EC2② ○
   ↓
サービス継続
```

---

# HAと冗長化の違い

似ていますが、意味は少し違います。

|用語|意味|
|---|---|
|冗長化|予備の機器やサーバーを用意すること|
|HA|システム全体を止まりにくくする考え方|
|フェイルオーバー|障害時に予備へ切り替える動作|

つまり、

```
冗長化する
   ↓
フェイルオーバーできる
   ↓
可用性が高くなる
```

という関係です。

HAは、冗長化やフェイルオーバーを含む、より大きな考え方です。

---

# HAを実現する主な方法

## 1. サーバーを複数台にする

```
ALB
 ├─ EC2①
 └─ EC2②
```

1台が故障しても、もう1台で処理できます。

---

## 2. AZを分ける

同じAZに複数台置くだけでは、そのAZ全体が停止すると使えません。

```
AZ-a

├─ EC2①
└─ EC2②
```

そのため、別のAZへ分散します。

```
東京リージョン

AZ-a              AZ-c
EC2①              EC2②
   ＼            ／
         ALB
```

これを**Multi-AZ構成**といいます。

---

## 3. ロードバランサーを使う

ALBはアクセスを複数のEC2へ振り分けます。

```
利用者
   │
   ▼
  ALB
 ／   ＼
▼     ▼
EC2① EC2②
```

ALBはヘルスチェックも行います。

```
EC2①：正常
EC2②：異常
```

この場合、異常なEC2②にはアクセスを送らなくなります。

---

## 4. データベースを冗長化する

例えば、RDSのMulti-AZ構成です。

```
AZ-a                    AZ-c
プライマリDB  ─同期→  スタンバイDB
```

プライマリDBに障害が起きると、スタンバイDBへ切り替わります。

```
プライマリDB ×
       ↓
スタンバイDBへフェイルオーバー
```

---

## 5. Auto Scalingを使う

アクセスが増えたとき、EC2を自動で追加します。

```
アクセス増加
    ↓
EC2を追加
```

逆にアクセスが減ったら、台数を減らします。

```
アクセス減少
    ↓
EC2を削減
```

Auto Scalingは負荷対策ですが、故障したEC2を新しく作り直すこともあるため、可用性の向上にも役立ちます。

---

## 6. 監視と自動復旧を行う

CloudWatchでシステムを監視します。

```
EC2で異常発生
     ↓
CloudWatch Alarm
     ↓
通知・自動復旧
```

障害を早く発見し、復旧までの時間を短くすることもHAでは重要です。

---

# 可用性の数字

可用性は、一般的に割合で表します。

例えば、

```
99%
99.9%
99.99%
```

などです。

「9」が多いほど、停止時間が短くなります。

|可用性|年間停止時間の目安|
|---|---|
|99%|約3日15時間|
|99.9%|約8時間46分|
|99.99%|約52分|
|99.999%|約5分|

例えば99.99%なら、1年間で停止してよい時間は、およそ52分です。

---

# SLAとは？

SLAは、

> **Service Level Agreement**

の略です。

日本語では、**サービス品質保証**などと呼ばれます。

例えばAWSサービスで、

```
月間稼働率99.99%
```

のように、サービス提供側が可用性の基準を示すものです。

ただし、

> AWSサービスのSLAが高いから、自分のシステムも自動的に高可用性になる

わけではありません。

EC2を1台だけ使っていると、そのEC2が止まればサイトも止まります。

---

# HA構成の例

```
利用者
   │
   ▼
Route 53
   │
   ▼
CloudFront
   │
   ▼
  ALB
 ／   ＼
▼     ▼
EC2① EC2②
AZ-a  AZ-c
   │
   ▼
RDS Multi-AZ
```

この構成では、

- EC2が1台故障しても、もう1台で継続
- AZが1つ停止しても、別AZで継続
- DBに障害が起きても、スタンバイへ切り替え
- CloudWatchで異常を監視

という対策をしています。

---

# HAとDRの違い

HAとDRも混同しやすい用語です。

|用語|目的|
|---|---|
|HA|日常的な障害でもサービスを継続する|
|DR|大規模災害からシステムを復旧する|

HAは、EC2やAZの障害への対策です。

```
AZ-a障害
   ↓
AZ-cで継続
```

DRは、リージョン全体の障害などへの対策です。

```
東京リージョン障害
        ↓
大阪リージョンへ切り替え
```

---

# HAとバックアップの違い

|項目|HA|バックアップ|
|---|---|---|
|主な目的|サービスを止めない|データを戻せるようにする|
|障害時|予備へ切り替える|バックアップから復元する|
|復旧速度|比較的速い|時間がかかる場合がある|
|誤削除への対応|弱い|過去のデータへ戻せる|

つまり、

```
HA
＝サービス継続

バックアップ
＝データ復旧
```

です。

両方必要です。

---

# HAで重要な考え方

## 単一障害点をなくす

単一障害点とは、

> **そこが壊れると、システム全体が止まる箇所**

です。

例えば、

```
EC2① ─┐
       ├─ RDS 1台
EC2② ─┘
```

EC2は2台でも、RDSが1台だけなら、RDSが単一障害点になります。

そのため、

```
EC2複数台
   ＋
RDS Multi-AZ
   ＋
ALB
   ＋
複数AZ
```

のように、システム全体で考える必要があります。

---

# Yasukariのような予約サイトで考えると

HAを考えない構成は、

```
利用者
   │
   ▼
EC2 1台
   │
   ▼
予約システム
```

EC2が停止すると、予約できなくなります。

HAを考えた構成は、

```
利用者
   │
   ▼
ALB
 ／   ＼
▼     ▼
EC2① EC2②
AZ-a  AZ-c
   │
   ▼
DynamoDB
```

となります。

さらに、

- 画像はS3へ保存
- セッションはEC2内に置かない
- ログはCloudWatchへ送る
- 障害通知を設定する
- 定期的にバックアップする

といった対策も組み合わせます。

---

# HAのメリット

- 障害が起きてもサービスを継続しやすい
- 利用者への影響を小さくできる
- メンテナンス中もサービスを継続できる
- 信頼性の高いシステムを作れる
- 売上や予約機会の損失を減らせる

---

# HAのデメリット

- サーバーやDBが増えて料金が高くなる
- 構成が複雑になる
- 監視や運用の負担が増える
- データ同期や切り替え設計が必要になる
- 実際に障害テストをしないと、正しく動くか分からない

HAは高ければ高いほど良いわけではありません。

システムの重要度や予算に合わせて設計します。

---

---

# まとめ

- **HAはHigh Availabilityの略**
- **日本語では高可用性**
- **必要なときにシステムを使える状態を保つこと**
- **冗長化・フェイルオーバー・監視などを組み合わせて実現する**
- **AWSではALB、複数EC2、Multi-AZ、Auto Scalingなどを使う**
- **HAはサービス継続、バックアップはデータ復旧が目的**
- **システム全体から単一障害点をなくすことが重要**

## 一言でまとめると

> **高可用性・HAとは、どこかで障害が起きても、利用者がサービスを使い続けられるようにする設計です。**
