**AWS Lambda** は、

> **サーバーを用意せずにプログラムを実行できるサービス**

です。

一言でいうと、

> **「必要なときだけコードを動かしてくれるAWSの実行環境」**

です。

---

# イメージ

普通のWebシステムでは

```
利用者
    │
    ▼
EC2
    │
    ▼
Node.js
    │
    ▼
データベース
```

EC2は

**24時間起動**

しています。

---

Lambdaは違います。

```
利用者
    │
    ▼
Lambda
    │
    ▼
処理
```

アクセスが来た瞬間だけ

```
起動

↓

実行

↓

終了
```

します。

---

# EC2との違い

## EC2

```
EC2

──────────────
```

夜中でも

誰も使っていなくても

```
↓

```

必要な時だけ動きます。

# EC2とLambda比較

|項目|EC2|Lambda|
|---|---|---|
|サーバー管理|必要|不要|
|常時起動|○|×|
|起動速度|常時起動|呼び出し時に起動（コールドスタートが発生することがある）|
|料金|起動時間|実行時間|
|長時間処理|○|制限あり（最大15分）|
|API|○|○|
|バッチ|○|◎|

# あなたのシステムならどう使う？

今の構成を見る限り、

```
利用者
    │
    ▼
EC2
    │
    ▼
Next.js
    │
    ▼
API Routes
    │
    ▼
DynamoDB
```

という構成です。

この構成なら、**予約APIそのものはEC2のままでも問題ありません。**

一方で、次のような「予約処理の後に実行する仕事」はLambdaに向いています。

```
予約完了
    │
    ├─ 完了メール送信
    ├─ 管理者通知
    ├─ LINE通知
    ├─ 利用履歴の集計
    ├─ CloudWatchへのログ集約
    └─ S3へアップロードした画像の加工
```

つまり、

- **EC2**：常に動いているWebアプリ（Next.js）
- **Lambda**：イベントが発生したときだけ実行する処理

という役割分担がよく採られます。

---

## 予約システムの視点で覚えるなら

- **EC2** = 「レストラン（店舗）」…いつでも営業している
- **Lambda** = 「呼び出しスタッフ」…注文が入ったときだけ動く

そのため、予約システムでは**ユーザーが操作するWebサイトはEC2（または他のWeb実行環境）**、**メール送信や通知、画像加工などの裏方処理はLambda**という組み合わせが非常によく使われます。
