― Web通信を守り、「誰が使っているか」を確認する仕組み ―
## 1. HTTPSと認証とは

Webサービスを作るうえで、セキュリティは非常に重要です。

例えば、

```text
ログイン

会員登録

予約

決済

マイページ

管理画面
```

では、ユーザーの個人情報や重要なデータを扱います。

そこで重要になるのが、

```text
HTTPS

認証
```

です。

簡単に分けると、

```text
HTTPS
↓
通信を守る


認証
↓
誰がアクセスしているのか確認する
```

という役割があります。

---

# 2. HTTPSとは

HTTPSは、

> **ブラウザとサーバーの通信を暗号化する仕組み**

です。

正式には、

```text
HTTP
+
TLS
```

によって実現されています。

URLを見ると、

```text
http://example.com
```

ではなく、

```text
https://example.com
```

となっています。

この、

```text
s
```

は、

```text
Secure
```

を意味します。

---

# 3. HTTPの問題

普通のHTTP通信では、通信内容が暗号化されません。

例えばログインするとき、

```text
メールアドレス

password123
```

という情報を送るとします。

HTTPだけの場合、

```text
ユーザー
   ↓
メール
パスワード
   ↓
インターネット
   ↓
サーバー
```

という通信内容を、途中で盗み見られる危険があります。

イメージとしては、

```text
ユーザー

   ↓

「ID: tanaka
 Password: password123」

   ↓

第三者
「見える」

   ↓

サーバー
```

という状態です。

---

# 4. HTTPSではどうなる？

HTTPSを使うと、通信内容が暗号化されます。

```text
ユーザー

   ↓

暗号化

   ↓

x8F2a9K...

   ↓

インターネット

   ↓

復号

   ↓

サーバー
```

途中で通信を見られても、

```text
x8F2a9K...
```

のような意味の分からないデータになります。

これによって、

```text
ログイン情報

個人情報

クレジットカード情報

予約情報
```

などを安全に送信できます。

---

# 5. HTTPSが守るもの

HTTPSには大きく3つの役割があります。

```text
① 暗号化

② 改ざん防止

③ サーバーの本人確認
```

です。

---

# 6. ① 暗号化

最も分かりやすいのが暗号化です。

```text
通常

password123

↓

HTTPS

↓

x9A2fK81...
```

という形に変換して通信します。

そのため、通信を盗み見られても内容を理解されにくくなります。

---

# 7. ② 改ざん防止

HTTPSは、

> **通信内容が途中で書き換えられていないか**

も確認します。

例えば、

```text
振込金額

10,000円
```

という通信が途中で、

```text
100,000円
```

に変更されたら大問題です。

HTTPSでは、通信内容が改ざんされていないか確認する仕組みがあります。

---

# 8. ③ サーバーの本人確認

HTTPSでは、

> **接続しているサーバーが本物なのか**

も確認します。

例えば、

```text
example-bank.com
```

へアクセスしたつもりなのに、

偽物のサーバーへ接続していたら危険です。

そこで、

**SSL/TLS証明書**

を使います。

---

# 9. SSL/TLS証明書とは

SSL/TLS証明書は簡単に言えば、

> **Webサイトの身分証明書**

です。

例えば、

```text
example.com

↓

証明書

↓

「このサーバーは
example.comの正式なサーバーです」
```

という確認を行います。

証明書は、

**認証局（CA）**

と呼ばれる組織によって発行・検証されます。

---

# 10. HTTPS通信の流れ

簡略化すると、

```text
ブラウザ

   ↓

https://example.com

   ↓

サーバー
「証明書です」

   ↓

ブラウザ
「この証明書は信用できる？」

   ↓

確認OK

   ↓

暗号化通信開始
```

となります。

---

# 11. HTTPSはどこで使われる？

現在では、ほぼすべてのWebサイトでHTTPSを使うべきです。

特に、

```text
ログイン

お問い合わせ

会員登録

決済

管理画面

API
```

では必須と考えてよいです。

---

# 12. HTTPSとHTTPの違い

|項目|HTTP|HTTPS|
|---|---|---|
|暗号化|なし|あり|
|改ざん防止|弱い|あり|
|サーバー確認|なし|証明書|
|ポート|80|443|
|URL|http://|https://|

Webサービスでは基本的に、

```text
HTTPS
```

を利用します。

---

# 13. HTTPSのポート番号

HTTPSでは通常、

```text
443
```

番ポートを使用します。

HTTPは、

```text
80
```

です。

つまり、

```text
Webサーバー

├── 80
│   ↓
│   HTTP
│
└── 443
    ↓
    HTTPS
```

というイメージです。

---

# 14. HTTPSとnginx

Webサーバーでは、

```text
nginx
```

でHTTPSを受けることがあります。

例えば、

```text
ユーザー

   ↓

HTTPS :443

   ↓

nginx

   ↓

Node.js :3000
```

という構成です。

外部通信はHTTPSで安全に行い、

内部でNode.jsへ転送します。

---

# 15. HTTPSとロードバランサー

AWSなどでは、

```text
ALB
```

でHTTPSを処理することもあります。

例えば、

```text
ユーザー

   ↓

HTTPS

   ↓

ALB

   ↓

EC2

   ↓

nginx / Next.js
```

という構成です。

SSL/TLS証明書をALBに設定することもできます。

---

# 16. 認証とは

次に、

**認証**

です。

認証とは、

> **アクセスしている人が誰なのか確認する仕組み**

です。

例えば、

```text
メールアドレス

パスワード
```

を入力してログインします。

```text
ユーザー

   ↓

メールアドレス
パスワード

   ↓

サーバー

   ↓

本人確認

   ↓

ログイン成功
```

これが認証です。

---

# 17. 認証と認可の違い

非常に重要なのが、

```text
認証

認可
```

の違いです。

### 認証

```text
Authentication
```

> あなたは誰ですか？

を確認します。

例えば、

```text
田中さんである
```

ことを確認します。

---

### 認可

```text
Authorization
```

> あなたは何をしてよいですか？

を確認します。

例えば、

```text
一般ユーザー
↓
自分の予約だけ見られる

管理者
↓
すべての予約を見られる
```

という仕組みです。

---

# 18. 認証と認可の例

例えば会社の建物を考えると、

```text
入口

社員証を確認

↓

認証
「田中さんですね」
```

その後、

```text
一般社員

↓

一般フロアのみ


管理者

↓

サーバールームにも入れる
```

これが認可です。

つまり、

```text
認証
↓
誰なのか


認可
↓
何ができるのか
```

です。

---

# 19. ログインの基本的な流れ

一般的なログインでは、

```text
① メールアドレス入力

② パスワード入力

③ サーバーへ送信

④ ユーザー検索

⑤ パスワード確認

⑥ 認証成功

⑦ ログイン情報を保持
```

という流れになります。

---

# 20. パスワードはそのまま保存しない

非常に重要なのが、

> **パスワードをそのままデータベースへ保存しない**

ことです。

悪い例は、

```text
users

name    password

田中    password123
佐藤    abc123
```

です。

データベースが漏洩した場合、パスワードがそのまま盗まれます。

---

# 21. ハッシュ化

そこで、

**ハッシュ化**

を行います。

例えば、

```text
password123

↓

ハッシュ関数

↓

ef92b778...
```

のように変換します。

データベースには、

```text
田中

ef92b778...
```

を保存します。

ログイン時も入力されたパスワードをハッシュ化して比較します。

---

# 22. ログイン後はどうする？

認証が成功した後、

```text
毎回メールアドレスと
パスワードを送る
```

のは安全でも効率的でもありません。

そこで、

```text
Session

Cookie

Token
```

などを使って、

> **ログイン済みであることを保持する**

仕組みを使います。

---

# 23. Cookieとは

Cookieは、

> **ブラウザに保存される小さなデータ**

です。

例えばログイン成功後、

```text
サーバー

↓

Cookieを発行

↓

ブラウザへ保存
```

します。

その後、

```text
ブラウザ

↓

Cookie付きでアクセス

↓

サーバー

↓

ログイン済みと判断
```

できます。

---

# 24. Sessionとは

Sessionは、

> **ログイン情報をサーバー側で管理する仕組み**

です。

例えば、

```text
ログイン成功

↓

サーバー

Session ID
ABC123を作る

↓

ブラウザ

Cookie
ABC123を保存
```

します。

次回アクセスすると、

```text
ブラウザ

↓

ABC123

↓

サーバー

↓

Session確認

↓

「田中さんだ」
```

と判断します。

---

# 25. Session認証のイメージ

```text
Browser

Cookie
session_id=ABC123

     ↓

Server

ABC123
   ↓
田中さん

     ↓

Database
```

ブラウザにはユーザー情報そのものではなく、

```text
Session ID
```

を持たせます。

---

# 26. JWTとは

認証を学ぶと、

**JWT**

という言葉も出てきます。

JWTは、

```text
JSON Web Token
```

の略です。

簡単に言えば、

> **ユーザー情報などを持った署名付きトークン**

です。

例えば、

```text
xxxxx.yyyyy.zzzzz
```

のような文字列になります。

---

# 27. JWT認証の流れ

例えば、

```text
① ログイン

↓

② サーバー
本人確認

↓

③ JWT発行

↓

④ ブラウザへ返す

↓

⑤ APIアクセス時にJWT送信

↓

⑥ サーバーがJWT確認
```

という流れです。

---

# 28. JWTとSessionの違い

簡単に比較すると、

|項目|Session|JWT|
|---|---|---|
|主な情報管理|サーバー側|Token側|
|ブラウザ|Session ID|Token|
|サーバー保存|必要なことが多い|不要にできる|
|無効化|比較的簡単|設計が必要|
|API|よく使う|よく使う|

どちらが絶対に優れているというわけではありません。

システムによって使い分けます。

---

# 29. OAuthとは

OAuthは、

> **他サービスの権限を安全に利用するための仕組み**

です。

例えば、

```text
Googleでログイン

GitHubでログイン

LINEでログイン
```

などで関連します。

ただし厳密には、

```text
OAuth
=
認証そのもの
```

ではありません。

OAuthは本来、

> **サービスへのアクセス権限を渡す仕組み**

です。

---

# 30. OpenID Connect

Googleログインなど、

```text
「この人は誰なのか」
```

という認証を行う場合、

OAuthに加えて、

**OpenID Connect（OIDC）**

が使われることがあります。

簡単に整理すると、

```text
OAuth
↓
権限を渡す


OpenID Connect
↓
ユーザー本人を確認する
```

というイメージです。

---

# 31. 認証の実務例

例えば予約システムなら、

```text
ログイン

↓

メール + パスワード

↓

認証

↓

Cookie / Session

↓

予約ページ

↓

自分の予約情報だけ取得
```

という流れになります。

管理画面では、

```text
ログイン

↓

認証

↓

role確認

↓

admin

↓

管理画面表示
```

という認可処理も加わります。

---

# 32. フロントエンドと認証

ReactやNext.jsでは、

```text
ログイン状態

ユーザー情報

権限
```

によって画面を変えることがあります。

例えば、

```tsx
if (!user) {
  return <LoginButton />;
}

return <MyPage />;
```

という処理です。

つまり、

```text
未ログイン

↓

ログインボタン


ログイン済み

↓

マイページ
```

のように表示を切り替えます。

---

# 33. ただしフロントだけで認可してはいけない

重要なのは、

> **画面を隠すだけではセキュリティ対策にならない**

ことです。

例えば、

```javascript
if (user.role === "admin") {
  showAdminButton();
}
```

としても、

API自体が誰でも使える状態なら危険です。

必ずサーバー側でも、

```text
このユーザーはadminか？
```

を確認する必要があります。

---

# 34. 認証情報はどこに保存する？

認証では、

```text
Cookie

localStorage

sessionStorage
```

などが候補になります。

ただし、セキュリティ上、

> **重要な認証情報を安易にlocalStorageへ保存しない**

ことが重要です。

XSSなどによってJavaScriptから読み取られる危険があります。

Cookieでは、

```text
HttpOnly

Secure

SameSite
```

といった設定が重要になります。

---

# 35. HttpOnly

Cookieに、

```text
HttpOnly
```

を設定すると、

JavaScriptからCookieを読み取りにくくできます。

つまり、

```javascript
document.cookie
```

から認証用Cookieを取得できないようにできます。

XSS対策として重要です。

---

# 36. Secure

Cookieの、

```text
Secure
```

属性を設定すると、

> **HTTPS通信でのみCookieを送信する**

ようにできます。

つまり、

```text
HTTP
↓
送らない

HTTPS
↓
送る
```

という設定です。

---

# 37. SameSite

SameSiteは、

> **別サイトからCookieを送る条件を制御する設定**

です。

CSRF対策などに関係します。

例えば、

```text
SameSite=Lax

SameSite=Strict

SameSite=None
```

などがあります。

---

# 38. XSS

認証と一緒に覚えておきたい攻撃が、

**XSS**

です。

XSSは、

```text
Cross Site Scripting
```

の略です。

悪意のあるJavaScriptをWebページ上で実行させる攻撃です。

例えば、

```html
<script>
  stealCookie();
</script>
```

のようなコードが実行されてしまうと、

認証情報を盗まれる可能性があります。

---

# 39. CSRF

もう一つ重要なのが、

**CSRF**

です。

CSRFは、

```text
Cross Site Request Forgery
```

です。

例えば、

```text
ユーザー
銀行サイトへログイン済み

↓

悪意あるサイトへアクセス

↓

勝手に銀行APIへリクエスト

↓

送金
```

のような攻撃です。

Cookieベースの認証では特に注意が必要です。

---

# 40. HTTPSだけで安全になる？

HTTPSは非常に重要ですが、

```text
HTTPS
=
すべて安全
```

ではありません。

HTTPSが守るのは主に、

> **通信経路**

です。

例えば、

```text
弱いパスワード

SQL Injection

XSS

CSRF

権限設定ミス
```

などはHTTPSだけでは防げません。

---

# 41. 認証だけで安全になる？

認証も同じです。

```text
ログイン機能がある
=
安全
```

ではありません。

例えば、

```text
他人のユーザーIDを指定すれば
予約情報を見られる
```

のであれば危険です。

そのため、

```text
認証

+

認可
```

が必要です。

---

という役割です。

# 47. まとめ

HTTPSは、

> **ブラウザとサーバーの通信を暗号化して安全にする仕組み**

です。

認証は、

> **アクセスしているユーザーが誰なのか確認する仕組み**

です。

整理すると、

|技術|役割|
|---|---|
|HTTP|Web通信|
|HTTPS|暗号化されたWeb通信|
|TLS|HTTPSの暗号化|
|証明書|サーバー確認|
|認証|誰なのか確認|
|認可|何をしてよいか確認|
|Cookie|ブラウザに情報保存|
|Session|サーバーでログイン管理|
|JWT|Tokenによる認証|
|OAuth|権限を渡す|
|OIDC|ユーザー認証|
|XSS|JavaScriptを悪用する攻撃|
|CSRF|ログイン状態を悪用する攻撃|

Webアプリ全体では、

```text
ユーザー

↓

HTTPS

↓

ログイン

↓

認証

↓

Session / Token

↓

認可

↓

API

↓

Database
```

という流れになります。

最も重要なのは、

```text
HTTPS
=
通信を守る

認証
=
誰なのか確認する

認可
=
何をしてよいか決める
```

という3つの役割を分けて理解することです。

この3つが分かると、

```text
React / Next.js
↓
ログイン画面

HTTP / HTTPS
↓
サーバー通信

Node.js
↓
認証処理

Cookie / Session
↓
ログイン状態

認可
↓
アクセス制御
```

という、Webアプリのセキュリティ全体の流れがかなり理解しやすくなります。
