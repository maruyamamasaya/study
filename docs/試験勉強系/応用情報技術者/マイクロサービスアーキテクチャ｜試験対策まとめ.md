## 1. マイクロサービスとは？

**マイクロサービスアーキテクチャ（Microservices Architecture）**とは、

> 1つの大きなシステムを、業務・機能単位の小さなサービスに分割し、それぞれを独立して開発・デプロイ・運用する設計方式

のこと。

例えばECサイトなら、

```text
ECサイト
│
├─ 会員サービス
├─ 認証サービス
├─ 商品サービス
├─ 注文サービス
├─ 決済サービス
└─ 通知サービス
```

のように分割する。

それぞれのサービスは、**APIなどを使って通信する**。

---

# 2. モノリシックとの違い

マイクロサービスを理解するには、まず**モノリシックアーキテクチャ**と比較すると分かりやすい。

## モノリシック

「Monolithic = 一枚岩」という意味。

```text
┌─────────────────────┐
│       ECサイト       │
│                     │
│  会員                │
│  商品                │
│  注文                │
│  決済                │
│  通知                │
│                     │
└─────────────────────┘
```

基本的に1つの大きなアプリケーションとして開発する。

### 特徴

* 構成が比較的シンプル
* 小規模システムでは開発しやすい
* 一括してデプロイしやすい
* 機能同士の連携が単純

一方、システムが巨大になると、

```text
決済機能だけ変更したい
        ↓
アプリ全体への影響確認が必要
        ↓
システム全体をデプロイ
```

となりやすい。

---

# 3. マイクロサービス

同じECサイトをマイクロサービス化すると、

```text
                ┌─ 会員サービス
                │
ユーザー → API ├─ 商品サービス
                │
                ├─ 注文サービス
                │
                ├─ 決済サービス
                │
                └─ 通知サービス
```

となる。

それぞれを**独立したアプリケーション**として扱う。

例えば、

```text
決済サービス
     ↓
決済機能だけ修正
     ↓
決済サービスだけテスト
     ↓
決済サービスだけデプロイ
```

といった運用が可能になる。

---

# 4. 一番重要なのは「独立性」

試験では、

> 「小さいプログラムに分割する」

だけで覚えないこと。

マイクロサービスの重要なポイントは、

**各サービスの独立性が高いこと。**

例えば、

```text
会員サービス
├─ 独立して開発
├─ 独立してテスト
├─ 独立してデプロイ
└─ 独立してスケール

決済サービス
├─ 独立して開発
├─ 独立してテスト
├─ 独立してデプロイ
└─ 独立してスケール
```

という構成を目指す。

### 試験キーワード

問題文に、

* 業務機能単位
* 小さなサービス
* 疎結合
* APIによる連携
* 独立して開発
* 独立してデプロイ
* 独立してスケール

などが出てきたら、

**マイクロサービス**

を疑う。

---

# 5. サービス間はどうやって通信する？

別々のサービスなので、通信する仕組みが必要になる。

代表的なのが**API**。

```text
注文サービス
     │
     │ API
     ↓
決済サービス
     │
     │ API
     ↓
通知サービス
```

例えば、

```text
POST /payments
```

として決済サービスを呼び出す。

イメージとしては、

> 「決済しておいて」

と別サービスに依頼するための窓口がAPI。

REST APIやHTTPだけでなく、メッセージングなどを利用してサービス同士を連携させる場合もある。

---

# 6. なぜマイクロサービスとDockerがセットなのか？

ここが重要。

マイクロサービスでは、

```text
会員サービス
商品サービス
注文サービス
決済サービス
通知サービス
```

のように、たくさんのアプリケーションが存在する。

すると、

```text
会員サービス
→ Node.jsが必要

商品サービス
→ Javaが必要

決済サービス
→ Pythonが必要
```

など、それぞれ実行環境が違うこともある。

これを1台ずつサーバーで管理すると大変。

そこで**コンテナ**が便利になる。

---

# 7. Dockerを使うとどうなる？

Dockerでは、

**アプリケーション＋実行に必要な環境**

をコンテナとしてまとめられる。

```text
┌─────────────────┐
│ 会員コンテナ     │
│ Node.js + アプリ │
└─────────────────┘

┌─────────────────┐
│ 商品コンテナ     │
│ Java + アプリ    │
└─────────────────┘

┌─────────────────┐
│ 決済コンテナ     │
│ Python + アプリ  │
└─────────────────┘
```

つまり、

**1サービス = 1つまたは複数のコンテナ**

のように管理しやすい。

---

# 8. Dockerの何がマイクロサービスと相性がいい？

例えば決済サービスを更新したい。

Dockerなら、

```text
決済サービス
     ↓
新しいDockerイメージ作成
     ↓
新しいコンテナを起動
     ↓
決済サービスだけ更新
```

とできる。

他の、

```text
会員
商品
注文
通知
```

には基本的に触らなくていい。

つまり、

> **マイクロサービスの「独立してデプロイしたい」という思想と、Dockerの「アプリを独立した実行環境としてパッケージ化する」という特徴が相性がいい。**

---

# 9. じゃあKubernetesは何をする？

Dockerなどでコンテナを作れるようになっても、別の問題が出てくる。

マイクロサービスが増えると、

```text
会員コンテナ × 3

商品コンテナ × 5

注文コンテナ × 3

決済コンテナ × 5

通知コンテナ × 2
```

など、数十・数百・数千のコンテナを管理する可能性がある。

人間が全部管理するのは大変。

そこで登場するのが、

**Kubernetes（K8s）**

---

# 10. Kubernetes = コンテナを管理する仕組み

Kubernetesは、

**大量のコンテナを管理・制御するコンテナオーケストレーション基盤**

として使われる。

例えば、

```text
              Kubernetes
                  │
      ┌───────────┼───────────┐
      ↓           ↓           ↓
   会員          商品         決済
 Container      Container    Container
 Container      Container    Container
               Container    Container
```

などを管理する。

---

# 11. Kubernetesがやってくれること

代表的な機能として、

### コンテナの起動

```text
「決済コンテナを3個動かして」
```

↓

```text
決済①
決済②
決済③
```

---

### 障害時の復旧

例えば、

```text
決済① ○
決済② × ← 障害
決済③ ○
```

となったら、新しいコンテナを起動して、

```text
決済① ○
決済④ ○ ← 新規起動
決済③ ○
```

のように必要な状態を維持する。

---

### スケーリング

アクセスが増えた。

```text
決済 × 3
```

↓

```text
決済 × 10
```

必要に応じてコンテナ数を増やす。

---

### 負荷分散

```text
ユーザー
   ↓
 Kubernetes
   ↓
 ┌─ 決済①
 ├─ 決済②
 └─ 決済③
```

複数のコンテナに処理を振り分ける。

---

# 12. マイクロサービス・Docker・Kubernetesの関係

ここを整理しておく。

```text
【マイクロサービス】

システムを

会員
商品
注文
決済
通知

などに分割する

        ↓

【Docker】

各サービスを
コンテナとして実行しやすくする

        ↓

【Kubernetes】

大量のコンテナを
まとめて管理する
```

つまり、

| 技術                    | 役割                 |
| --------------------- | ------------------ |
| **マイクロサービス**          | システムをどう分割するか       |
| **Docker**            | アプリをどう実行環境としてまとめるか |
| **Kubernetes**        | 大量のコンテナをどう管理するか    |
| **AWS / Azure / GCP** | それらをどこで動かすか        |

---

# 13. クラウドとの関係

マイクロサービスはクラウドそのものではない。

```text
マイクロサービス
↓
アプリケーション設計

Docker
↓
コンテナ技術

Kubernetes
↓
コンテナ管理

AWS / Azure / GCP
↓
クラウド基盤
```

例えば、

```text
AWS
│
└─ Kubernetes
      │
      ├─ 会員コンテナ
      ├─ 商品コンテナ
      ├─ 注文コンテナ
      ├─ 決済コンテナ
      └─ 通知コンテナ
```

という構成もできる。

AWSならAmazon EKSなどが、Kubernetesを利用するためのマネージドサービスとして提供されている。

---

# 14. マイクロサービスのメリット

## ① 独立して変更・デプロイできる

```text
決済だけ変更

↓

決済サービスだけデプロイ
```

システム全体を毎回リリースする必要性を減らせる。

---

## ② 必要な部分だけスケールできる

例えば、

```text
会員サービス
■■

商品サービス
■■■

決済サービス
■■■■■■■■■■
```

決済だけ負荷が高ければ、

**決済サービスだけ増強する**

ことができる。

---

## ③ 障害の影響範囲を限定しやすい

```text
おすすめサービス
        ↓
      障害

商品購入 → ○
決済     → ○
会員     → ○
```

適切に設計されていれば、一部サービスの障害がシステム全体の停止につながることを防ぎやすい。

---

## ④ チームを分けやすい

```text
会員サービス
→ チームA

注文サービス
→ チームB

決済サービス
→ チームC
```

大規模開発で特にメリットがある。

---

## ⑤ 技術をサービスごとに選択できる

例えば、

```text
会員 → Java

検索 → Go

AI → Python

画面 → TypeScript
```

など、サービスの特性に応じて技術を選択することも可能。

ただし、技術を自由にしすぎると運用が複雑になるため注意が必要。

---

# 15. マイクロサービスのデメリット

試験では**メリットだけでなくデメリットも重要。**

## ① システム全体が複雑になる

モノリシックなら、

```text
アプリ
↓
関数呼び出し
↓
別の処理
```

だったものが、

マイクロサービスでは、

```text
注文サービス
     ↓
ネットワーク
     ↓
決済サービス
     ↓
ネットワーク
     ↓
通知サービス
```

となる。

つまり、

**ネットワーク通信が増える。**

---

## ② 障害原因を追いにくい

例えば、

```text
注文
 ↓
決済
 ↓
在庫
 ↓
配送
 ↓
通知
```

と処理していてエラーになった場合、

> 「どこで失敗した？」

を調査する必要がある。

そのため、

* ログ
* 監視
* 分散トレーシング

などが重要になる。

---

## ③ データ管理が難しい

マイクロサービスでは、サービスごとにデータを独立して管理する設計も多い。

```text
会員サービス
    ↓
 会員DB


注文サービス
    ↓
 注文DB


決済サービス
    ↓
 決済DB
```

すると、

**複数サービスをまたいだトランザクション管理**

が難しくなる。

---

## ④ 通信障害を考える必要がある

```text
注文サービス
     ↓
     ×
     ↓
決済サービス
```

決済サービス自体が正常でも、

**ネットワーク障害によって呼び出せない**

可能性がある。

---

# 16. モノリシック vs マイクロサービス

試験ではこの比較が重要。

|        | モノリシック     | マイクロサービス    |
| ------ | ---------- | ----------- |
| システム構成 | 一体型        | 小さなサービスに分割  |
| サービス間  | 内部処理が中心    | API・メッセージなど |
| デプロイ   | 全体単位になりやすい | サービス単位      |
| スケーリング | 全体単位になりやすい | サービス単位      |
| 障害影響   | 広がりやすい     | 分離しやすい      |
| 構成     | 比較的単純      | 複雑          |
| 運用     | 比較的簡単      | 難しくなりやすい    |
| 小規模開発  | 向いている      | 過剰になる場合がある  |
| 大規模開発  | 複雑化しやすい    | チーム分割しやすい   |

# 17. 試験で出てきたらどう判断する？

## パターン①

> システムを業務機能ごとの小さなサービスに分割し、それぞれを独立して開発・デプロイする。

### 答え

**マイクロサービスアーキテクチャ**

---

## パターン②

> 各サービスがAPIを介して連携し、サービスごとに独立して変更・拡張できるようにする。

### 答え

**マイクロサービスアーキテクチャ**

---

## パターン③

> アプリケーションとその実行環境を一つの単位としてパッケージ化する。

### 答え

**コンテナ**

マイクロサービスそのものではない。

---

## パターン④

> 多数のコンテナについて、配置、起動、停止、スケーリングなどを自動的に管理する。

### 答え

**コンテナオーケストレーション**

代表例：

**Kubernetes**

---

# 18. 試験で引っかかりやすいポイント

### 「マイクロサービス = Docker」ではない

違う。

```text
マイクロサービス
→ 設計思想・アーキテクチャ

Docker
→ コンテナ技術
```

---

### 「マイクロサービス = クラウド」ではない

違う。

```text
マイクロサービス
→ システムの設計

クラウド
→ ITリソースの提供・利用形態
```

オンプレミスでもマイクロサービスは構築できる。

---

### 「マイクロサービスなら必ずKubernetes」ではない

これも違う。

Kubernetesを使わなくてもマイクロサービスは構築できる。

ただし、

```text
マイクロサービス増加
        ↓
コンテナ増加
        ↓
管理が大変
        ↓
Kubernetesなどで管理
```

という流れになるため、

**実務ではセットで登場しやすい。**

---

# 19. 試験用の最終整理

```text
モノリシック
    ↓
「全部まとめて1つ」


マイクロサービス
    ↓
「機能ごとに分割」
「APIで連携」
「独立してデプロイ・スケール」


Docker
    ↓
「アプリ＋実行環境をコンテナ化」


Kubernetes
    ↓
「大量のコンテナを管理」


AWS / Azure / GCP
    ↓
「それらを動かせるクラウド基盤」
```

## 一言で覚える

> **マイクロサービス = 分ける**
> **API = つなぐ**
> **Docker = 包む**
> **Kubernetes = 管理する**
> **クラウド = 動かす基盤**

**マイクロサービスアーキテクチャとは、システムを業務機能単位の独立した小さなサービスに分割し、APIなどを介して連携させることで、サービスごとに独立して開発・デプロイ・スケーリングできるようにするアーキテクチャである。**
