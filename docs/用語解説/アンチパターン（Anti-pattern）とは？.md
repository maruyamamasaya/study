**アンチパターン（Anti-pattern）**とは、簡単にいうと、

> **「一見よさそうだけど、実際には問題を起こしやすい“ありがちなやり方”」**

のことです。

### たとえば開発なら

こんなものがアンチパターンです。

| アンチパターン    | どういう状態？              | 問題               |
| ---------- | -------------------- | ---------------- |
| コピペ開発      | 同じコードを大量にコピー         | 修正箇所が増える         |
| 巨大な関数      | 1つの関数に全部書く           | 読みにくい・直しにくい      |
| 巨大クラス      | 1クラスが何でも担当           | 影響範囲が分からなくなる     |
| とりあえず動けばOK | 設計せず機能追加             | 後から変更しづらい        |
| エラーを握りつぶす  | エラーが起きても無視           | 障害原因が分からない       |
| ハードコーディング  | URLやパスワードなどをコードに直接記述 | 変更・管理・セキュリティ面で問題 |
| AIに全部丸投げ   | 設計・実装・検証をAI任せ        | 間違いが連鎖しやすい       |

### 「パターン」と「アンチパターン」

対比すると分かりやすいです。

```
パターン
  ↓
よくある問題に対する
「うまくいきやすい定石」

アンチパターン
  ↓
よくやってしまうけど
「問題になりやすい典型例」
```

たとえば、

```
❌ アンチパターン

「この関数長いけど、
  動いてるから全部ここに追加しよう」

        ↓

気づいたら2,000行
        ↓
誰も触れない
        ↓
修正すると別の機能が壊れる
```

こういう**「ありがちな失敗の型」に名前をつけたもの**がアンチパターンです。

なので技術記事で、

> 「これはアンチパターンです」

と書かれていたら、

**「それ、よくやりがちだけど、基本的には避けたほうがいい設計・実装・運用だよ」**

くらいの意味で捉えると分かりやすいです。
