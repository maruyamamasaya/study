この記事の言いたいことをかなり簡単にすると、

> **「ユーザーが入力した文字列を、そのままHTMLとしてブラウザに解釈させると危険。Reactは通常、入力値をただの文字として扱ってくれるのでXSSが起きにくい」**

という話です。

## そもそもXSSとは？

**XSS（Cross-Site Scripting）**は、

> 攻撃者が入力した悪意のあるHTMLやJavaScriptを、他のユーザーのブラウザで実行させる攻撃

です。

たとえば掲示板があるとします。

普通の投稿なら、

```
こんにちは！
```

ですが、攻撃者がこんな投稿をしたとします。

```
<img src="x" onerror="alert('攻撃成功')">
```

掲示板側がこれを**HTMLとしてそのまま表示**してしまうと、ブラウザは、

「これは文字じゃなくてHTMLだな」

と解釈します。

そして`onerror`のJavaScriptまで実行されてしまいます。

これがXSSの基本的な仕組みです。

---

## なぜ危険なの？

`alert()`が表示されるだけなら大したことありません。

でも実際には、攻撃者がJavaScriptを実行できるということなので、

```
攻撃者が掲示板に悪意あるコードを投稿
        ↓
DBに保存される
        ↓
別のユーザーが掲示板を見る
        ↓
悪意あるコードもブラウザへ届く
        ↓
ブラウザでJavaScriptとして実行
```

となる可能性があります。

すると、サイト上での不正操作、画面の改ざん、フィッシング画面の表示、アクセス可能な情報の窃取などにつながります。

特に「投稿をDBに保存して、あとから他の人が見る」タイプは**Stored XSS（格納型XSS）**と呼ばれます。

---

# ReactはなぜXSSを防げるの？

ここが記事の一番重要なところです。

Reactでは普通、

```
<div>{comment}</div>
```

のように表示します。

仮に`comment`の中身が、

```
<img src="x" onerror="alert('攻撃')">
```

だったとしても、Reactは基本的にこれを**HTMLとして解釈させません**。

イメージとしては、

```
<img src="x" onerror="alert('攻撃')">
```

という**ただの文字列**として画面に表示します。

つまり、

```
ユーザー入力
    ↓
React
    ↓
「これはHTMLじゃなくて文字として表示しよう」
    ↓
ブラウザ
    ↓
JavaScriptは実行されない
```

となります。

これを理解すると、Reactが「XSSを魔法のように検知してブロックしている」というより、

> **そもそもユーザー入力をHTMLとして扱わない**

という設計になっている、と考えると分かりやすいです。

---

## じゃあReactならXSS対策は完璧？

**いいえ。**

Reactには、意図的にHTMLを埋め込むための

```
dangerouslySetInnerHTML
```

があります。

例えば、

```
<div dangerouslySetInnerHTML={{ __html: comment }} />
```

とすると、`comment`をHTMLとしてブラウザに渡せます。

名前にわざわざ**dangerously（危険に）**と付いているのはそのためです。

外部やユーザー由来のHTMLをこれで表示する場合は、DOMPurifyなどを使った**サニタイズ（危険なHTMLの除去）**が必要になるケースがあります。

---

## この記事から覚えておけばいいこと

|ポイント|意味|
|---|---|
|XSS|悪意あるコードを他人のブラウザで実行させる攻撃|
|原因|ユーザー入力などをHTMLとして不用意に解釈させる|
|React|`{value}`なら基本的に文字列として安全に表示する|
|エスケープ|`<`などをHTMLとして機能しない形で扱う|
|`dangerouslySetInnerHTML`|HTMLを直接埋め込むので注意|
|サニタイズ|危険なHTML・属性などを取り除く|

一番大事なのは、

**「データ」と「実行されるコード」を混ぜない**

という考え方です。

XSSはこの境界が壊れたときに成立します。Reactは通常の書き方なら、その境界を守ってくれるわけです。
