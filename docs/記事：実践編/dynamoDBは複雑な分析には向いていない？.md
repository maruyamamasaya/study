**DynamoDBは「分析」よりも「高速なデータ取得」が得意**なデータベースです。

言い換えると、

- **DynamoDB = 1件のデータを素早く取り出すのが得意**
- **MySQL・PostgreSQL = データを集計・分析するのが得意**

という違いがあります。

---

# なぜ分析に向いていないの？

理由は、DynamoDBは**「アクセスパターン（どう取得するか）」を先に決めて設計する**データベースだからです。

例えば予約システムなら

```
予約IDで取得

ユーザーIDで取得

店舗IDで取得
```

このような取得は非常に速いです。

しかし、

```
過去3か月の予約を集計

年代別に分析

店舗ごとの売上ランキング

曜日ごとの予約率
```

のような分析は苦手です。

---

# 例① 売上ランキング

例えば

```
予約

ID
店舗
金額
日付
```

というデータが100万件あります。

欲しいもの

```
今月

売上ランキング

TOP10
```

MySQLなら

```
SELECT store_id,
SUM(price)
FROM reservations
WHERE date >= '2026-07-01'
GROUP BY store_id
ORDER BY SUM(price) DESC
LIMIT 10;
```

一発です。

---

DynamoDBでは

基本的には

```
100万件読む

↓

店舗ごとに計算

↓

並べ替え

↓

TOP10
```

という流れになります。

つまり

**全部読む（Scan）**

必要があります。

---

# Scanが問題

例えば

```
1000万件
```

あったら

```
全部取得

↓

全部メモリへ

↓

集計
```

になります。

これは

- 遅い
- コストが高い

です。

---

# 例② 年齢別分析

例えば

```
Users

年齢
```

があるとします。

知りたい

```
20代

30代

40代
```

人数。

MySQL

```
GROUP BY age
```

終了。

DynamoDB

```
全員読む

↓

年齢を見る

↓

20代++

30代++

40代++
```

自分で数える必要があります。

---

# 例③ JOINがない

例えば

```
Users

id
名前
```

と

```
Reservations

userId
```

があります。

欲しい結果

```
田中さん

予約10件
```

MySQL

```
JOIN
```

で終わります。

DynamoDB

```
Users読む

↓

Reservations読む

↓

コードで結合
```

になります。

---

# 例④ WHEREが弱い

MySQLなら

```
WHERE
```

で

```
価格

日付

店舗

ステータス

年代
```

自由に検索できます。

例えば

```
WHERE

price > 5000

AND

status='paid'

AND

date > ...
```

これも簡単。

---

DynamoDBでは

主キー以外は

基本検索できません。

検索したいなら

```
GSI
```

を作る必要があります。

つまり

**あとから自由に検索条件を増やす**

という考え方ではありません。

---

# 例⑤ ORDER BY

例えば

```
売上順

予約数順

人気順
```

MySQL

```
ORDER BY
```

だけ。

DynamoDB

```
取得

↓

コードでソート
```

になります。

# 実際の分析システムは？

AWSでも

DynamoDBだけでは分析しません。

例えば

```
ユーザー

↓

DynamoDB

↓

DynamoDB Streams

↓

Lambda

↓

S3

↓

Athena

↓

分析
```

または

```
DynamoDB

↓

Redshift
```

へコピーします。

つまり

**運用用DB**

↓

**分析用DB**

に分けます。

これは実務ではよくある構成です。

---

# Yasukariならどうなる？

例えば予約システムでは

通常の画面

```
予約IDで取得

ユーザー予約一覧

車両取得

店舗取得
```

これはDynamoDBが非常に得意です。

---

しかし経営者から

```
今年の売上

曜日別

時間帯別

店舗別

リピーター率

平均利用時間
```

と言われると、

DynamoDBだけでは効率が悪くなります。

そのため、

```
予約

↓

DynamoDB

↓

夜間バッチ

↓

Redshift

↓

BIツール
```

のような構成にして分析を行うことが多いです。

---

# まとめ

|項目|DynamoDB|MySQL / PostgreSQL|
|---|---|---|
|1件取得|◎ 非常に速い|○|
|主キー検索|◎|◎|
|JOIN|✕|◎|
|GROUP BY|✕|◎|
|HAVING|✕|◎|
|ORDER BY|△（限定的）|◎|
|自由な検索条件|△（インデックス設計が必要）|◎|
|集計・分析|✕|◎|
|大量アクセス|◎|○|

**重要なのは、「どちらが優れているか」ではなく、用途が違うことです。**

- **DynamoDB** は「ユーザーが今すぐ必要なデータを高速に返す」ためのデータベース。
- **MySQL / PostgreSQL** は「大量データを柔軟に検索・集計・分析する」ためのデータベース。

そのため、AWSを使った実務でも**DynamoDBと分析用データベース（Athena、Redshiftなど）を組み合わせて使う**ケースが非常に多くあります。
