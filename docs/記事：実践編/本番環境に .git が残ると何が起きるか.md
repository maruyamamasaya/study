この記事も、ポイントを絞るとかなり分かりやすいです。

## 一言でいうと

> **本番Webサーバーに`.git`を置いてしまうと、GitHubを非公開にしていても、ソースコードや過去の履歴を外部から復元される可能性がある。**

だから、

> **「`.git`へのアクセスを禁止する」より、そもそも本番環境に`.git`を置かないことが重要**

という記事です。

---

# そもそも `.git` って何？

Gitで管理しているプロジェクトには、通常こんな構造があります。

```
my-app/
├── .git/
├── src/
├── public/
├── package.json
└── README.md
```

この`.git`が、**Gitの履歴や管理情報を保存している場所**です。

例えば、

```
git log
```

で過去のコミットを確認できたり、

```
git checkout
```

で昔の状態に戻せたりするのも、`.git`に情報が入っているからです。

つまり、

> `.git` ≒ そのプロジェクトの「Gitの記憶」

と考えると分かりやすいです。

---

# 何が問題なの？

例えば開発環境で、

```
my-app/
├── .git/
├── src/
├── package.json
└── ...
```

となっているものを、そのまま本番サーバーへコピーしたとします。

すると設定によっては、

```
https://example.com/.git/HEAD
```

などにインターネットからアクセスできてしまいます。

これが危険です。

---

# `.git`から何が分かるの？

単に「Gitを使っている」という情報だけではありません。

`.git`には、

```
.git
 ↓
コミット履歴
 ↓
各コミットのファイル構成
 ↓
実際のソースコード
```

を復元するための情報があります。

そのため攻撃者に取得されると、

```
現在のソースコード
過去のソースコード
削除したファイル
設定ファイル
内部APIの情報
DB接続情報
過去にコミットしたAPIキー
```

などが漏れる可能性があります。

特に怖いのが**過去の履歴**です。

例えば、

```
DATABASE_PASSWORD=super-secret-password
```

を間違えてGitにコミットしたとします。

気付いて、

```
「あ、まずい！」

↓
.envを削除

↓
GitHubに再Push
```

したとしても、過去のコミットに残っていれば復元できる可能性があります。

つまり、

> **現在のファイルから削除した ≠ Gitの履歴から消えた**

です。

---

# 「フォルダ一覧を非表示にしてるから大丈夫」ではない

この記事で特に重要なのがここです。

Webサーバーで、

```
https://example.com/.git/
```

を開いて、

```
403 Forbidden
```

になったからといって、必ずしも中のファイルまで安全とは限りません。

Gitには、

```
.git/HEAD
.git/index
.git/config
.git/refs/
.git/objects/
```

など、**ある程度決まった構造**があります。

そのため個々のファイルへアクセスできる状態なら、

```
.git/HEAD
   ↓
現在のブランチ
   ↓
コミット
   ↓
tree
   ↓
blob
   ↓
ソースコード
```

という形で情報を辿られる可能性があります。

だから、

> **ディレクトリ一覧を非表示にするだけでは対策にならない。**

というのが記事の主張です。

---

# そもそもなぜ本番に `.git` が入るの？

普通に開発しているだけなら`.git`は存在するので、デプロイ方法によっては一緒にコピーしてしまいます。

例えばDockerで、

```
COPY . .
```

とすると、「このディレクトリを丸ごとコピーする」という意味です。

`.dockerignore`で除外していなければ、`.git`まで入ってしまう可能性があります。

つまり、

```
開発PC

my-app/
├── .git/
├── src/
├── package.json
└── ...

        ↓ 丸ごとデプロイ

本番サーバー

my-app/
├── .git/    ← これが問題
├── src/
├── package.json
└── ...
```

ということです。

---

# じゃあどう対策する？

一番重要なのは、

> **本番環境に`.git`を持っていかない。**

です。

例えばDockerなら`.dockerignore`に、

```
.git
```

を入れる。

さらにNginxなどでも、

```
/.git/*
```

へのアクセスを拒否する。

考え方としては、

```
① そもそも置かない
       ↓
② Webサーバーでも拒否
       ↓
③ WAF/CDNでも拒否
       ↓
④ CI/CDで混入チェック
       ↓
⑤ 公開後も監視
```

という**多層防御**にします。

---

# もし `.git` を公開していたら？

ここも重要です。

単純に、

```
rm -rf .git
```

して、

> 「消したからOK！」

ではありません。

すでに誰かに取得されている可能性があるからです。

そのため、

```
.git公開を発見
   ↓
すぐ遮断・削除
   ↓
Git履歴を調査
   ↓
APIキーなどが入っていなかったか確認
   ↓
入っていたらキーを無効化
   ↓
新しいキーを発行
```

まで必要になります。

この「古いキーを無効化して新しいキーに交換する」のが、記事に出てくる**認証情報のローテーション**です。

---

# XSSの記事と合わせて覚えるなら

今回の記事も、セキュリティの基本的な考え方は似ています。

|問題|原因|基本対策|
|---|---|---|
|XSS|信頼できない入力をコードとして扱う|データとして扱う・エスケープ|
|`.git`漏洩|開発用データを本番公開領域に置く|そもそも配置しない|
|APIキー漏洩|秘密情報をコード・Gitに入れる|Secrets等で分離する|

つまりセキュリティでは、

> **「外から見えないはず」ではなく、「見られても困らない構成にする」「不要なものはそもそも置かない」**

という考え方がかなり重要です。

今回の記事で一番覚えておけばいいのは、**`.git`は単なる隠しフォルダではなく、ソースコードの過去を含めた「履歴データベース」のようなもの**という点ですね。
