## データの重複をなくし、管理しやすくする設計方法

---

# 概要

**正規化（Normalization）**とは、

**データの重複を減らし、更新しやすく壊れにくいデータベースを作るための設計方法**です。

簡単に言うと、

> **「同じ情報を何度も保存しないように整理すること」**

です。

データベースを設計するときに、とても重要な考え方になります。

---

# なぜ必要なの？

例えば、ECサイトの商品情報を考えてみます。

注文があるたびに商品情報も保存すると…

| 注文ID | 商品名 | 価格 | メーカー |
|--------|--------|------:|----------|
| 1 | パソコン | 120,000円 | A社 |
| 2 | パソコン | 120,000円 | A社 |
| 3 | パソコン | 120,000円 | A社 |
| 4 | マウス | 5,000円 | B社 |

同じ商品なのに、

```
パソコン
120,000円
A社
```

が何度も保存されています。

これが**重複データ**です。

---

# 重複すると何が困る？

例えば、

パソコンの価格を

```
120,000円

↓

130,000円
```

へ変更するとします。

しかし、

100件あるうち99件だけ変更して、

1件だけ更新し忘れたら…

| 商品名 | 価格 |
|--------|------:|
| パソコン | 130,000円 |
| パソコン | 130,000円 |
| パソコン | **120,000円** |

同じ商品なのに価格が違う

というおかしなデータになってしまいます。

---

# 正規化するとどうなる？

商品情報と注文情報を分けます。

## 商品テーブル

| 商品ID | 商品名 | 価格 | メーカー |
|---------|--------|------:|----------|
| 1 | パソコン |120,000円|A社|
| 2 | マウス |5,000円|B社|

---

## 注文テーブル

| 注文ID | 商品ID |
|--------|--------|
|100|1|
|101|1|
|102|2|

注文テーブルには

```
商品IDだけ
```

保存します。

商品の詳しい情報は

```
商品テーブル
```

だけが持っています。

---

# イメージ図

```
正規化前

注文

────────────

商品名

価格

メーカー

商品名

価格

メーカー

商品名

価格

メーカー

（同じ情報が何度も保存される）
```

↓

```
正規化後

商品テーブル

────────────

商品ID

商品名

価格

メーカー


注文テーブル

────────────

注文ID

商品ID
```

このように役割ごとにテーブルを分けます。

---

# SQLで見ると

商品テーブル

```text
products

id
name
price
maker
```

注文テーブル

```text
orders

id
product_id
```

商品情報を取得するときは

```sql
SELECT *
FROM orders
JOIN products
ON orders.product_id = products.id;
```

のようにJOINで結合します。

---

# 正規化のメリット

### ① 重複がなくなる

```
商品情報

↓

1回だけ保存
```

---

### ② 更新しやすい

価格変更は

```
商品テーブル

1件更新するだけ
```

で済みます。

---

### ③ データが壊れにくい

更新漏れがなくなります。

```
全部130,000円

↓

全部一致
```

となります。

---

### ④ データ容量が減る

例えば

```
商品説明

500文字
```

ある商品が1000件売れた場合、

正規化していないと

```
500文字 × 1000回
```

保存することになります。

正規化すると

```
500文字 × 1回
```

だけで済みます。

---

# 正規化のデメリット

メリットが多い一方で、

テーブルが分かれるため、

取得するときには

```
JOIN
```

が必要になります。

つまり、

```
商品情報

↓

注文情報

↓

JOIN
```

という処理が増えます。

大量データでは、

JOINが多すぎると検索速度が落ちることもあります。

そのため実務では、

**読み取り速度を優先して、あえて一部のデータを重複して持つ（非正規化）**こともあります。

---

# 実務ではどこで使われる？

正規化は、ほぼすべての業務システムで使われています。

例えば、

### ECサイト

```
商品

注文

会員
```

を別々のテーブルに分ける。

---

### 社員管理

```
社員

部署

役職
```

を分ける。

---

### 学校システム

```
学生

授業

履修情報
```

を分ける。

---

### SNS

```
ユーザー

投稿

コメント
```

を分ける。

このように、

**役割ごとにテーブルを分ける**のが基本です。

---

# 「第○正規形」って何？

正規化には

- 第1正規形（1NF）
- 第2正規形（2NF）
- 第3正規形（3NF）

などがあります。

初心者のうちは、

細かいルールを覚えるよりも、

> **「同じ情報を何度も保存しないようにテーブルを分ける」**

という考え方を理解することが大切です。

実務でも、多くの場合は**第3正規形**を意識して設計されます。

---

# まとめ

- 正規化は**データの重複をなくすための設計方法**
- 商品・注文・会員など、役割ごとにテーブルを分ける
- 更新漏れやデータの不整合を防げる
- データ容量を減らせる
- テーブルが増えるため、JOINが必要になることが多い

> **一言で覚えるなら**
>
> **「正規化 = データを整理整頓して、重複をなくす設計方法」**
