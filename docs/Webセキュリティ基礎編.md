― フロントエンドとバックエンド、どちらが守るのか？ ―
## 1. Webセキュリティとは

Webセキュリティとは、

> **Webサービスを、攻撃・情報漏えい・不正利用から守るための仕組み**

です。

Webアプリでは、

```text
ユーザー
↓
ブラウザ
↓
フロントエンド
↓
API
↓
バックエンド
↓
データベース
```

という複数の場所を通って処理されます。

そのため、

> **どこか1か所だけ守ればよい**

というものではありません。

---

# 2. セキュリティはフロント？バック？

結論から言うと、

```text
両方
```

です。

ただし、役割が違います。

|場所|主に守るもの|
|---|---|
|フロントエンド|ブラウザ、画面、入力、Cookie、XSS|
|バックエンド|API、認証、認可、DB、秘密情報|
|インフラ|HTTPS、サーバー、ネットワーク、FW|

---

このそれぞれにセキュリティがあります。

# 4. フロントエンド側のセキュリティ

フロントエンドでは、

```text
画面上の権限制御
```

---

# 5. XSS

代表的なフロントエンド攻撃が、

**XSS**

です。

XSSは、

```text
Cross Site Scripting
```

の略です。

悪意あるJavaScriptをWebページ上で実行させる攻撃です。

例えば、ユーザーが入力した文字をそのままHTMLとして表示するとします。

```html
<script>
  alert("attack");
</script>
```

これがそのまま実行されると危険です。

---

# 6. XSSで何が起こる？

XSSが成功すると、

```text
Cookieを盗む

画面を書き換える

偽ログイン画面を表示

ユーザー操作を盗む

外部サイトへ誘導
```

などが可能になる場合があります。

そのため、

> **ユーザー入力を信用しない**

ことが基本です。

---

# 7. ReactはXSSに強い？

Reactでは通常、

```tsx
<p>{userInput}</p>
```

と書いた場合、危険なHTMLをそのまま実行しないように処理してくれます。

そのため、素のHTML操作よりXSSを起こしにくくなっています。

ただし、

```tsx
dangerouslySetInnerHTML
```

を使う場合には注意が必要です。

名前の通り、

```text
dangerously
```

と付いています。

---

# 8. フロントに秘密情報を書いてはいけない

例えば、

```javascript
const API_KEY =
  "super-secret-key";
```

とフロントエンドに書くのは危険です。

なぜなら、

> **ブラウザへ送られたJavaScriptはユーザーから確認できる**

からです。

つまり、

```text
Reactコード

↓

ビルド

↓

JavaScript

↓

Browser

↓

ユーザーが確認可能
```

です。

---

# 9. 秘密情報はどこに置く？

秘密情報は基本的に、

```text
バックエンド

または

サーバー側環境変数
```

に置きます。

例えば、

```env
DATABASE_PASSWORD=xxxx
SECRET_KEY=xxxx
```

です。

フロントエンドから直接見える場所へ置かないことが重要です。

---

# 10. Cookieの安全設定

認証用Cookieでは、

```text
HttpOnly

Secure

SameSite
```

が重要です。

### HttpOnly

JavaScriptからCookieを読み取れなくする。

### Secure

HTTPS通信のみで送信する。

### SameSite

別サイトからのCookie送信を制限する。

---

# 11. フロントの入力チェック

例えば会員登録フォームで、

```text
メールアドレス

パスワード

電話番号
```

を入力するとします。

フロント側で、

```text
メール形式か

空欄ではないか

文字数は正しいか
```

をチェックします。

これは、

> **ユーザー体験を良くする**

ためにも重要です。

---

# 12. ただしフロントのチェックだけではダメ

例えば、

```javascript
if (age < 18) {
  return;
}
```

とフロントで制御しても、

ユーザーはブラウザを通さず直接APIへアクセスできます。

```text
普通

Browser
↓
API


攻撃者

curl
↓
API
```

つまり、JavaScriptの制御は回避できます。

そのため、

> **重要なチェックは必ずバックエンドでも行う**

必要があります。

# 13. バックエンド側のセキュリティ

バックエンドでは、

```text

認可

入力検証

SQL Injection

```

---

# 14. 認証

認証とは、

> **あなたは誰ですか？**

を確認する処理です。

例えば、

```text
メールアドレス

+

パスワード

↓

本人確認
```

です。

---

# 15. 認可

認可とは、

> **そのユーザーは、この操作をしてよいか？**

を確認する処理です。

例えば、

```text
一般ユーザー
↓
自分の予約だけ見られる


管理者
↓
全ユーザーの予約を見られる
```

という違いです。

---

# 16. フロントで管理者ボタンを隠せば安全？

安全ではありません。

例えば、

```tsx
if (user.role !== "admin") {
  return null;
}
```

として管理者ボタンを隠したとします。

しかし、

```text
POST /api/admin/delete-user
```

というAPIを直接呼べるなら危険です。

そのためバックエンドでも、

```text
このユーザーはadmin？

↓

YES → 実行

NO → 403
```

と確認する必要があります。

---

# 17. セキュリティの基本原則

非常に重要なのが、

> **フロントエンドを信用しない**

という考え方です。

ブラウザ側はユーザーのPC上で動きます。

つまりユーザーは、

```text
JavaScriptを見る

JavaScriptを書き換える

APIを直接呼ぶ

送信データを書き換える
```

ことができます。

そのため、

```text
最終判断
↓
バックエンド
```

が基本です。

---

# 18. SQL Injection

バックエンドで有名な攻撃が、

**SQL Injection**

です。

例えば、

```sql
SELECT *
FROM users
WHERE name = '入力値'
```

というSQLに、ユーザー入力を直接入れると危険です。

悪意あるSQLを入力される可能性があります。

---

# 19. SQL Injection対策

基本的には、

```text
ユーザー入力を
SQL文字列に直接連結しない
```

ことが重要です。

例えば、

```javascript
const query =
  "SELECT * FROM users WHERE id = " + id;
```

のような書き方は避けます。

代わりに、

```text
Prepared Statement

Parameter Binding

ORM
```

などを利用します。

---

# 20. パスワード管理

パスワードは、

```text
password123
```

のような状態でDBへ保存してはいけません。

基本は、

```text
Password

↓

Hash

↓

Database
```

です。

例えば、

```text
password123

↓

bcrypt / Argon2

↓

$2b$12$...
```

のように保存します。

---

# 21. 暗号化とハッシュ化は違う

ここも重要です。

### 暗号化

```text
元に戻せる
```

### ハッシュ化

```text
基本的に元に戻さない
```

パスワードは通常、

```text
ハッシュ化
```

します。

HTTPS通信では、

```text
暗号化
```

を利用します。

---

# 22. APIセキュリティ

WebアプリではAPIが重要です。

例えば、

```text
GET /users

POST /reservations

DELETE /users/123
```

などです。

APIでは、

```text
誰でも呼べる？

ログイン必須？

管理者だけ？

自分のデータだけ？
```

をチェックする必要があります。

---

# 23. IDを変えれば他人のデータが見える？

例えば、

```text
/reservations/100
```

で自分の予約を見られるとします。

URLを、

```text
/reservations/101
```

に変更したら他人の予約が見えてしまう。

これは非常に危険です。

バックエンドで、

```text
予約ID 101

↓

ログインユーザーの予約？

↓

YES → 表示

NO → 拒否
```

と確認する必要があります。

---

# 24. CSRF

Cookie認証で重要なのが、

**CSRF**

です。

例えばユーザーが銀行サイトにログイン中だとします。

```text
銀行サイト

ログイン済み
Cookieあり
```

その状態で悪意あるサイトへアクセスします。

```text
悪意あるサイト

↓

銀行APIへ送金リクエスト

↓

ブラウザがCookieを送る

↓

送金される
```

可能性があります。

---

# 25. CSRF対策

代表的には、

```text
SameSite Cookie

CSRF Token

Origin確認

Referer確認
```

などがあります。

---

# 26. CORS

APIを扱うと、

**CORS**

という言葉もよく出てきます。

CORSは、

> **どのWebサイトからAPIへアクセスしてよいかをブラウザ側で制御する仕組み**

です。

例えば、

```text
https://myapp.com

↓

APIアクセスOK


https://evil.com

↓

APIアクセス拒否
```

という設定ができます。

---

# 27. ただしCORSは認証ではない

重要なのは、

```text
CORS設定している

↓

APIは安全
```

ではないことです。

CORSは主にブラウザの制御です。

攻撃者は、

```text
curl

Postman

独自プログラム
```

から直接APIを呼べます。

そのため、

```text
認証

認可

入力検証
```

が別途必要です。

---

# 28. HTTPS

通信自体を守るのが、

**HTTPS**

です。

```text
Browser

↓

HTTPS

↓

Server
```

HTTPSでは、

```text
暗号化

改ざん防止

サーバー確認
```

を行います。

---

# 29. HTTPSだけでは守れない

例えば、

```text
HTTPS

↓

安全な通信
```

でも、

バックエンド側で、

```text
誰でも管理者APIを使える
```

なら危険です。

つまり、

```text
HTTPS
=
通信経路の安全

認証・認可
=
システム利用の安全
```

です。

---

# 30. Rate Limit

APIでは、

**Rate Limit**

も重要です。

例えばログインAPIへ、

```text
1秒間に10000回
```

パスワードを試されたら危険です。

そこで、

```text
1分間に5回まで
```

などの制限を設けます。

これによって、

```text
ブルートフォース攻撃
```

などを防ぎやすくなります。

---

# 31. ブルートフォース攻撃

ブルートフォース攻撃とは、

> **パスワードを大量に試す攻撃**

です。

例えば、

```text
password

password1

password2

123456

qwerty
```

などを大量に試します。

対策として、

```text
Rate Limit

アカウントロック

多要素認証
```

などがあります。

---

# 32. 多要素認証

MFAは、

**Multi-Factor Authentication**

です。

例えば、

```text
パスワード

+

SMSコード
```

や、

```text
パスワード

+

認証アプリ
```

などです。

パスワードだけより安全性を高められます。

# 34. ポートを開けすぎない

例えばEC2で、

```text

443 HTTPS

```

基本的には、

```text

↓

```

のように、必要な入口だけ公開します。

# 35. Firewall / Security Group

AWSなら、

```text

```

で通信を制御できます。

例えば、

```text

↓
全世界からOK

22
↓

3000
↓
ALBからだけ
```

という設定ができます。

---

# 36. WAF

WAFは、

**Web Application Firewall**

です。

Webアプリへの攻撃を検知・ブロックする仕組みです。

例えば、

```text
ユーザー

↓

WAF

↓

ALB

↓

Application
```

という構成になります。

ReactやNext.jsでは、


そのライブラリに脆弱性が見つかることもあります。

そのため、

```bash

```

などで確認します。

また、

```text
Node.js

Next.js

React

npm package
```

# 38. ログ

セキュリティではログも重要です。

例えば、

```text
誰がログインした？

何回失敗した？

どのIPから？

どのAPIを呼んだ？

管理者が何を変更した？
```

などを記録します。

攻撃が起きた場合、

```text

```

を調査するために必要です。

# 39. エラーメッセージにも注意

例えば、

```text

```

のような詳細情報をそのままユーザーへ返すのは危険です。

ユーザーには、

```text

```

程度にして、

詳細情報はサーバーログへ記録します。

```text

Strict-Transport-Security

Referrer-Policy
```

例えばCSPでは、

```text

```

# 43. 「フロントで防ぐ」と「バックで防ぐ」の違い

例えば入力フォームで、

```text
価格
1000円
```

を送るとします。

フロントで、

```javascript
price = 1000;
```

としていても、ユーザーは通信内容を、

```text
price = 1
```

へ書き換えられます。

そのためバックエンドでは、

```text
フロントから送られた価格
↓
信用しない

商品ID
↓
Databaseで価格取得
↓
正しい価格で決済
```

のように処理する必要があります。

> **Never Trust the Client**

という考え方があります。

つまり、

例えば、


# 50. まとめ

Webセキュリティは、

> **フロントエンド・バックエンド・インフラすべてで守るもの**

です。

役割を簡単に整理すると、

|場所|主なセキュリティ|
|---|---|
|フロント|XSS・Cookie・CSP・秘密情報|
|バック|認証・認可・API・入力検証|
|DB|SQL・アクセス制御|
|インフラ|HTTPS・Firewall・WAF|
|全体|ログ・監視・アップデート|

最も重要な考え方は、

```text
フロント
↓
ユーザー体験 + ブラウザ側の防御

バックエンド
↓
最終的なセキュリティ判断

インフラ
↓
通信・サーバーを守る
```

です。

特に覚えておきたいのは、

> **「フロントで制限しているから安全」ではない**

ということです。

ブラウザはユーザー側にあるため、

```text
通信を書き換える

APIを直接呼ぶ

JavaScriptを書き換える
```

ことができます。

そのため、

```text
入力値は信用しない

権限はサーバーで確認

秘密情報はフロントに置かない

通信はHTTPS

APIでも認証・認可する
```

という考え方が、Webセキュリティの基本になります。
